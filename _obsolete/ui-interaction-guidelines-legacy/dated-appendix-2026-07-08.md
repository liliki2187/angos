## 2026-06-22 补充：主舞台不得空心化

当 UI 页面存在“中央主舞台 / 主工作台 / 主物件”时，不能只为了减少重复或把信息合并到侧栏，就把中央主舞台清空成背景、地图底板、装饰路线或少量标签。合并信息后必须同步补足主舞台的决策内容，或收缩容器。

- **中央单独裁切测试**：遮住侧栏，只看中央主舞台 5 秒，必须能回答当前页面的核心决策问题。派遣签批台中必须能回答“谁去、带什么、补了什么、为什么可签”。答不出，不得交付。
- **空心率测试**：中央主承载物不得出现大面积无功能空白；地图、桌面、纸板、档案夹等背景空白必须被路线、队伍、器材、覆盖关系、风险、补强或等价功能信息解释。
- **右栏越权测试**：侧栏 / 票据 / 详情栏只能做复核、摘要、收据或 CTA，不得成为唯一解释“为什么可执行 / 为什么值得点”的位置。
- **删除回收测试**：从主舞台删掉一块信息后，必须用新的主信息填回，或收缩主舞台面积；不能留下同等面积空洞。
- **旧版优点保护**：返工前列出上一版已经成立的 3 个优点；新稿不能修掉重复、拥挤或边界问题，却丢掉主决策闭环。
- **禁止转场补丁文案**：不要用“见右侧 / 见下方 / 详见票据”等文案修补布局关系；如果必须写这种文案，说明信息归属还没有成立。

该规则由派遣签批台 V3 过度合并反例触发：V3 将“需求覆盖与补强”移入右侧票据后，中央主舞台空心化。后续同类结构稿必须先过本 Gate，再交付给用户。

## 2026-06-22 补充：表达增强不得伪装成新增功能

派遣签批台的中央主舞台只能重排、放大和清晰化既有功能，不得为了填补空间或提高“决策密度”另起第五功能区。尤其是“需求覆盖信息”可以被放大、拆行、标注来源、贴回角色卡或道具槽，但不能包装成 `覆盖矩阵`、`队伍覆盖关系系统`、`协同网络`、`关系算法` 等独立系统对象。

- **四区归属检查**：中央主舞台里的每个块，必须能归属到 `任务人员空槽 / 当前角色列表 / 辅助骰位或随队道具 / 需求覆盖信息` 四区之一；归属不清的块视为新增功能，先退回 UX / UI / 系统边界复审。
- **旧功能放大优先**：当中央显得空、散或信息密度不足时，优先给原四区更多尺寸、状态、贡献标签和关系说明；不要新增一个同级大模块来“解释”原功能。
- **命名降权**：禁止在功能界面中使用会暗示新增玩法的标题，例如 `覆盖矩阵`、`队伍覆盖关系`、`关系网络`、`协同矩阵`。默认使用 `需求覆盖`、`覆盖明细`、`可签依据` 等直接签批语言。
- **表现增强边界**：允许显示“谁贡献了哪项需求”“道具补了哪项缺口”“加入后缺口如何变化”；不允许新增覆盖分、协同值、关系加成、稳定性奖励，也不允许让玩家手动连线、锁定覆盖线或指定角色负责某属性。
- **右侧复核边界**：右侧票据只能复述最终摘要和承载 CTA，不得把“为什么可签”的主解释从中央拿走。遮住右侧后，中央仍应能读懂本次派遣配置成立。
- **交付前误读检查**：截图第一眼如果像多了一个新系统对象，而不是原四区获得了更清楚的表达，则该稿不得交付；先改名、降权、合并回席位 / 道具 / 需求行。

## 2026-06-23 补充：复核摘要优先归右侧票据

派遣签批台的完整复核摘要不应占据中央主舞台。`需求 2/2`、`有效点 13/8`、`缺口 无`、`风险 压力+2`、`耗时 2天` 这类签批前最终核对，优先合并进右侧签批票据；中央只保留贴近操作对象的局部证据，例如角色卡贡献章、器材补缺标签、任务短条需求摘要和薄状态戳印。

- **中央主语检查**：第一眼应读作“正在组一支外勤队并准备盖章派遣”，而不是“正在查看一张校验表 / KPI 面板”。
- **重复复核检查**：如果中央和右侧同时大面积展示覆盖、达标率、缺口、风险，说明复核信息重复；应把完整摘要收进右侧，把中央空间还给人员、候选、器材和拟物工作台。
- **拟物留白允许**：中央可以有约 20-30% 的桌面 / 地图 / 档案负空间，但这些空间必须承托当前任务路线、人员卡摆放、器材托盘、纸层、线索或盖章动线；不得只是空背景。
- **局部证据保留**：把复核表移到右侧后，中央仍要通过角色贡献章、器材补缺、任务短条等回答“为什么大致可签”；不能让玩家必须只看右侧才知道配置效果。
- **候选与人员优先**：释放出的中央高度优先给已选人员席位和候选人员抽屉，其次给随队器材托盘，再给拟物桌面层次；不要用新的横向面板重新填满。
- **交付前截图判断**：截图若被读成后台表格、审批系统或配置页，而不是外勤派遣现场，应退回重排；修正方向是减少系统面板、增加派遣物件和人员操作面积。

## 2026-06-23 补充：拟物留白不得用伪状态块填充

当复核摘要已经归入右侧票据后，中央主舞台不应再用 `需求已满足`、`压力 +2`、`待盖章`、`可签`、`复核通过`、`覆盖已核对` 等小便签 / 戳印 / 状态块填补空位。这些块如果只是把右侧票据的结论换一种形状重复，必须删除，而不是缩小、改色或换成拟物贴纸。

- **删除优先于换皮**：发现重复复核信息时，默认删除；不要把大核对表改成小状态块，把表格问题变成便签问题。
- **三问 Gate**：中央每个非角色、非器材、非候选、非任务短条的块，都必须回答：玩家会操作它吗？它是否提供角色 / 器材附近无法表达的新局部证据？删掉它是否会让派遣操作链断裂？三问全否则删除。
- **负空间允许成立**：中央可以留出干净的地图、纸面、路线、桌面阴影和档案层次；这些拟物空间不需要被状态标签填满。空一些不等于空心，前提是人员席位、器材和候选操作已经清楚。
- **复核单一承载位**：签批状态、风险、耗时、缺口、有效点和盖章前确认只在右侧票据完整表达。中央若需要局部证据，只能贴在角色卡、器材槽或任务短条上。
- **父级整合责任**：subagent 给出“合并到右侧 / 删除重复”的结论后，父级 Codex 不得折中保留同义残留块。若仍不确定，先交付更少元素的结构稿，而不是添加解释性状态块。

## 2026-06-23 补充：派遣签批台必须先重构页面主语

当用户指出“不要只是简单删掉，而是整个界面重构”时，后续派遣签批台不能再以删减单个面板、缩小重复信息或给空白处补便签作为主要改法。父级 Codex 必须先重新确认页面主语、玩家动作和四物件关系，再出结构稿。

- **页面主语 Gate**：V8 以后派遣签批台的第一眼应读作“主编在编辑部外勤案卷桌面上组本次骰池、配辅助骰位并盖章”，而不是“任务条件达标后提交审批”。
- **四物件结构**：整屏默认组织为 `左侧任务卷宗 + 中央外勤案卷桌面 + 底部候选抽屉 + 右侧签批票据`。左侧回答为什么派人；中央回答谁去、带什么、组成了怎样的本次骰池、局部为什么可派；底部只供应人员 / 器材；右侧只做完整复核和 CTA。
- **不得以新功能填空**：中央空间释放后，优先放大已选人员席位、可选增援席、辅助骰位 / 随队器材托盘、本次骰池预备纸、档案底纸和局部贡献证据。不得新增覆盖矩阵、协同网络、队伍关系、路线规划、复核状态块或解释性便签来填补。
- **视觉代入感来自物件承载动作**：人员卡应像外勤证 / 派遣卡，器材应像随队托盘，地图应承载路线与任务地点，票据应是最终签批回执。若拟物元素不能承载当前操作或局部证据，应降级为背景或删除。
- **交付前反问**：遮住右侧票据后，中央是否仍能回答“谁去、带什么、组成了怎样的本次骰池、为什么大致可派”；遮住中央后，右侧是否只剩复核摘要而不是完整玩法解释。任一答案不成立，都不得进入真实内容风格稿或资产化生图。

## 2026-06-23 补充：拟物物件必须对应真实机制

派遣签批台可以有任务地点、地图纹理、路线暗线、图钉和档案纸层来增强外勤感，但这些元素不得暗示游戏内不存在的操作。若游戏没有路线规划、站点选择或路径分配，中央就不能把“路线纸 / 去哪里 / 地图线路”作为高权重功能物件。

- **真实机制优先**：中央拟物物件优先对应 `本次骰池`、`角色骰`、`辅助骰位 / 一次性道具骰`、`需求覆盖 / 有效点目标`、`签批后进入角色骰判定`。
- **路线降级**：路线、地名、图钉、地图折面只能作为背景装饰或任务身份线索，不得拥有标题、字段、按钮、状态、强描边或主要视觉面积。
- **物件越界检查**：每个拟物物件都要回答“玩家是否真的会在游戏里操作 / 判断这个对象”。答案是否时，只能作为无字装饰或 no-text 层；不能成为功能区。
- **中央替代表达**：需要外勤代入感时，优先把“人员证件卡被放入本次骰池”“一次性道具骰写回辅助骰位”“签批后进入角色骰判定”做成桌面物件，而不是发明路线规划物件。

## 2026-06-23 补充：骰面 / 覆盖不得常驻摊成中央表

派遣签批台即使要回到真实机制，也不得把角色骰面、道具骰面、需求覆盖或来源明细常驻摊成中央独立表格。若这些信息可以集成在角色卡、候选卡、道具卡或 hover / 详情层里，就不应占用中央主舞台。

- **卡牌内聚优先**：角色贡献、dice net、适配、补缺和移出动作优先放在角色卡 / 道具卡本体；中央只表达这些卡已经被投入当前任务。
- **苏丹式部署语法**：可参考《苏丹的游戏》的 `候选手牌池 -> 当前事件 / 任务承载 -> 投入卡牌 -> 右侧说明 / 确认`。学的是部署关系，不是宫廷皮肤、旧羊皮纸或整屏装饰。
- **表格降级**：完整骰面矩阵、来源明细和覆盖表默认进入 hover、详情、调试或右侧短说明；不得作为中央常驻主物件。
- **中央空间优先级**：中央空间优先给任务案卷承载台、已选卡槽、空槽、随队器材槽和当前投入卡之间的归属关系，而不是给解释表。

## 2026-06-23 补充：底层重构不得沿用旧骨架换皮

当用户要求“从底层重新思考界面怎么布置”时，不能只把旧页面的四栏骨架换成新标题、新纸张或新拟物称呼。派遣签批台 V9 复盘已确认：如果页面仍是 `左任务 + 中央已选卡 + 右复核票据 + 底部候选库存`，即使中间画了案卷、图钉或纸层，也仍然是旧结构。

- **骨架剪影检查**：遮住文案和材质，只看大块位置。若仍能一眼认出旧四栏，就不得称为底层重构。
- **动线重排检查**：新结构必须改变玩家视线顺序和操作动作，例如从 `候选手牌 -> 当前案卷 -> 本次队伍 -> 右下盖章` 读起，而不是继续 `左读题 -> 中停卡 -> 右看数 -> 下补卡`。
- **职责迁移检查**：至少改变两类关键职责的位置或关系：候选层、当前队伍、任务承载物、签批回执、CTA 锚点。只改变宽度、高度、标签或装饰不算。
- **旧稿降级**：V8.2 的苏丹式经验只保留“卡牌投入语法”；V9 降级为旧骨架换皮反例。后续真实内容风格稿和生图 prompt 不得以 V9 作为布局基准。
- **父级自检责任**：在让用户看图前，父级 Codex 必须先写出一句新的玩家动作流。写不出，或写出的句子与旧版相同，就先重排结构，不要交付截图。

## 2026-06-23 补充：左右栏成立时只重构中间主舞台

若用户明确指出左右两边栏目没有问题，父级 Codex 不得继续推翻整屏。此时问题域应锁定在中间主舞台：如何让中间空白成为“当前派遣现场”，而不是新增功能或重复右侧复核。

- **保留边界**：左侧继续承载任务卷宗 / 简报 / 外勤目的；右侧继续承载签批票据 / 复核清单 / 盖章 CTA；底部继续作为候选员工与器材抽屉。
- **中间改造目标**：把已选角色、空槽、随队器材和任务案卷底板组织成一个 `当前外勤承载台`。玩家第一眼应看到“这支队伍已经被放到 M330 案卷上”，而不是看到空桌面或后台状态条。
- **不新增功能**：不得用路线规划、中央骰池表、覆盖矩阵、队伍关系、伪状态块或解释便签填补空白。空白应通过卡片尺寸、纸层、压入关系、器材嵌入条和拟物背景解决。
- **局部证据位置**：角色贡献、补缺、低贡献风险放在角色卡和器材卡上；完整达标率、耗时、缺口和盖章前状态仍归右侧票据。
- **交付前检查**：只裁切中间区域看 5 秒，必须能回答“派谁 / 带什么 / 还缺哪个槽 / 卡片属于哪份任务”。若不能，先重排中间，不动左右。

## 2026-06-18 补充：任务级 CTA 与全局推进动作不得相邻

当一个页面同时存在“当前对象确认动作”和“全局时间 / 阶段推进动作”时，必须把二者在空间、材质、颜色语法和点击热区上分离：

- 当前对象动作只作用于当前选中任务、卡片、稿件或队伍，例如 `进入派遣签批`、`签批本次派遣`。
- 全局推进动作会改变天数、周阶段、结算或世界状态，例如 `推进一天`、`结束探索周`、`进入发刊结算`。
- 全局推进动作不得放在当前对象主 CTA 的正下方、右侧紧邻、同一托盘内或同一视觉延长线上；玩家不能因为追随主 CTA 动线而误触全局推进。
- 两者不得共享按钮底图、颜色语法、装饰托盘或 hit rect；资产化 UI 中必须拆成独立 atlas、状态矩阵和安全区。
- 全局推进若可能造成任务错过、截稿流失、占用天数或状态结算，应提供确认态、长按、二次点击或等价误触保护。

本规则由地区任务台 v3.6 触发：`进入派遣签批` 属于右侧任务详情，`推进一天` 属于底部全局日程条，二者不得相邻。

## 2026-06-18 补充：功能承载页必须方正

用户在派遣签批台 V16 继续推进时明确指出：功能页面一定要方正，斜的界面资源很不好用。后续资产化 UI 应把这条视为比“拟物层次感”更高优先级的生产约束：

- 凡承载动态文字、数字、头像状态、按钮文案、可点击热区或状态矩阵的正面区域，必须是 square-on、axis-aligned、可测量的矩形。
- 签批票据、任务卡、正文纸、候选抽屉、器材托盘、CTA 文本槽和 ticker 文本槽不得整体倾斜、透视或做成梯形。
- 斜切、纸层、折角、外侧标签、夹子、票据舌片、阴影和半调可以保留，但只能作为背景、外轮廓或 `no_text_rects`；不得压入正文、数值、按钮 label 或 hit rect。
- 如果生图结果“整体好看但可写面倾斜”，应降级为灵感图 / 偏差案例，不能通过缩小字体、贴边排版或临时面板盖图补救。
- 交付前必须至少裁切检查一个核心功能页局部，例如右侧签批票据、底部 CTA、任务卡正文或候选卡，确认可写区和按钮区确实为 0 度正交。

## 2026-06-29 补充：方正不能只靠肉眼验收，必须做几何 QA

世界地图 v0.40 生图稿曾在 prompt 和文字记录中声明“信息面正交”，但用户复核指出右侧 dossier 仍明显倾斜。该问题说明：硬规则写入 prompt 不等于结果合格，整图肉眼检查也不能替代局部几何验收。

- 凡被称为“正交通过 / 可落地候选 / 前排参考”的资产化 UI 生图稿，交付前必须裁切核心信息面并叠加水平 / 垂直参考线。
- 对标题纸面、照片框、CTA 文本槽、状态票据、按钮热区等核心承载面，默认测量上 / 下 / 左 / 右边线；任一核心边线相对画布水平或垂直偏差超过 `0.5 deg`，不得判定为通过稿。
- QA 参考线必须贴住真实生成边缘；不能只在旁边画一个理想水平矩形来证明“应该是正的”。若参考框水平但实际纸边、CTA 边、文本槽边或票据边仍倾斜，判定为 false pass。
- 把候选交给用户做正向把关，也视为一次放行。若没有真实边缘角度 QA，只能标记“几何未验证 / 待测”，不得说“基本正交”“可以把关”“差不多正”。用户把关只能裁决风格、取舍和业务语义，不能替代 AI 先跑功能面正交硬门槛。
- 文字界面不斜是铁律。若同一类功能行在上一轮已经因倾斜失败，新一轮仍出现可见倾斜，不得继续用 prompt-only 整屏有字生图微调；必须转入分层工作流：生图只做无字材质、外轮廓、装饰和主图，文本槽 / CTA / hit rect / 状态条用正交资产、mask、Godot / DOM 运行时 UI 或可测量矢量层重建。
- 允许夹子、背页、纸边、折角、阴影、外侧标签和装饰贴纸倾斜；不允许它们带动可写区、按钮 label、状态数字或 hit rect 倾斜。
- 如果模型生成结果文字嵌合、颜色和质感都更好，但信息面倾斜，仍应降级为偏差样本。不能为了保留风格优势而放宽方正规则。
- 最终交付此类风格稿时，优先同时附“原图 + 正交 QA 图 / 局部裁切”，避免只用整图观感替代验收。

## 2026-06-15 补充：拟物纸张与动态文字安全区

世界地图、档案夹、票据、索引卡、签批纸等资产化 UI 可以使用倾斜纸页、叠页、夹子、口袋和标签制造拟物层次，但凡承载 Godot 动态文字、数字、状态或按钮文案的正面区域，必须优先满足可布局性：

- **承载文字的正面必须正交**：主纸面、卡片内框、CTA 文本槽、ticker 文本槽要与画布水平 / 垂直对齐；不要让动态文字跟随透视、旋转或斜纸边。
- **所有功能组件必须正交**：本规则不只针对右侧 dossier。左侧卡片、中央地图板、地图 pin / 选中热区、底部 ticker / receipt、CTA、状态票据、筛选签、拖拽槽、候选卡、确认按钮、日程器等，只要承载信息、状态、点击、hover、pressed、disabled、selected、drag-over 或其它玩家可操作语义，就必须使用 0 度正交功能面。只有不承载功能的夹子、背页、贴纸、纸边、阴影、胶带、外侧标签和纯装饰层可以倾斜。
- **正交不等于扁平化**：功能组件通过正交 Gate 后，还必须保留所属风格稿的材质语言。对 clean low-poly weekly / WMW 支线来说，左卡、右侧 dossier、CTA、ticker、票据和地图板即使正面 0 度，也应保留大块低多边形平面色块、4-8 个主要明度块面、块状明暗面和克制的裁纸阴影；只有动态文字中心槽需要安静，且不得有明显褶皱 / 折痕 / wrinkle / fold / tear 线穿过。若修正交后组件变成纯平空白矩形、SaaS 表单条或软件面板，应判定为风格保留失败。
- **装饰不得压内容边距**：三角兜、夹子、书签、色块、箭头、半调网点、折角、螺丝和装订边只能压在装饰层或禁入区，不得覆盖卡片正文框、标题槽、状态槽、按钮 label 槽和可读外边距。
- **图片内容不得非等比缩放**：地区缩略图、快照、角色头像、物品图、照片、地图 inset、证据图和任何静态内容图，不能为了塞进 UI 槽而直接拉伸或压扁。`photo_rect / snapshot_rect / portrait_rect / icon_art_rect` 必须先通过 `image_aspect_pass`：要么保持比例 cover crop，要么保持比例 contain 并明确留边 / matte，要么重设组件槽比例；不得使用非等比 `resize` 作为验收图或 atlas 来源。若组件壳正交、文字也放得下，但图片被压扁，仍判定该组件失败。
- **已有图槽与图片构图视为合同**：当用户认可的标杆或上一版 UI 中，`photo_rect / snapshot_rect` 和图片构图已经配合良好时，这个配合关系必须作为 `image_slot_contract_pass` 锁定。修正卡片正交、文字槽、按钮槽或状态区时，不得擅自改变照片槽宽高比，再用 cover crop 把旧图塞进去；cover crop 只能用于轻微裁边，不能遮盖“组件槽比例改错”的问题。若确实要改变图槽比例，必须同步重生 / 重裁快照到新比例，或把组件槽比例退回原合同。
- **先画视觉可写区，再落文字**：资产验收时不能只看控件 rect 是否未出界，要标出真实可写纸面、no-text rect 和至少 32px 视觉安全边距，再决定 Godot 动态层的位置。
- **底部 / 末张卡优先检查**：叠页和档案夹最容易在最后一张卡、底部 CTA、右侧详情纸板发生遮挡或斜切；截图验收必须局部裁切检查这些区域，而不是只看整屏远景。
- **不靠缩小字体补救资产问题**：如果 PNG 本身没有正交可写区或可读边距不足，应重出美术资源；不要通过减小字号、贴边排版或把文字挤进斜面来硬塞。

## 2026-06-24 补充：美术标杆必须转译成组件生产语法

当用户给出新的 UI / 美术风格标杆时，父级 Codex 不能只生成一张“看起来像标杆”的 moodboard、style board 或整屏相似图。除非用户明确要求只要灵感图，否则下一步必须把标杆转译成 Angus 真实界面的组件改造蓝图。

- **先盘点真实组件**：至少覆盖世界地图、地区任务台、派遣签批台、报道 / 发刊、角色 / 骰子、全局 HUD 中反复出现的组件，例如主舞台、地区索引卡、地图 pin、任务卡、详情纸、角色卡、候选抽屉、签批票据、主 CTA、全局推进、ticker、弹窗和状态贴纸。
- **每类组件必须给生产语法**：输出该组件应读作什么物件、承载什么玩家决策、对应哪些 `content_rects / no_text_rects / hit_rects`、需要哪些状态矩阵，以及哪些信息不得烘焙进底图。
- **标杆只提供语言，不替代功能分区**：深蓝主场、低多边形照片、现代编辑设计、周刊 / 案卷 / 文件夹 / 便签 / 贴纸 / CRT / CD 等风格元素，只能包装既有真实功能；不得为了贴近标杆新增不存在的路线规划、后台终端、证据墙或装饰性状态块。
- **组件化不得变成面板化**：把标杆用于真实 UI 时，不能只保留 `左列表 / 中地图 / 右详情` 这种功能骨架，然后丢掉标杆的资产板密度、纸件叠层、橄榄绿 / 芥末黄文件夹、大胆周刊版式、贴纸 / 夹子 / 照片 / 色票 / 图标系统。若第一眼不像用户给的标杆，即使可操作区清晰，也只能算偏差稿。
- **低多边形必须先看块面颗粒度**：新标杆里的低多边形是大块概括、手绘裁纸感和形状经济，不是密集三角网、GIS 终端纹理、摄影噪声或票据微装饰。世界地图、地区卡、dossier 快照和周刊图像应先成立大块剪影；票条、ticker、CTA 同屏只保留极少微细节，孔洞、条码、点阵、短刻度、微线不得堆叠。
- **低多边形必须留在组件本体上**：不能只让缩略图 / 快照保留低多边形，而把功能组件外壳做成平面 UI。若风格标杆的价值来自纸件上的平面色块、切面明度和手绘贴纸张力，左卡壳、右 dossier 纸面、CTA plate、底部 receipt 和状态票据都必须继承这些大块面语言；但文字组件上不能出现纸张被折起的褶皱线。
- **先做单组件或单状态 vertical slice**：优先选择一个真实状态验证，例如“北美禁区 selected + 红线升温 + 可进入”的右侧详情，或“M330 当前队伍 + 可签批”的派遣中间主舞台。单状态的图文功能融合通过后，再扩展全屏、多状态和运行时。
- **生图 prompt 必须带组件约束**：若使用生图推进 UI，prompt 必须声明目标组件、动态文字空白区、禁写区、状态层和运行时动态字段；不得只写“照着标杆风格做一张界面”。
- **交付必须说明可落地性**：最终交付除视觉图外，还要说明哪些部分是 bitmap 底图、哪些是动态 UI、哪些需要独立 atlas / 状态贴图、哪些只是灵感图不能直接切入运行时。

## 2026-07-01 补充：修标杆组件不得扩大成整屏重生

当用户的目标是“把标杆组件改正、包装成实际游戏界面可用的组件”，父级 Codex 不得把任务升级为反复生成完整世界地图、完整地区页或完整派遣页。整屏生图会重新采样布局、色调、材质、地图块面和按钮语法，容易把已经认可的标杆特征洗掉。

- **锁定不变项**：标杆的深色主场、纸品色号、大块低多边形色面、手绘贴纸符号、现代周刊物件和已认可布局先冻结；本轮只修组件可落地问题。
- **先组件板后整屏**：优先输出 `component_correction_sheet`，覆盖地区卡、右侧 dossier、CTA、底部 receipt、状态票据、贴纸 icon、标题条和 folder tab。组件板只验证组件语法，不验证整屏动线。
- **最小改造目标**：只解决正交、动态文字可写区、按钮/框体嵌合、状态矩阵、图标手绘感、低多边形块面保留和色号漂移；不得顺手重画世界地图、路线、任务内容或全屏构图。
- **回填验证**：组件板通过用户把关后，再选一个真实状态，例如“北美禁区 selected + 红线升温 + 可进入”，把组件回填到世界地图单屏验证。未通过组件板，不进入 atlas、manifest 或 Godot runtime。
- **产物命名**：这种图只能叫组件转译候选或组件校正板；在完成真实中文填充、几何 QA、色号复采样和像素艺术复审前，不得叫生产标杆或资源真源。

## 2026-07-01 补充：WMW 支线纸张材质必须先锁定

Clean low-poly weekly / WMW 支线里，纸张不是普通背景色，而是核心材质语言。后续世界地图、地区界面、任务派遣、票据、dossier、CTA 和状态卡只要使用该支线纸品组件，就必须先引用 `design/art-direction/clean-lowpoly-weekly-paper-material-contract.md`，不得只靠 prompt 写“高级灰 / warm beige / paper texture”让模型自由生成。

- **纸张真源来自标杆裁切**：使用 `docs/screenshots/2026-07-01-wmw-component-correction/13-wmw-paper-material-truth-board-v0-3.png` 与对应 JSON token 作为纸张校色尺。失败候选图不能反向成为纸张真源。
- **先材质后整屏**：先声明组件使用哪个纸张 token，再做组件板、单状态 mock 或整屏回填。没有纸张 token，不进入风格通过判断。

- **生产建议**：若要追求稳定一致，生图只负责形状和氛围，纸张可通过 mask、材质 atlas 或 Lab 色彩归一化回到标杆 token；不要每次全局重调整张图。

## 2026-07-06 补充：文字正交不等于美术壳正交

世界地图 WMW 右侧 dossier 在 v0.3/v0.4 迭代中暴露了一个反复误判：运行时文字层是水平的，但底层按钮框、标题框或纸面美术壳仍然带斜角 / 透视 / 整体倾斜。此时文字会像浮在错误物件上，不能算 UI 落地通过。

- **两张通行证**：任何承载动态文字、按钮 label、状态数值或 hit rect 的组件，必须同时通过 `text_geometry_pass` 和 `art_shell_geometry_pass`。只验证文字没有出框，只能说明容量通过，不能说明资产可用。
- **先验美术壳，再回填文字**：右侧 dossier、CTA、左侧地区卡、底部 receipt、ticker、状态章、任务卡、候选卡等功能组件，必须先交付 no-text shell / geometry QA crop，证明真实 bitmap 边缘、颜色模块、文本槽和按钮热区同轴，再进入真实文字回填。
- **QA 框要贴真实边缘**：参考线和检测框必须沿着可见美术壳的上 / 下 / 左 / 右边走。若绿色安全框是正的，但底层红 / 蓝 / 绿按钮壳是斜的，判定失败。
- **不把斜切当倾斜豁免**：角切、纸边、外侧装饰、夹子、背页可以斜；但它们不得带动正文槽、按钮 label 槽、状态槽、action plate 或 hit rect 倾斜。功能面主边仍必须 0 度水平 / 垂直。
- **低多边形色块只能是材质，不是褶皱或箭头**：功能文字槽内允许低对比的大块面色差，但不得出现会被读成折痕、撕裂、压痕、高对比斜线、尖刺、箭头、路线指示或按钮延伸的形状。即使尖形块面没有越过 `visual_module_rect`，只要它刺向文字槽、图标槽或 action plate，也判定为失败。文字槽越核心，色块越克制，优先使用横向压边、宽面明暗和低对比矩形块。
- **失败处理**：一旦发现“文字层正、底层壳斜”，不得继续调字号、调 safe zone 或在整屏图上补贴片。必须退回到分层资产：重建正交 no-text 壳，锁定 shell manifest，再回填文字。
