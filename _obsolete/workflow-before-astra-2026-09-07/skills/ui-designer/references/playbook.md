# PLAYBOOK · UI Designer × UX Critic 协作工作流

> **本文件目的**：给 UI Designer Agent 和 UX Critic Agent 的**联合使用者**（你 / 主调度器 / 团队成员）一份操作手册，让两个 agent 配合产出 1 + 1 > 2 的成果。

---

## 🎭 两个 agent 是什么关系？

```
            ┌────────────────────┐
            │   UI 工作的本质      │
            ├────────────────────┤
            │                     │
            │  🏗️ 从 0 设计       │  ← UI Designer Agent
            │      ↓              │
            │  🩺 评审已有        │  ← UX Critic Agent
            │      ↓              │
            │  🔄 迭代            │  ← 两个 agent 接力
            │                     │
            └────────────────────┘
```

**核心定位差异**：

|  | UI Designer | UX Critic |
|---|---|---|
| 角色 | 建筑师 🏗️ | 医生 🩺 |
| 心智 | "我来造一个" | "我来检查一下" |
| 时机 | UI 还不存在 | UI 已经存在 |
| 输入 | brief / 需求文字 | 截图 / 现有 UI |
| 主要输出 | 元素清单 + 布局 mock + 设计规范 | 认知负荷诊断 + 业务风险 + 改进建议 |
| 用户问法 | "帮我设计 X" | "X 好不好用" |
| 失败时 | 出垃圾 mock（可丢弃） | 给错误诊断（可能误导） |
| 性格 | 主张 / 决策 / 执行 | 怀疑 / 拷问 / 建议 |

**铁律**：**两个 agent 不能互相替代**。让 UI Designer 做评审 → 它会自我表扬；让 UX Critic 做设计 → 它给的是改进建议而不是 mock。

## 🗺️ 三种协作模式

### 模式 A · 单独调用（90% 的日常场景）

#### A.1 只用 UI Designer
```
触发关键词：
  - "帮我设计"、"画一下"、"做个 mock"、"出 wireframe"、"从 0 开始"
  - "我有个 brief"、"这是需求文档"
  - "活动页 / 商店页 / 登录页 / 关卡 UI / HUD"

例子：
  用户: "帮我设计一个独立游戏角色选择界面"
  → @UI Designer
```

#### A.2 只用 UX Critic
```
触发关键词：
  - "评审"、"诊断"、"看看哪里不好"、"有问题吗"、"可用性"
  - "竞品对比"、"AB 测试结果"、"认知负荷"
  - "用户反馈说..."

例子：
  用户: "看看这个登录页有什么问题"  [上传截图]
  → @UX Critic
```

### 模式 B · 接力（设计 → 评审 → 改进）⭐ 最高价值场景

```
用户: "我要做一个游戏商店页"
   │
   ▼
┌─────────────────────┐
│ Phase 1 · 设计 v1   │
├─────────────────────┤
│ @UI Designer        │
│ - 提取元素对照表     │
│ - 风格匹配判定       │
│ - 出 mock v1        │
│ - 输出"给 UX Critic │
│   的上下文摘要"      │
└──────────┬──────────┘
           │
           ▼
┌─────────────────────┐
│ Phase 2 · 评审 v1   │
├─────────────────────┤
│ @UX Critic          │
│ - 收 mock v1 + 摘要 │
│ - 认知负荷诊断       │
│ - 业务风险扫描       │
│ - 给改进建议清单     │
│   (P0/P1/P2 分级)   │
└──────────┬──────────┘
           │
           ▼
┌─────────────────────┐
│ Phase 3 · 改进 v2   │
├─────────────────────┤
│ @UI Designer        │
│ - 收 UX Critic 建议 │
│ - 按 P0 必改        │
│ - P1 视情况采纳      │
│ - 出 mock v2        │
│ - 标注改了什么       │
└──────────┬──────────┘
           │
           ▼
   循环 Phase 2-3 直到稳定
   (一般 2-3 轮就够)
```

**用户怎么发起这个流程？**

主调度器 / 用户的标准发起话术：
> "帮我设计一个商店页，**完成后让 UX Critic 评审一下**"

或者分两步：
> 1. "帮我设计一个商店页" → 拿到 v1 mock
> 2. "@UX Critic 评审一下" → 拿到改进建议
> 3. "@UI Designer 按建议改" → 拿到 v2 mock

## 🚦 路由决策树（用户该 @ 谁？）

```
用户输入
  │
  ├── 有现成 UI 截图吗？
  │     │
  │     ├── 有
  │     │   ├── 问"好不好" → UX Critic 单独
  │     │   ├── 问"改进" → UX Critic（先诊断）→ UI Designer（改）
  │     │   └── 问"对比 A/B" → UX Critic 单独
  │     │
  │     └── 没有
  │         ├── 给 brief / 需求 → UI Designer 单独
  │         ├── 给 brief + 要评审 → UI Designer → UX Critic 接力
  │         └── 模糊不清 → UI Designer 主动询问"从 0 设计还是评审现有"
  │
  └── 用户明确说"评审 / 诊断 / 看看好不好" → 直接 UX Critic
  └── 用户明确说"设计 / 画 / 做 mock" → 直接 UI Designer
```

## 🔌 数据交接协议（两个 agent 之间怎么传数据）

### 4.1 UI Designer → UX Critic 的标准交接

UI Designer 完成 mock 后，会**自动输出**这一段（详见 SPEC §10.3.1）：

```markdown
---
## 给 UX Critic 的上下文摘要

### 设计意图
（一句话说本设计要解决的核心问题）

### 元素对照表（精简版）
| # | 元素 | 类型 | 文案 | 位置 |
| 1 | ... | ... | ... | ... |

### 已应用的设计约束
- 字号档位：使用了 L1/L2/L4/L6
- 颜色语义：主操作（橙）/ 辅助说明（灰）
- 主次按钮：1 主 + 2 辅（无混用）

### Confidence Gate 决策记录
- AUTO-DECIDE：风格匹配度 🟡，已选择降级方案 X
- TAG：未指定 padding，按规范默认 24px

### 已知降级项 / 待改进
- 缺少品牌色（用户未提供）
- 缺少 favicon（待用户补）
```

### 4.2 把这段交给 UX Critic 时怎么说？

```
"@UX Critic 评审下面这份设计：

[贴 mock 图]

[贴上下文摘要]"
```

UX Critic 会优先**读上下文摘要**，避免误判约束选择为缺陷。比如它看到摘要里说"主次按钮无混用"，就不会再提"建议拆分按钮层级"这种 Designer 已经处理过的问题。

### 4.3 UX Critic → UI Designer 的标准交接

UX Critic 输出建议清单格式：

```markdown
## 改进建议

| # | 问题位置 | 严重等级 | 改进方向 | 优先级 |
|---|---------|---------|---------|--------|
| 1 | 主 CTA 按钮 | 🔴 高 | 加大点击区到 ≥44pt | P0 |
| 2 | 字号 L4/L5 混用 | 🟡 中 | 统一到 L4 | P1 |
| 3 | 倒计时无 Doherty 阈值 | 🟢 低 | <400ms 反馈 | P2 |
```

### 4.4 UI Designer 接收建议的转换规则

```
🔴 P0 必改 → 写进 v2 的「修改项」
🟡 P1 选改 → 标注「视情况采纳」
🟢 P2 可改 → 仅记录，不强制改

输出 v2 mock 时必须有「相对 v1 的变更说明」：
- ✅ 已改：xxx（按 P0 #1 建议）
- 🟡 部分采纳：yyy（按 P1 #2，但保留 X 因为 ...）
- ⏭ 暂不改：zzz（P2 #3，留下次迭代）
```

## 📊 效率最大化的 5 个实战技巧

### 技巧 1 · 用「接力」而非「合并」

❌ **不要这样**：
```
"帮我设计一个商店页并评审一下，给我最终版"
```
（一句话同时找两个 agent → 它们会混乱，输出质量下降）

✅ **应该这样**：
```
"@UI Designer 帮我设计一个商店页"
[等输出 v1]
"现在 @UX Critic 评审 v1"
[等输出建议]
"@UI Designer 按这些建议出 v2"
```

### 技巧 2 · 给上下文摘要留 token 预算

UI Designer 的 §10.3.1 上下文摘要可能占 200-500 token。在长会话里这是值得的——它让 UX Critic 评审准确度提升 30%+，且避免「Critic 提的建议 Designer 早已规避」的浪费。

### 技巧 3 · 让两个 agent 看到同一份原始 brief

理想情况下，把原始 brief 也传给 UX Critic（不只是给 mock）。这样 Critic 能判断"mock 是否完整覆盖 brief 的需求"，而不只是"mock 本身好不好"。

### 技巧 4 · 控制迭代轮次（≤ 3 轮）

```
v1（设计）→ v2（修 P0）→ v3（修 P1 + 验证）= 3 轮
```

超过 3 轮通常意味着：
- brief 本身没想清楚 → 回去补 brief
- 风格 / 资源根本不匹配 → 走 NEEDS_NEW_ASSETS 路径
- 两个 agent 在打架 → 换一个更明确的诉求

### 技巧 5 · 复杂项目用「分页接力」

不要一次让两个 agent 处理整个游戏所有 UI。**按页面分批接力**：

```
Week 1: 登录页（设计 → 评审 → 改）
Week 2: 主菜单（设计 → 评审 → 改）
Week 3: 商店页（设计 → 评审 → 改）
...
```

每页只在两个 agent 间循环 ≤ 3 轮。整个项目走完 = 高质量 + 可控成本。

## 🚫 协作禁令（绝对不要做）

### 禁令 1 · 不让 UI Designer 评审
❌ "@UI Designer 看看这个截图怎么样"
（它不懂 UX 评审，会自我表扬或乱给建议）
✅ 改成 → "@UX Critic 看看这个截图怎么样"

### 禁令 2 · 不让 UX Critic 出 mock
❌ "@UX Critic 帮我画一个改进版"
（它擅长诊断不擅长出稿，画出来的 mock 通常没有设计约束）
✅ 改成 → "@UX Critic 给改进建议" → "@UI Designer 按建议出改进版 mock"

### 禁令 3 · 不在同一对话里反复切角色
```
❌ 你: 设计  / 评审 / 设计 / 评审 / 设计 / ...
（agent 角色切换会污染上下文，质量逐轮下降）
✅ 用 ≤3 轮就收敛
```

### 禁令 4 · 不忽略 Confidence Gate 警告
当 UI Designer 触发 🔴 AUTO-DECIDE（风格不匹配）时：
❌ "你别管，硬塞一个出来"
（它会出垃圾稿）
✅ 走 NEEDS_NEW_ASSETS 路径找美术 / 用 gemini-image 出概念稿

### 禁令 5 · 不让两个 agent 直接对话（如果你的平台支持 multi-agent）
即使技术上能让 UI Designer 和 UX Critic 自动接力，**强烈建议保留人在中间**：
- 你能在中间补充新需求
- 你能否决某条 P0 建议（业务原因）
- 你能控制何时停止迭代

## 🎁 适用场景速查表

| 场景 | 推荐流程 | 预估轮次 |
|------|---------|---------|
| 全新页面从 0 设计 | UI Designer 单独 | 1 轮 |
| 评审现有页面找问题 | UX Critic 单独 | 1 轮 |
| 改进现有页面 | UX Critic → UI Designer | 2 轮 |
| 高质量从 0 设计 | UI Designer → UX Critic → UI Designer | 3 轮 |
| 多版本 AB 验证 | UI Designer ×N → UX Critic 对比 | 1+N 轮 |
| 竞品分析 | UX Critic 单独（多张截图） | 1 轮 |
| 风格探索 | UI Designer 多次（变 brief） | N 轮 |
| 设计系统建立 | UI Designer 出基准 → UX Critic 验证 → 沉淀规范 | 2-3 轮 |

## 📦 配套交付物清单

每完成一个完整接力流程，最终交付物应该包含：

```
✅ 必出：
1. 元素对照表（来自 UI Designer Phase 0）
2. 最终版 mock（v2 或 v3）
3. UX Critic 的最终评审报告
4. 变更日志（v1→v2→v3 改了什么）

🟡 推荐：
5. 设计 rationale（解释关键决策）
6. NEEDS_NEW_ASSETS 清单（如有）
7. 下一步行动（开发交付清单 / 美术补漏清单）
```
