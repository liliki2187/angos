# AI Radar Loop Cases

> 状态：2026-07-02 起维护。
> 用途：记录 AI 日报 / 次报线程的强反馈、错题本和可转 eval case。每次发日报前先读本文件，防止重复犯同一类错。
> 家族归属（2026-07-08 起）：AIR-CASE-005（旧内容冒充今日日报）与 AIR-CASE-006（配置存在冒充调度可用）属于全项目错误家族 F1「验证等级冒充」，家族索引见 `docs/onboarding/ai-collaboration-guidance.md` §7.0；本文件只记日报域内的触发器和实例，家族级复发判定与升级律以该索引和 harness §5.2 为准。

## Active Loop Cases

### AIR-CASE-001. Benchmark 被误写成工具能力

- **触发来源**：TUA-Bench 图文页复盘。
- **用户反馈**：TUA-Bench 的工作不是文档编辑、邮件管理等，而是用 120 个真实任务验证 agent 能力。
- **错误模式**：把 benchmark 里的任务领域写成了“这个工具实际能做什么”，混淆了评测集、被测 agent 和真实产品能力。
- **防复发规则**：遇到 benchmark / eval / dataset / survey，必须先说明“它评估什么 / 用什么任务评估 / 它本身不是生产工具”。
- **交付前检查**：重点条目里若 `类型` 包含 benchmark、eval、dataset、survey，`它实际能做什么` 必须改成“它能提供什么评测或判断”，不能写成可直接操作的产品能力。
- **适用范围**：AI 日报、周报、图文页、agent workflow 工具筛选。
- **Eval 可能性**：high。可检查标题和能力描述是否出现“它能编辑文档 / 管理邮件 / 操作软件”等冒充工具能力的表述。
- **状态**：active。

### AIR-CASE-002. “雷达”误用为单个工具标题

- **触发来源**：LiveEdit 图文页标题误写为“视频生成雷达”。
- **用户反馈**：LiveEdit 不是雷达，而是视频局部编辑工具。
- **错误模式**：把栏目名 / 报告名“雷达”误塞进单个工具标题，造成工具性质错误。
- **防复发规则**：“AI Radar / 雷达”只可作为日报栏目名，不能作为具体工具名或能力名，除非来源官方名称就是 Radar。
- **交付前检查**：每个重点条目的大标题必须先回答“这是什么工具 / 论文 / 变化”，再给正式名称。标题不得出现非官方的“雷达化”命名。
- **适用范围**：日报标题、图文页标题、生成图 prompt。
- **Eval 可能性**：medium。可检查非报告标题中是否出现“雷达”。
- **状态**：active。

### AIR-CASE-003. 图形化降低信息密度

- **触发来源**：TUA-Bench 图文页初版。
- **用户反馈**：图形化之后文字量太少，更看不懂；不要为了图形化降低信息密度。
- **错误模式**：为了生成图片，把复杂条目压缩成几个短标签，丢失“它是什么、实际能做什么、为什么重要、不要误读”。
- **防复发规则**：先写文字版，再图形化。图形化不等于少字；密集中文解释优先使用可控排版，不优先依赖生图模型写字。
- **交付前检查**：重点图文页必须包含 5 个模块：人话标题、它是什么、实际能做什么 / 示例、制作人判断、风险误读。若没有这些模块，不交付为正式图文页。
- **适用范围**：日报重点图文页、工具解释卡、周报长图。
- **Eval 可能性**：medium。
- **状态**：active。

### AIR-CASE-004. Angus 判断压过工具事实

- **触发来源**：日报图文页结构反馈。
- **用户反馈**：缺少“这个工具实际可以做什么、有什么示例”的模块，Angus 可以怎么样的模块太重，应集成到下方制作人判断力。
- **错误模式**：先讲 Angus 想象，后讲事实，导致用户看不懂工具本身。
- **防复发规则**：所有重点条目先解释工具 / 论文 / 平台本体，再给 Angus 制作人判断。Angus 判断不能代替工具说明。
- **交付前检查**：每条重点中，`它实际能做什么` 和 `典型例子` 必须出现在 `制作人判断` 之前。
- **适用范围**：AI 日报、次报、图文页、周报评论。
- **Eval 可能性**：high。
- **状态**：active。

### AIR-CASE-005. 重复昨天内容冒充今日日报

- **触发来源**：用户指出“这不就是昨天的内容吗，为什么今天的日报和昨天一样”。
- **错误模式**：没有正确维护上次报告状态，导致旧条目被重新包装为今日内容。
- **防复发规则**：报告必须有覆盖窗口和 `上次报告状态`。上次重点条目默认禁止重复，除非出现新版本、官方进展、可复现代码、安全事件或 Angus 跟进行动。
- **交付前检查**：发次报前先读 `ai-radar-memory.md` 的 `当前报告状态`。若复用旧条目，必须显式写“追踪进展，不是新条目”，并说明新进展是什么。
- **适用范围**：日报、次报、周报。
- **Eval 可能性**：medium。
- **状态**：active。

### AIR-CASE-006. 自动化触发失败后不应继续假设可用

- **触发来源**：Codex heartbeat / cron 测试多次未触发。
- **用户反馈**：多次询问“触发测试成功了吗 / 似乎没成功 / 还没生效”，最终改为手动“发次报”。
- **错误模式**：把配置存在当成调度可用，未用真实触发结果证明自动化可用。
- **防复发规则**：自动化只有在真实 heartbeat / sentinel / 日志 / 后台线程证据出现后才能称为通过。否则只能标为“配置存在但调度未验证或失败”。
- **交付前检查**：不要承诺 Codex 会自动推送日报。当前正式模式是手动触发：用户说“发次报”，覆盖上次报告之后到当前时间。
- **适用范围**：日报自动化、Codex automation、提醒 / 推送承诺。
- **Eval 可能性**：low。
- **状态**：active。

### AIR-CASE-007. 平台内创作者内容不得用通用网页搜索结果替代覆盖判断

- **触发来源**：2026-07-02 “AI 从 0 到接近 Steam 上线完成度的游戏落地经验”中文来源补查。
- **用户反馈**：用户指出自己在 B站和小红书看到大量 AI 做独立游戏的视频、帖子，质疑为什么检索不到。
- **错误模式**：使用通用网页搜索查找 B站 / 小红书这类平台内短视频和帖子，把搜索引擎召回不足误读成“暂未找到可用内容”。同时把“未找到完整 Steam 级生产链实录”和“平台上没有大量实践内容”混在一句话里，证据口径不够清楚。
- **防复发规则**：涉及 B站、小红书、抖音、知乎、微博、Discord、论坛、itch devlog 等平台内创作者实践时，必须区分“通用网页搜索结果”“平台内搜索结果”“用户提供的一手链接”和“已完整看完并可归类的证据”。平台内内容没有被通用搜索召回时，只能写“通用搜索未覆盖，需平台内补查”，不能写成“没有”或“暂未找到”。
- **交付前检查**：若报告结论包含“未找到中文开发者实录 / 未找到 B站或小红书案例”，必须同时说明检索入口是否包含平台内搜索；若没有平台内搜索或用户链接验证，结论必须降级为“网页检索阶段未覆盖到”，并列出下一步平台内补查关键词和证据分级口径。
- **适用范围**：AI 日报、次报、周报、游戏开发者实践调研、AI 工具生态筛选、中文媒体 / 自媒体 / 短视频平台补查。
- **Eval 可能性**：medium。可检查报告中“未找到 / 很少 / 没有案例”前是否附带“检索入口与覆盖范围”说明。
- **状态**：active。

## Candidate Eval Checklist

发日报 / 次报前，人工过一遍：

- [ ] 每条重点都有“人话标题 + 正式名称”。
- [ ] 每条重点都有“新在哪里”。
- [ ] 每条重点先解释事实，再写 Angus 制作人判断。
- [ ] benchmark / eval / dataset 没有被写成生产工具。
- [ ] 视频生成、视频编辑、局部编辑、图像生成、平台、模型没有互相误命名。
- [ ] “雷达”只用于报告栏目名。
- [ ] 图文页没有因为图形化而删掉关键信息。
- [ ] 上次报告重点没有无新进展重复出现。
- [ ] 自动化能力没有在无真实触发证据时被称为成功。
- [ ] 涉及 B站 / 小红书 / 抖音 / 知乎 / 论坛等平台内创作者内容时，没有把通用网页搜索失败写成平台内容不存在；若未做平台内搜索，必须降级说明覆盖不足。
