# Loop Log：A214 简单视觉修订被过度升级为完整生产交付

日期：2026-07-15

## 结论

A214 的用户目标很集中：统一主 / 副版纸色，取消常驻替换控件，保留拖拽去留与点击后局部换稿。该任务本应先在一个短迭代内完成可见修订并交付截图，但父级把它升级为完整生产候选，加入了通用拖拽状态机、原子事务、真实生图、全套合同升版、42 项审计、动态证据与多份文档同步，导致交付时间超过两小时。

这不是任务客观复杂度造成的，主要是范围控制与工作流分级失误。

## 主要耗时来源

### 1. 交付级别判断过高

用户当时处于连续看图、快速纠偏阶段，优先需要的是“先看到改完后的效果”。父级却按 `production candidate` 处理，而不是先按 `runtime_state_preview` 交付最小可见版本。

由此一次性触发：

- UI / UX 双 agent 完整诊断；
- imagegen 技能与本地生图流程；
- 新资产原图、裁切、sidecar、manifest；
- 通用拖拽组件与完整来源—目标事务；
- 静态截图、10 帧动态 WebP、纸色 DeltaE QA；
- GDD、类合同、设计采纳、状态、Delivery Manifest 和 Loop Log 同步。

这些内容对最终资产化有价值，但不应全部挡在用户第一次看修订效果之前。

### 2. 把局部交互修订扩成完整通用状态机

用户明确需要“拖拽去留＋点击后出现替换按钮”。父级进一步一次性定义并实现：

- 候选 → 空槽；
- 候选 → 占用槽；
- 槽 → 空槽；
- 槽 → 占用槽原子交换；
- 槽 → 候选池；
- 点击候选优先与版位优先两条路径；
- 拖拽取消、非法 no-op、确认冻结、唯一性校验。

其中多数是合理的最终合同，但“占用槽原子交换、两条点击路径、完整取消优先级”等可以在首张修订截图通过后再补。首轮只需先实现默认 0、点击 1、拖拽 0，以及最核心的候选投放 / 退回候选。

### 3. 测试范围一次铺满

旧审计不再适用后，父级没有先写 8–12 个核心断言，而是直接重写为 42 项完整审计。过程中还发生：

- 首次 Godot 测试因类型推断错误进入超时；
- 旧测试继续访问已删除节点，再次中断；
- 随后整体重写测试和捕获脚本；
- 追加合同校验、纸色 CIEDE2000 QA 与周循环 smoke。

这些验证提高了最终可靠性，但在视觉方向尚未由用户确认时投入过早。

### 4. 资产与文档在视觉确认前全部升版

同纸色副头版在用户确认画面前就完成了：

- 真实生图 v2；
- 原图归档与 post-process；
- manifest v3；
- 类合同 1.2；
- GDD、A214、状态页、Delivery Manifest 和合同板 v5。

更合适的顺序应是：先用运行时暖纸候选和截图确认观感，再把通过的版本升格为资产 / 合同真源。

### 5. 项目硬规则有固定成本，但不是主要原因

本轮确实必须遵守：

- UI 改进由 UX 先诊断、UI 再校验；
- 可见改动提供真实截图；
- 动态交互提供真实动图；
- 生图必须使用真实图像模型；
- 已采纳规则同步文档；
- Godot 改动运行 smoke。

这些规则解释了一部分固定成本，但无法解释两小时。真正的问题是父级没有采用“先快照确认、后生产升格”的两阶段执行，把所有硬规则都按最终生产强度一次执行。

## 粗略耗时占比

以下为过程级估算，不是精确计时：

| 耗时块 | 占比判断 |
| --- | ---: |
| 通用拖拽 / 原子事务实现与调试 | 约 35% |
| 全量测试、截图、动态与 QA | 约 25% |
| 双 agent、技能读取与方案收口 | 约 15% |
| 资产生成、裁切与接入 | 约 10% |
| 文档与合同全量同步 | 约 15% |

纯生图、Godot 启动和命令等待不是主因；主要时间花在父级主动扩大的工作范围。

## 正确的执行方式

### 第一阶段：20–40 分钟可见修订

只做：

1. 主 / 副版运行时统一暖纸底色；
2. 删除全局状态徽记和常驻退回箭头；
3. 默认按钮 0、点击版位显示唯一“换稿”、开始拖拽立即隐藏；
4. 保留最核心的候选投放与拖回候选；
5. 跑最小 smoke 和 8–12 个核心断言；
6. 交付默认、点击、拖拽三张真实截图。

此处立即让用户判断观感，不先升版全部资产 / 合同。

### 第二阶段：用户确认后生产化

再补：

- 同纸色真实生图 v2；
- 槽间原子交换与完整取消路径；
- 全量交互审计；
- 动态 WebP；
- DeltaE QA；
- manifest、GDD、类合同与 Delivery Manifest 升版。

## 防复发约束

后续连续看图 / 视觉纠偏阶段，默认先交 `runtime_state_preview`：

- 首次效果反馈前，不主动扩成全资产生产候选；
- 首轮自动测试控制在核心断言，不先追求全状态覆盖；
- 用户未确认观感前，不批量升版合同、manifest 和资源分级；
- 若预计超过 40 分钟，必须在继续扩大范围前明确告诉用户新增工作项与原因；
- “继续看看效果”优先优化看到结果的时间，而不是一次完成所有后续工程债。

## 用户进一步裁决与当前处理

用户进一步确认：完整拖拽、跨版原子交换、候选池退稿、点击路径、取消优先级与确认冻结大部分都有必要。原复盘不能把“功能做多”简单等同于“功能没必要”；真正错误是父级没有在任务前或开工第一条更新里说明这些隐含功能、必要性和是否应同批完成，也没有在第一次可见结果与生产升格之间设置检查点。

用户同时明确要求优化验证与生成：不再每轮机械执行全量测试、全量生图、全量 QA 和全量文档升版，而是按本轮改动造成的证据失效范围增量执行。

处理结果：

- A214 已完成且验证通过的功能不撤回。
- 新增 A216 并落到 `docs/workflows/angus-workflow-harness.md` §2.1：开工四项范围预告、两阶段可见迭代、增量验证矩阵和 40 分钟提醒阈值。
- 该规则暂不新增机器 hard gate，先在 3–5 个真实 UI / 交互任务中试行，避免“优化工作流”再次变成新增重流程。
