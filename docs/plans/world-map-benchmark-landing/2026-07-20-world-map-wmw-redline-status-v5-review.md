# WMW 地区档案“红线升温”状态章 v5 复核

## 结论

当前“红线升温”不独占回答一个玩家问题，已退出 warning 默认态。用户于 2026-07-20 采纳 B：撤下可见章，让左下日程器独占承载剩余天数，`限时 1` 回答“有没有 / 有几条”，具体任务行 `限时至第 4 天` 回答“哪一条 / 何时截止”。

A 只作为条件候选：若未来世界地图需要在不展开任务时支持跨地区紧迫度比较，且 runtime 建立与任务行同源的 `earliest_deadline_day` 聚合，状态章才可改为“最早截止 / 第4天”。当前不得硬编码，也不得复用 `remaining_days`。

两案均删除正文里的错误句“红线稿需在 7 天内处理。”。该句来自周剩余行动天数，不是任务截止；任务内容真源的 `deadline_day` 为 4。

## 职责复核

| 位置 | 应回答的问题 | 当前信息 | 是否重复 |
| --- | --- | --- | --- |
| 左侧地区卡 | 哪个地区值得关注 / 当前选中谁 | 地区名与状态 | 不与截止明细抢职责 |
| 右栏任务情报摘要 | 本区有没有限时任务、有几条 | `限时 1` | 地区级存在性主承载 |

| 顶部状态章 | 当前仅表示“有一条限时” | `红线升温` | 重复且最模糊 |

状态章只有改为真实的地区级“最早截止”时，才新增“本区最早什么时候有任务截止”这一独立问题。

## 代码与数据依据

- `_build_region_status_primary()`：只要 `deadline_count > 0` 就返回“红线升温”。
- `_build_region_warning_text()`：使用 `run_state.remaining_days` 生成“红线稿需在 N 天内处理”。
- `_build_region_card_status_line()`：同样把 `remaining_days` 拼到红线状态。
- `temp_ufo.deadline_day = 4`：具体任务的绝对周内截止日。
- 当前 payload 没有 `earliest_deadline_day`；因此周剩余预算与任务截止不能混作一个口径。

## 双 agent 复核正文

### UX 老哥

UX 老哥判定当前章是第三次重复“本区存在限时任务”，同时是三处里最模糊、视觉位置最高的一处。P0 是“7 天内处理”与“第 4 天截止”的时间锚点冲突；P1 是高权重空信息和周天数冒充截止天数；P2 是“红线升温 / 红线稿 / 限时”术语碎裂。

其明确推荐为 B：先删除 warning 态的可见章，同时撤下错误 7 天句。B 不等于删除 locked / chain 状态能力，也不等于从 compact A5.1 合同退役 `status_stamp`。A 只有在 `visible active deadline nodes → earliest_deadline_day = min(deadline_day)` 的同源数据流成立后才有独立用途。

动态风险包括：切换地区时旧章是否残留一帧、推进日后聚合与任务可见性是否同帧刷新、展开态是否从两次重复放大成三次重复。以上需要进入 runtime 阶段后验证，本轮不宣称完成。

### UI Designer

UI Designer 将 UX 结论转成两个精确局部规格。A 保留 87×87 状态框，只用“最早截止 / 第4天”两层字重，不新增图标或装饰；B 选择扩宽 warning 标题框至 333px，不保留 93px 无职责空位。两案共同删除错误时间句并保持正文外框、任务区与 CTA 坐标不变。

UI Designer 同样推荐 B；A 在同源字段成立前只能是 `CONDITIONAL`。其容量约束为：A 标签固定四字，日期固定 `第1天`—`第7天`；A 标题最多 8 个全角字，B 标题最多 11 个；正文主说明建议不超过 17 字，辅助说明不超过 20 字。若差异审计触及左栏、中央、照片、任务区或 CTA，直接判范围漂移。

- B 相对 v4 仅允许变化 `[1519,72,337,92]` 与 `[1431,456,414,135]`；范围外变化像素为 0。

## 用户裁决

用户选择 B，并明确补充理由：“剩余天数实际上在左下角已经标注出来了”。该反馈确认左下日程器是全局时间的唯一主承载位，右栏无需重复剩余天数或泛化升温状态。

本裁决已登记为 A233。A 图继续作为未来 `earliest_deadline_day` 同源聚合成立后的条件参考，不进入当前默认态。
