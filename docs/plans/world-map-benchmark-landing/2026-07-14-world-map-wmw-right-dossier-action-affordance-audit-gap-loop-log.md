# Loop Log：右 dossier 动作作用域与视觉控件数量审计缺口

> **结论**：A2 虽通过字段来源、必要性与单一 `hit_rect` 校验，却仍把一个命令画成三块完整控件，并把页内披露与跨层导航画成同级入口；组件审计缺少“动作后果 → 控件语法”的整体检查。
> **影响**：604 的数据语义证据继续有效，但 A2 两份 action child 的视觉结论降级为 `visual_fail_action_scope_and_affordance`，不得冻结或扩多状态。
> **下一步**：新增 `action_scope_and_affordance_audit` 口径；下一候选先证明一行一个视觉控件、secondary / primary 后果层级清楚，再交用户看美术。

## 这次错在哪里

A205 后的审计逐项回答了“字段从哪里来、是否必要”，却没有回答“点击后发生什么、是否切页、是否改状态、是否耗时、应该长成什么控件”。因此左文档圆标、中米白板、右箭头圆标虽然都能解释自己的局部语义，组合起来却像三个可点对象；两行又共用完整边框、端部圆槽与右箭头，使青色预览和橄榄绿进入被读成两个并列的前往动作。

这不是单纯配色不足。A196 的同宽共轴只建立外部秩序；执行时却误把“同宽 + 不同颜色”当成主次层级成立，忽略了形态、方向符号、纸厚、阴影和 pressed 强度仍然同构。

## 为什么已有 Gate 没拦住

1. `visible_component_audit` 检查了组件是否有数据源与页面归属，没有记录 `effect_scope / navigation_change / state_change / time_cost`。
2. `hit_rect=[0,0,w,h]` 只证明程序点击范围是整行，不能证明美术没有画出三个独立按钮。
3. `state_color_note` 只验证青蓝 / 橄榄绿语义互斥，没有比较两条动作的相对纸厚、边界数量、方向符号和反馈强度。
4. 双 agent 已把三段式与主次过近列为 P1，父级仍把它们留给用户裁决，没有先把每一部分的真实功能讲清并给出结构性建议；这违背了 A205“主动过一遍基础组件”的意图执行。
5. `查看任务情报 · 4项` 与 popover 只展示 2–3 条的范围差异未进入审计，数量正确但动作承诺仍可能错误。

## 修正律

下一版候选交付前，每个可交互组件必须登记：

| 字段 | 含义 |
| --- | --- |
| `effect_scope` | 当前组件内展开、当前页面状态变化、跨层导航或不可逆提交 |
| `navigation_change` | 是否切页 / 切上下文，目标层级是什么 |
| `state_change` | 是否改变选择、资源、任务或世界状态 |
| `time_cost` | 是否直接消耗天数；不能用“进入”暗示派遣耗时 |
| `runtime_hit_rect_count` | 实际独立热区数量 |
| `visual_control_count` | 玩家从完整边框、承托、阴影与反馈中读到的控件数量 |
| `direction_symbol` | 展开、返回、前进、确认必须与真实后果一致 |
| `relative_priority` | 与同组其它动作的主 / 次关系及视觉证据 |
| `count_scope` | 数字表示总数、已显示数还是剩余数 |

硬判据：`visual_control_count` 必须等于 `runtime_hit_rect_count`；不同 `effect_scope` 的相邻动作不得共用同模板、同方向符号和近似视觉重量。程序热区通过不能替代 100% 局部截图目检。
