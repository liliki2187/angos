### 暴露程序绘制感的主要可见区域

- RegionCard：外框、分隔线、Eye、状态章、选中脊线、右侧信息组织均由 Pillow 绘制；
- Schedule：内框、减号盒、状态块、分隔线和绝大部分版式均由 Pillow 绘制；
- Evidence Map：标签板、连线、选中圆弧、锁定组合徽记、照片白框和条件便签排版由 Pillow 绘制；
- Dossier：页面框线、状态章、图片框、Disclosure、印章框和 CTA 底板由 Pillow 绘制；
- 综合色彩主要依靠程序矩形、描边和文字色，而不是生图组件自身的色块、轮廓、套印和接触关系。

因此，虽然底层纸纹和照片来自真实图像，玩家第一眼接触的“组件身份层”仍是程序 UI，最终读感自然接近开发期面板。

## 根因

1. 前一轮为解决 ImageGen 无法稳定保持三张卡同壳，正确停止了整屏 prompt 修卡；但随后把“精确合成只负责合同与回填”扩大为“精确合成可以绘制最终组件外观”。
2. 将真实纸纹铺在程序矩形上误认为已完成美术资产化，忽略标杆质感主要来自定制轮廓、大块面、套印、裁纸边、非对称图文关系和物件接触，而不是纸纹本身。
3. UI / UX 审查聚焦状态语义、同类规格和操作闭环；父级没有独立执行“visible surface source audit”，导致功能安全通过被误报为视觉目标通过。
4. 前一轮回复把当前成熟度描述成阶段 7 `filled_state_text_mock`，未区分“有真实内容的合同回填”与“主要可见组件已由真实美术资产承担”的阶段 7 硬门槛。

## 立即纠偏

- 撤销 `09 / 10 / 11` 的视觉目标、资产化候选与阶段 7 通过身份；保留几何 / 状态 QA 价值。
- 不再用 Pillow 给程序壳增加噪点、阴影、折线或假低多边形面；这会继续加深程序重绘，而不是提高质感。
- 下一轮先交真实 ImageGen 组件母板或真实 ImageGen 整屏改造预览，明确标注图像来源；用户确认组件语言后才反向生成无字母件。
- 任何重新升格的视觉目标必须附 `visible_surface_source_audit`：逐块列明真实生图、美术裁片、动态文字、程序 QA 四种来源。若程序绘制最终可见壳体、按钮底板、状态章、标签板或主图标，直接阻断。

## 复发保护

1. **视觉来源审计先于视觉 Gate**：页面进入用户视觉确认前，按主组件统计“玩家可见身份层”的来源。纸纹覆盖程序矩形不算真实美术组件。
2. **程序允许清单收窄**：程序只负责裁切、等比缩放、alpha / chroma key、mask、九宫格、动态文字、坐标合成和检测；不得绘制最终纸壳、边框、章、图标、按钮底板或标签板。
3. **宣称分级**：若真实美术只提供背景、纸纹和照片，而主要组件轮廓仍由程序绘制，产物最高只能标 `contract_composite`，不得标 `filled_state_text_mock` 或 `visual_target`。
4. **分层路线不等于程序美术**：一类一母版要求“真实美术母版＋程序派生状态”，不是“程序绘制母版＋贴一层真实纹理”。
