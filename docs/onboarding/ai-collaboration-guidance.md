# AI 协作指引：如何更精准理解当前用户

> **用途**：给后续接手本仓库的 AI / 新对话提供一份可执行的协作约束与偏差复盘。  
> **对象**：不是给用户看的总结稿，而是给 AI 自己看的工作指引。  
> **维护方式**：每当用户给出新的负反馈、纠偏指令或暴露出新的误判模式，先按 `docs/workflows/angus-workflow-harness.md` §7.1 沉淀去重律查重；已有承载位则更新原条目，确属新模式才补进 §7 对应主题小节，不再按日期在尾部追加补丁段落。  
> **最后更新**：2026-07-08（§7 补丁堆主题化重构，原文归档至 `_obsolete/ai-collaboration-guidance-legacy/`）

---

## 1. 文档定位

这份文档记录的不是“项目功能需求”，而是**当前用户的沟通方式、判断标准、常见雷区，以及 AI 在本项目中最容易犯的偏差**。

目标只有两个：

1. 让后续 AI 在接手时更快抓住用户真正要的东西。  
2. 把已经暴露过的误判模式写成硬规则，避免重复犯错。

如果本文与临时想法冲突，**优先遵守本文**，除非用户在新对话里明确推翻。

涉及 UI、交互、原型呈现、视觉实验页时，还必须同时读取并执行 [`ui-interaction-guidelines.md`](./ui-interaction-guidelines.md)。本文保留“为什么犯错”的复盘，UI 文档提供“具体怎么做”的执行规则。

## 2. 用户的核心偏好画像

### 2.1 用户最看重“玩家是否能明显感知到变化”

用户判断“做出来了没有”，不是看规则是否已经在后台生效，而是看：

- 玩家是否在界面上看得到；
- 玩家是否在操作中感知得到；
- 玩家是否能明确分辨“这次和之前不一样”。

因此：

- **规则存在** 不等于 **玩法成立**；
- **结算文案提到** 不等于 **机制被感知到**；
- **内部状态变化** 不等于 **玩家体验发生变化**。

### 2.2 用户偏好“最小改动验证”，不喜欢顺手改大范围外观或载体

当用户说“完善一下某个玩法”时，默认理解为：

- 优先在**当前熟悉的载体**上验证；
- 优先做**最小行为改动**；
- 不要顺手把 UI、节奏、入口、运行方式一起重做。

尤其是：

- 如果用户原本在看 HTML 原型，**不要擅自切到 Godot 运行时做演示**；
- 如果用户要的是“补骰子玩法”，**不要顺手重做阶段切页、整体布局或产品壳层**。
- 修一个明确视觉问题时，不要用单一目标覆盖其它已确认亮点。例如为了让功能组件正交，不能把低多边形色块、手绘贴纸感和标杆色彩一起抹平；为了逃离写实探案，也不能把卡通、黑色幽默和怪谈符号同时拉满，导致原标杆的克制成人周刊气质被怪谈漫画 / 贴纸包取代。每次纠偏都要回看“本轮修了什么、旧优点是否还在、纠偏维度是否从不足跳到过量”。同时要警惕把用户说的“色块 / 明度块面”误翻译成“褶皱 / 折痕 / paper folds / tears”，这会把平面图形语言带偏成纸张皱纹或撕裂痕。几何 QA 也必须贴住真实生成边缘；手动画一个理想水平框不等于图像里的功能组件真的正交。
- 资产化 UI 的文字贴合问题，不能只用 safe-zone、inner box、bbox pass 或 overlay pass 回答。用户指出“文字不在框体内 / 偏上 / 偏下 / 落在深色条外”时，AI 必须先回到原图识别真实颜色模块：深色标题条、浅色标签纸、按钮内板、票据色块、章槽、图标禁入区。若自画框和真实色块不重合，所有数值 pass 都是 false pass。正确顺序是先修 `visible_color_module_rect -> carrier_rect -> inner_rect -> runtime glyph_bbox`，再谈字号、字重、行高和文本内容；不要用“缩小字 / 居中到自画框 / 加绿色框 / 手工 y 偏移”掩盖模块理解错误。若合同槽本身过小，必须显式升版并让可见 carrier 与槽同步扩展；字体代理通过后仍要看目标引擎真实字体。

### 2.3 用户希望“首个可玩区域就能体验到核心机制”

用户非常重视“上手即得”。

如果某套新机制需要：

- 解锁后续区域；
- 玩很久才能遇到；
- 或藏在不容易触发的节点里，

用户通常会认为“实际上没做出来”。

因此：

- 优先把新机制集中到**第一个可玩区域**；
- 优先把 showcase 节点放到**最早可触达的位置**；
- 不要把主要机制分散在后续地图里等玩家慢慢打。

### 2.4 用户要“可思考、可控制”的操作权

用户对“自动替玩家推进”的系统反应会比较强，尤其是：

- 自动重投；
- 自动跳过思考阶段；
- 很短的时间窗口；
- 玩家还没理解就已经进入下一段。

因此：

- 玩家需要决策时，必须有**明确的停顿**；
- 最好有**明确按钮**而不是自动继续；
- 锁定 / 重投 / 确认这类动作，优先给玩家手控权。

### 2.5 用户对界面偏差很敏感

如果用户要求的是玩法补强，而结果把界面视觉体验改得面目全非，用户会认为：

- 做偏了；
- 没有抓住重点；
- 甚至怀疑“你是不是在做另一件事”。

因此：

- 改玩法时默认**不改大 UI 风格**；
- 若必须改展示层，优先局部嵌入，不重做整体布局；
- 如果要换载体或大改交互壳层，必须先明确征得用户同意。
- 当用户已经给出或反复指向标杆截图时，AI 不能只抽象出“深色、几何、高级、清爽”等关键词；必须回到截图逐项比对主物件、灯光、材质、物件密度、动作入口和情绪。若结果变成更简洁的功能面板，仍然属于界面偏差。

## 3. 本次对话里用户提出过的关键问题与指令

以下不是完整逐字转录，而是对后续最重要的需求轨迹摘要。

### 3.1 关于骰子玩法本身

用户反复要求：

- 先发散，再收束；
- 把可操作维度和机制按层级梳理；
- 新机制不能只停留在“系统算了”，必须让玩家明显体会到；
- 没有直接对抗时，也要做出“像被对抗”的感觉；
- 关卡类型（考古 / 科学调查 / 异常接触等）应有不同机制偏好。

### 3.2 关于当前验证载体

用户一开始接受把玩法落进当前 demo，但在实际看到效果后明确表达：

- 不希望因为做骰子玩法，导致界面观感和熟悉的网页版本差太远；
- 重点是**保留熟悉体验的前提下补玩法**；
- 如果 Godot 包体 UI 太开发态，应优先回到 HTML 原型继续做展示。

### 3.3 关于“玩家能感受到”这件事

用户提出的关键判断标准包括：

- 干预、污染等不能只存在于最后结算文字里；
- 每个小机制应该有明显触发时机；
- 机制之间要有间隔，不要一闪而过；
- 单颗骰子要足够清晰，骰子太多时会让所有机制失效；
- 应有手动锁定某个骰子的操作；
- 锁定后要有明确的“开始重投”按钮，不能自动替玩家继续。

### 3.4 关于内容分布

用户明确要求：

- 把主要新机制优先放在北美禁区；
- 因为那是第一个能玩到的区域；
- 不要把 showcase 主要放在后续区域。

### 3.5 关于后续协作

用户希望形成一份长期文档，记录：

- 本次对话里所有关键问题和指令；
- AI 为什么没做好、没考虑到；
- 用户思考方式和偏好；
- 后续新反馈继续往里追加；
- 并且要让别的对话或 AI 接手时也能受到约束。

## 4. 本次对话里 AI 已暴露的主要偏差

### 偏差 1：把“补玩法”误做成“换载体验证”

#### 表现

用户原本更熟悉 HTML 原型，但 AI 为了“让用户能玩到”，优先把新玩法塞进了 Godot `weekly_run`。

#### 为什么这是问题

这改变了用户熟悉的体验壳层。即使规则本身没错，用户看到的也会先是：

- 界面不一样；
- 节奏不一样；
- 操作感觉不一样；

从而掩盖掉用户本来真正想看的“骰子玩法变化”。

#### 后续硬规则

- 如果用户最初讨论的是 HTML 原型或网页体验，默认先在 **HTML** 验证。  
- 不得以“更容易运行”为理由，擅自把玩法迁到另一种载体演示。  
- 如果必须换载体，必须先明确征得用户同意。

### 偏差 2：把“规则被算进去了”误当成“玩家已经体会到了”

#### 表现

AI 先把：

- 类型包、
- 副轴、
- 干预、
- 余波、
- 链式节点

都写进了逻辑层，但玩家看到时仍然觉得“还是原来的简单作废骰”。

#### 为什么这是问题

因为这些变化主要在：

- 计算层；
- 结果文案；
- 状态写回；

而不是在玩家视野里的阶段演出中。

#### 后续硬规则

- 任何新机制如果只在结算文字或状态里可见，默认视为**未做完**。  
- 规则层完成后，必须立刻追问：  
  - 玩家在哪个时刻第一次能感知到它？  
  - 玩家会误以为它还是老机制吗？  
  - 没看说明能不能区分出来？  

### 偏差 3：低估了“骰子数量过多”对可读性的破坏

#### 表现

早期实现仍然使用大量骰子，导致：

- 单颗骰子存在感过低；
- 被干预、被污染、被保住的具体骰子看不清；
- 锁定决策没有重量。

#### 为什么这是问题

当骰子过多时：

- 任何单颗机制都会被淹没；
- 反馈再多也只是噪声；
- 玩家不会觉得自己在“做选择”，只会觉得系统在“播结果”。

#### 后续硬规则

- 只要玩法想强调单颗骰子、锁定、干预或污染，优先先压缩总骰数。  
- 在没有强理由前，把单次判定总骰数控制在 **10 个以内**。  
- 若强调“角色骰”，优先按角色出骰，而不是按属性点数直接堆骰。

### 偏差 4：过早自动推进，剥夺了用户思考窗口

#### 表现

锁定阶段一开始只有 2 秒自动重投。

#### 为什么这是问题

用户明确重视：

- 可思考；
- 可慢慢看；
- 可手动确认；

自动推进会直接破坏这类体验。

#### 后续硬规则

- 玩家需要决策时，默认不要自动继续。  
- 锁定 / 重投 / 确认类交互，优先提供明确按钮。  
- 如果有时间限制，必须先得到用户明确认可。

### 偏差 5：没有足够早地把“核心机制集中到首个区域”当作硬要求

#### 表现

早期把一些 showcase 放到了东亚或更后面区域。

#### 为什么这是问题

用户想要的是：

- 马上打开就能试；
- 第一张图就能覆盖主要机制；

否则就会被判断为“实际上玩不到”。

#### 后续硬规则

- 新机制的第一轮验证，默认优先集中到**首个可玩区域**。  
- 若需要 showcase 节点，也优先放在首区。  
- 后续区域可以留第二版或补充版机制，但不能承载第一轮验证的主要内容。

### 偏差 6：补玩法时顺手改了太多展示层

#### 表现

在 Godot 阶段，AI 一度同时改了：

- 规则层；
- 任务面板文案；
- 阶段显隐；
- 禁用态样式；
- 整体流程切页表现。

#### 为什么这是问题

这会让用户无法分辨：

- 是玩法变了；
- 还是整个界面被重做了。

#### 后续硬规则

- 如果用户要求是“补玩法”，默认展示层改动只做**局部嵌入式增强**。  
- 不主动做全局 UI 重组、阶段切页或视觉风格迁移。  
- 一旦发现实现开始往“另一个任务”扩张，必须停下来收束。

### 偏差 7：把控件盒子通过误当成视觉安全区通过

#### 表现

世界地图 v5 资产化 UI 中，AI 多次认为“布局测试通过、控件没有超出父容器、整屏观感改善”就可以交付，但用户在 100% 局部截图中指出 CTA 出框 / 拉伸、票据文字压右侧装饰、左侧 INDEX 文字贴夹子和纸边、底部 ticker 文字压色块、按钮文字贴近下沿等明显问题。

#### 为什么这是问题

拟物 / 资产化 UI 的真实可写区域不等于 Godot Control / HTML DOM 的矩形。PNG 内部的书签、折角、螺丝、箭头、纸边、装订、色条主体、强半调和装饰凸起都是视觉禁入区。控件盒子没越界，只能证明程序布局没炸；文字压到资产禁入区时，玩家看到的仍是“硬塞进贴图”的坏界面。

这种错误会被整屏远景掩盖。越是整体风格进步明显，AI 越容易忽略局部文字贴边、基线偏低、压装饰和视觉归属错误。

#### 后续硬规则

- 资产化 UI 落地前，必须先分析视觉可使用区域：标出 `content_rects`、`no_text_rects`、九宫格拉伸边界和最长文案约束。
- 截图验收不能只交整屏图；必须裁切关键局部，至少包含 CTA、票据、正文框、底部 ticker、左侧索引顶部 / 底部。
- 自动测试不能只测控件在父容器内；应尽量加入安全区断言，检查文字槽与禁入区不相交。
- UI Designer 出稿时要给拟物组件附文字安全区表；UX 老哥评审时要明确检查“控件盒通过但视觉安全区失败”的情况；美术指导审 UI 资产时要判断资产是否留出足够干净的动态文字区。
- 如果用户指出“文字位置不对 / 贴边 / 压装饰 / 出框”，不要只调单个坐标。先回到资产可写区模型，判断是不是安全区定义缺失。

## 5. 当前用户的思考方式与决策风格

### 5.1 用户习惯先发散，再收束

当用户谈新系统时，通常会先：

- 大量发散机制方向；
- 看可能性空间；
- 再要求压成分层、路线、范围。

因此 AI 在前半段可以发散，但一旦用户开始要求：

- 总结、
- 梳理、
- 正式文档、
- 组合建议，

就必须从脑暴切到收束模式。

### 5.2 用户偏好“先做出可玩的最小体验，再慢慢加层”

用户不反对复杂机制，但很明确地希望：

- 先有一个可玩的第一层；
- 再看是否需要更复杂的层；
- 不要一上来把所有层都做进同一套演示里。

### 5.3 用户非常看重“感知到”

用户并不满足于：

- 文档写明了；
- 代码里算到了；
- 结果页写出来了。

用户真正要的是：

- 玩的时候能看出来；
- 能操作到；
- 能记住发生了什么；
- 能感觉到“这次和以前不同”。

### 5.4 用户会持续纠偏，并希望 AI 能把纠偏转成永久规则

用户不是只想要一次性修正，而是希望 AI：

- 把反馈抽象成规律；
- 写进文档；
- 让以后别的 AI 也遵守；
- 避免每次都重新教一遍。

因此，收到用户强反馈后，AI 应主动做：

1. 纠正当前实现；  
2. 把问题上升为规则；  
3. 把复盘写成未来可执行的判断流程，而不是只写“这次错了”；
4. 更新长期协作文档。

复盘和总结必须能被未来 AI 迁移使用。写入文档时不要只记录具体对象，例如“骰子文字歪了”；应按以下结构抽象：

- **用户看到的症状**：截图第一眼被读成什么、哪里违背用户目标；
- **AI 错误判断口径**：是把实现意图当感知结果、把局部进步当整体通过、只看新问题不查旧优点，还是用远景替代局部检查；
- **可观察门槛**：下次肉眼要检查哪些具体信号，哪些信号一出现就判定失败；
- **可迁移规则**：同类问题在按钮、地图点、模型、贴图、动效、信息层级中对应什么检查；
- **交付约束**：最终回复只能陈述截图已经支持的结论，不能把“比上一轮好”说成“已通过”。

典型反例：不要写“3D 骰子以后要做得更好”。正确写法是“声称 3D / 实体 / 贴面时，必须分别检查闭合体积、不透明面、内容是否属于材质、遮挡噪音和旧版优点回归；任何一项截图未通过，都不能用技术实现解释为通过”。

## 6. 后续协作硬规则（必须执行）

以下规则是从本次对话里提炼出来的**长期约束**。

### 6.1 关于载体选择

- 默认优先在用户当前讨论和熟悉的载体上验证。  
- 不擅自从 HTML 切到 Godot，或从 Godot 切到 HTML。  
- 如果要换载体，先明确说明原因并征得用户同意。

### 6.2 关于展示与感知

- 新机制必须明确回答：  
  - 玩家在哪个时刻第一次感知到它？  
  - 玩家在哪个界面理解到它？  
  - 它是否只存在于结算文案？  
- 若答案是“只在结算文案里”，则视为未完成。

### 6.3 关于范围控制

- “补玩法”不等于“顺手重做 UI”。  
- 默认只做与用户明确目标直接相关的最小改动。  
- 一旦实现开始扩张到：
  - 全局 UI、
  - 阶段切页、
  - 入口重构、
  - 运行时迁移，
  就必须停下来重新确认。

### 6.4 关于首区试玩

- 第一轮机制验证优先集中在**首个可玩区域**。  
- showcase 节点优先也放在首区。  
- 如果用户还没玩到，就不要把关键体验放到后面区域。

### 6.5 关于玩家决策权

- 只要玩家有“锁定 / 重投 / 确认”决策，默认给明确按钮。  
- 不自动 2 秒倒计时，不替玩家自动推进。  
- 如果用户没明确要求快节奏，就优先让玩家“慢慢看、慢慢选”。

### 6.6 关于骰子数量

- 需要强调单颗骰子的玩法时，先压缩总骰数。  
- 默认目标：单次判定总骰数不超过 10。  
- 角色基础骰优先于属性点直接堆骰。

### 6.7 关于反馈循环

- 用户一旦指出“体会不到”“还是原来的”“太快了”“界面变了”，必须优先判断这是：
  - 感知层问题，
  - 节奏问题，
  - 载体问题，
  - 还是范围失控问题。  
- 不要立刻再加新规则，先处理感知与节奏。

### 7.1 范围控制与需求理解

- **元素语义不明确只改表达（2026-05-12）**：用户指出某 UI 元素"语义不明确"时，第一轮只改该元素的文案 / 图标 / tooltip；先识别用户想保留的优点，除非明确要求，不得重排已认可结构。
- **局部认可只保留局部（2026-05-21）**：用户只认可某个局部控件（如候选排序标签）时，只保留该局部，撤回其它未确认的整页结构。
- **修标杆组件不得扩成整屏重生（2026-07-01）**：锁定不变项，先组件校正板后整屏回填；详见 `ui-interaction-guidelines.md` §13.5。
- **小对象落地不擅自改整页布局（2026-05-25）**：用户只要求应用模型 / 动效 / 局部视觉时，默认只替换对象本身；若真实资源需要更大画布或不同信息顺序，先提问确认，验收要包含"原布局是否仍成立"。
- **采纳记录转方案先复述评注（2026-04-28）**：先按条目复述"核心意图 / 限定范围 / 不该做什么 / 玩家应感知什么"，确认理解后再写落地方案。
- **跨系统术语先锚定对象（2026-05-22）**："人数 / 槽位 / 卡片 / 布局"这类词先确认属于当前轮最新讨论对象（如骰子判定 vs 派遣）；不确定先用一句话澄清，不凭近邻记忆落错页面。
- **组件正式接线先锚定整屏身份（2026-07-16）**：不能因为某旧场景已有数据流和容器，就把它当成当前视觉路线的运行宿主。接线前必须列目标 scene / page、真源截图、正向锚点与禁止锚点；首张整屏与真源并排。局部组件、smoke 与 agent 复核都不得跳过该门槛。
- **判定机制先做玩法创意（2026-04-29）**：核心判定保持简单成败或少量大档位；机制创意应大颗粒、可操作、一眼可懂；叙事放关卡主题 / 任务链 / 结果选择，不把骰面写成小叙事。
- **呈现层单独验收（2026-05-07）**：规则和基础功能实现不等于落地完成；入口显眼、操作有可感知差异、反馈发生在决策现场、截图覆盖玩家第一次感知时刻，缺一视为未完成。

### 7.3 UI 信息架构与组件语法

执行细则大多已沉淀到 `ui-interaction-guidelines.md` 对应章节；判断器索引：

- **信息主承载位（2026-05-27）**：每个核心决策事实只能有一个主承载位；二次出现必须承担摘要 / 引用 / 对比 / 解释 / 阻断 / 反馈之一且权重低于主承载位；说不出新增职责的重复必须删除或降级并回收空间。
- **一语义一位置、符号必须有读法（2026-05-12）**：孤立数字、重复感叹号不作为独立信息；需要解释的压力信息（危险 / 黑骰 / 对手骰）放有文字读法的标签区；按钮固定列宽对齐。
- **同类标识固定槽位（2026-05-12）**：同类功能标识不得随任务类型漂移槽位；信息缺省可以留空，已有信息不能换位置。
- **只显示改变决策的信息（2026-05-12）**：默认规则不上卡面（如"失败保留、可反复追踪"）；同一含义只保留一处；含义不明或无玩法后果的标签删除或改成明确规则词。
- **删减后回收空间（2026-05-12）**：删信息必须同步回收行高 / gap / padding / 占位；交付截图确认"内容少了，空间也变紧凑"。
- **去重后不弱化关键数值（2026-05-13）**：去重必须重排视觉主语；关键数值要有唯一且高权重的承载，不得降级为说明句的一部分。
- **固定位置不等于高视觉重量（2026-05-12）**：固定关键信息槽位时同步控制视觉重量；只有强时效信息（倒计时 / 严重危险 / 当前可操作）才允许高权重组件。
- **标识按层级显示（2026-05-13）**：图标 / 标签 / 图例必须绑定本界面真实可见对象与决策用途；把详情层摘要搬到上层界面属跨层借语义，默认删除或移回。执行见 UI 指南 §4.1。
- **状态与类型分槽（2026-05-13 / 05-18）**：`已派遣 / 执行中 / 待结算` 等状态不混入类型标签行，靠近标题 / 主操作 / 被状态化对象；人员占用优先头像表达；执行中对象从主操作候选流下沉到次级只读队列。
- **特殊机制专属槽位（2026-05-18）**：常规 meta（耗时 / 需求 / 对手骰）与例外机制（红色截稿 / 深度链当前环 / 黑骰终局）分槽；已完成深度链旧环退出当前任务列表，只进日志回顾。
- **整卡可点则不放重复按钮（2026-05-18）**：单主动作且整卡已是点击入口时，删除卡内重复小按钮；按钮只留给多动作 / 确认 / 不可逆场景。
- **选择器与详情两套语法（2026-05-18）**：父级选择器用按钮语法（箭头 / hover / 选中态）；从属详情用注释 / 属性表语法（透明背景、缩进、细线、轻量属性行），不是弱版卡片。
- **选择不换位置（2026-05-18）**：候选列表在点击 / 选中 / 取消 / hover 时原位置稳定；选择状态只改高亮与已选区，不参与候选池排序。
- **同组控件一致撤回语义（2026-05-18）**：同组追加资源的可撤回性必须一致或明确分区（购买入口与阵容管理分开）；槽位用掉后保留空位，不拉伸剩余元素。
- **容量上限不自动替换（2026-05-18）**：满员后继续选择必须阻止并提示，保持当前选择不变；替换由玩家显式撤下旧对象完成。
- **可点 / 不可点拉开距离（2026-05-18）**：不能只靠弱色差；不可用项用锁定 / 幽影语法，去主箭头、禁 hover 抬升，并明确展示阻断原因。
- **主操作大、放流程终点（2026-05-14）**：核心 CTA 必须比次级按钮更大更醒目，默认右下角或玩家完成选择后的视线终点；层级返回按钮可低权重但必须有稳定点击面积和一致样式（2026-05-19），修正时扫所有同类返回按钮。
- **时间推进归属工作上下文（2026-05-14 / 05-18）**：上层选择页不放 `下一天`；日程推进 / 结算 / 结束周从任务列表容器独立出来，用明确文案放独立日程区；跨阶段捷径不放低层工作台顶栏。任务级 CTA 与全局推进不得相邻，见 UI 指南 §13.1。
- **只读预览不像可点列表（2026-05-14）**：只负责选择的页面不复用下层任务卡结构 / hover / 交互类名；只读预览默认 2-3 条，自动验收检查预览容器内无按钮与交互类。
- **角标必须有安全区（2026-05-14）**：数字角标 / 进度徽章 / 头像叠层必须有独立槽位或预留安全区；重叠审计覆盖 `9+`、百分比、长状态词、多人头像组等边界文本。
- **同形控件不等于同语义（2026-05-19）**：并列卡片 / 进度条 / 状态块必须能用一句话证明共同回答同一个玩家问题（同对象、同口径、同判断结果），否则拆父子结构；不能按"都是进度条"的视觉形态归类。
- **条件与挑战分开（2026-05-21）**：条件=玩家需满足的准入（文案 `条件：探索2`）；对手骰 / 危险 / 黑骰=关卡挑战压力，用 `挑战：…` 或专门槽位，不进条件标签。
- **角色骰保持骰子语法（2026-05-14）**：展示完整 6 面角色骰时用 dice net 立方体摊开，不退回横向 chip 行；压缩卡片高度不得牺牲已采纳核心视觉语法。
- **判定选择先修最短决策链（2026-05-22）**：第一优先级是"看见可选骰面 → 选择后看见目标变化 → 提交前看见结果"；一键推荐、黑骰表现、投骰动效作为后续独立确认项，不与基础入口混绑。

### 7.4 地图与空间语义

- **地图必须有空间语义（2026-05-09）**：不用抽象圆斑 / 光斑替代地图背景；临时占位也要让玩家看出"这是地图"。
- **深度链入口只显当前环（2026-05-09）**：地图只显示当前可做一环，用叠层 / 折角暗示背后有链；点击后展开，已完成环可见、下一环最多"？"预告；完成后替换为下一环。
- **叠层形变为线性链（2026-05-09）**：展开用同一对象的空间形变（默认规整叠层 → hover 轻量错位 → 点击排成线性链），不另开独立详情面板。
- **展开 / 进入 / 收起分离（2026-05-18）**：展开后当前子项直接可进入，同一点击不兼任"进入"和"收起"；收起交给点击外部 / 关闭；点击未解锁环必须就近反馈原因，全局 toast 不算有效反馈。
- **标签避让是机制不是坐标（2026-05-11 / 05-12）**：多类入口共存时渲染后检查碰撞，高优先级入口（深度链 / 黑骰 / 高危）保位；按"可读安全区"验收——阴影 / 描边 / hover 展开范围都膨胀为保留区，不是只看矩形相交。
- **世界地图风格锚点（2026-06-06 / 06-07 系列）**：不做写实旧地图，也不退回简陋像素或留空黑区；"风格方向正确"和"成熟度足够"必须同时满足；风格稿必须套进真实 16:9 界面骨架再判断可否落地；落地必须做风格等价检查（版式比例、主视觉占比、材质、色彩干净度、信息密度、pin / 按钮形状），只继承局部元素仍算未完成。现行真源见 `design/art-direction/angus-visual-style-guide.md` 与 WMW 支线合同文档。

### 7.5 数值与概率诚实

- **风险预览用真实结算公式（2026-05-13）**：风险 / 成功率 / 达标率类 UI 文案必须调用或等价复刻真实结算公式，不能用潜在覆盖 / 静态面值总和替代；新随机结算至少跑一次代表组合概率审计。风险徽标同时显示实际达标率，多人提升不得被粗档位标签吞掉（2026-05-19 修订）。
- **概率诚实不是难度修复（2026-05-14）**：显示准确不等于值得玩；"总是不成功 / 没乐趣"类反馈必须列代表任务在普通 / 适配 / 带支援下的达标率，适配队伍仍几乎不可能成功时优先修需求 / 公式 / 骰面密度，不是只把风险显示得更准。
- **普通任务 1-2 人可玩（2026-05-14）**：派遣难度按档位分 1 / 2 / 3 人评估；普通任务以 1-2 人可玩为基准，3 人提供稳妥而非最低门槛；高档难度来自时限 / 后果 / 反噬 / 资源占用。
- **低贡献角色不反向升险（2026-05-11）**：整体风险看需求覆盖度与缺口，不看相关骰面占总骰面比例；加入角色不得让风险提示变差，低贡献以"贡献低 / 占人数槽"提示呈现。

### 7.6 实验页与验证路径

- **实验页必须比正式落地快（2026-05-18）**：先定义窄问题、最小输出、停止条件；默认只做局部组件、复用现有样式、最多 2-3 个状态；成本接近直接改本体时立即停止，改为本体最小切片。
- **已有本体不默认假实验页（2026-05-13）**：UI 方向明确且有承载页时直接在本体做最小切片；独立实验页只用于多方案比较、无承载页、必须隔离风险或用户点名。
- **实验页继承可读性保护（2026-05-12）**：复用正式 UI 语义（地图 / 任务卡 / 可展开入口）就必须继承避让 / 碰撞审计 / 状态截图；带 transform 过渡的元素用"基础矩形 + 偏移量"测量或临时禁用过渡。
- **实验页通过不等于完整版同步（2026-05-12 / 05-13）**：index 主入口必须指向已确认改动，旧壳层降级为次级入口并标注；用户要求"完整版也是最新版"时必须真同步并用真实浏览器截图验证完整路径。
- **动效演示独立系列页 + 可直接播放入口（2026-05-13）**：按动作类型分类、提供重播控制和浏览器直接可玩入口，源码链接不能替代演示入口；见 UI 指南 §10.4 / §11.4。

### 7.7 视觉风格与美术方向

现行守门链为 `@像素艺术` + `design/art-direction/angus-visual-style-guide.md`（AGENTS.md 顶层规则）；本节保留早期方向性错题：

- **高级感不等于空白（2026-04-29）**：报刊 / 杂志 / 编辑部 / 档案类 UI 页面本体要有插画、章印、边栏、标题装饰、印刷纹理等可辨识叙事锚点；用户没要求极简时不推大留白模板。
- **独游需要记忆点（2026-04-29）**：不满足于"高级、贴题、可用"；主动找角色化符号、图形母题、强色彩策略、黑色幽默微文案，服务"危险小报包装现实"。
- **怪异要图形化讨喜（2026-04-29）**：扁平图形 / 粗轮廓 / 低细节 / 商品贴纸化；避免湿润眼球、写实皮肤、触手牙肉等生理质感；讨喜来源参考"表情包包体 + 复古纸媒活动页 + 周边商品图册"组合。
- **报道重组不退化功能面板（2026-06-06）**：清爽只能来自主物件承担表达，不能来自删除或抽象化物件；已有标杆截图的界面返工先做"标杆截图对照表"（主承载物 / 功能物件 / 主 CTA 是否像场景动作 / 后台面板语法下线清单）。
- **杂志本体承载品牌与决策（2026-06-07）**：质感不只靠纸纹做旧；刊头品牌、期号、主图、栏目条、导语、分栏正文、版位语义和就近决策反馈都要落在杂志本体；右侧签批只做最终确认。
- **UI 诊断下钻组件解剖（2026-06-09）**："不高级 / 不像标杆 / 另一个诊断更好"类反馈必须拆到组件解剖层：容器角色、背板明度与材质、边框职责、文字金字塔、语义色面积、密度节奏、CTA 锚定、100% 裁切验收；只说"层级不清 / 更清爽"不算合格诊断。
- **UI 返工扫同类组件语法（2026-06-08，2026-07-14 补强）**：修用户圈出局部前先建"同类组件清单"（同页同语法的卡片 / 票据 / 角标 / pin / 日志条），验收裁切至少含一个未被用户点名的同类局部，同类复发不得交付。若被指出的是字段语义或数字，清单必须扩为该页全部可见基础组件，逐项核对玩家问题、必要性、唯一归属和正式数据源；执行细则见 `assetized-ui-production-chain.md` §2.1 / §7.1。

### 7.8 动效与 3D 资产验收

骰子 3D 化连续 13 轮修订的可迁移判断器（原文见归档；执行链路见 `docs/workflows/art-motion-asset-landing-workflow.md`）：

- **实现侧进展不等于视觉侧成立（2026-05-21 复盘口径）**："画了多个面"≠立方体，"修好闭合"≠整体通过，"代码填充了面"≠不透明，"屏幕文字位置接近"≠贴图。视觉对象必须拆成独立可否决条件逐项验收；每次修 A 都要回归旧版已成立的 B；结论来自逐对象局部放大肉眼检查，不来自"比上一版好"的趋势判断。
- **视觉需求先拆可观察条件（2026-05-21）**：通用流程：提取需求词 → 写成立条件 → 写禁止误读 → 整页截图 → 局部裁切放大 → 多状态检查 → 旧错回归；截图读法与用户目标不一致即未通过，不得用实现意图辩解。
- **实体骰验收要点（2026-05-19 至 05-21 系列）**：闭合体积（共享边角、侧面厚度、遮挡投影一致）；不透明面材（背面线 / 网格 / 轨迹不得在正面文字区可辨认）；面内容作为贴图随面投影（不用屏幕坐标文字层）；CSS 3D 被读成薄片时立即转真实几何体路线（Three.js / Godot / Blender），不再消耗在透视贴片上。
- **摇骰要像实体骰（2026-05-19）**：骰子区是判定弹窗视觉主舞台；动效至少含实体骰盘、位移、旋转、落地反弹、阴影 / 轨迹中的多项线索；动效未成熟先撤出本体隔离到实验页，用户确认后最小化迁移。
- **按用户打开方式验收（2026-05-21）**：不能只在本地 HTTP / 脚本截图环境通过；避免被 `file://` 拦截的 ES module；局部动效必须嵌回原界面布局验证，不扩成全新大舞台。
- **落地不得同名降级（2026-05-25）**："把实验页方案落地"意味着迁移被认可的视觉主体、建模方式、材质和截图读法；先列出实验页不可降级项，本体截图与实验页基准图并排验收；本体第一眼不像已通过对象即判未完成。

### 7.9 生图与资产化 UI 放行

执行真源为 `docs/workflows/ui-geometry-and-text-safety-gates.md`、`docs/onboarding/assetized-ui-production-chain.md`、`docs/onboarding/imagegen-color-contract-gate.md`；本节保留触发错题：

- **文字 QA 框必须来自实际字形（2026-07-14）**：文字排版、粉色 overlay 与 manifest 必须共用实际渲染后的 alpha glyph bbox，并保留字体 left/top bearing；禁止用 `draw_origin + width/height` 合成视觉框，禁止只测宽高却宣称绝对位置通过。详见 gates 真源 `text_carrier_capacity` 与 `scripts/ui-contracts/validate_text_bbox_evidence.py`。
- **硬规则必须绑定放行动作（2026-07-03）**："交给用户看候选"也是一次放行；凡称可把关候选 / 落地候选 / 生产候选，必须先附真实边缘几何 QA（≥3 个核心信息面、参考线、逐项判定）；无角度证据只能写"几何未验证"，不得写"基本正交 / 可以把关 / 差不多正"。现已固化为 gates 文档 §2.2 自动触发。
- **文字功能面倾斜复发即切分层路线（2026-07-03 追加）**：文字界面不斜是铁律；同类功能行连续两轮因倾斜失败时，停止 prompt-only 整屏有字生图，改为"生图无字外观 + 正交功能资产 / 运行时文字层 / 可测量 mask"的分层资产化流程。
- **程序合成不能用几何 / 统计 gate 代替内容目检（2026-07-08，2026-07-13 补充）**：世界地图 `left_region_card` B1 曾出现几何、边缘统计、运行截图均 PASS，但肉眼可见双地球、warning 双三角、照片槽越界和源图绿条残留；B1.1 又在写入 `composite_cleanliness` 后漏判四状态右缘竖向暗带，B1.2 进一步把合法右侧卡壳当成 bleed 擦成透明洞，导致边框被照片 / 透明带隔断且深色背景读成“底层图片泄漏”，说明“目检”若没有局部证据仍会假通过。B2.9 又证明：即使“外环逐像素保留、右框 0 变化、无 inpaint”全部成立，新生成的内芯仍可能因手写端点形成明显歪 X；局部 gate 只能证明其声明拥有的区域，不能替代对本轮所有新增可见像素的独立形状审查。后续任何程序合成 UI 资产必须执行三条硬规则：照片 / 插图裁片先按合同槽位做掩膜，槽外 0px 溢出；图标、徽章、文字只能有一个主承载轨，运行时不得再叠同语义图标补救；`geometry / greenish / nonblack` 只能证明形状和像素口径，不证明内容干净。manifest 必须加入 `composite_cleanliness`，逐状态人工目检重复元素、接缝、槽外溢出、源图残留和卡体轮廓内透明洞；涉及图片槽或拼接边缘时，必须附 100% / 200% 边缘 close-up，尤其检查低饱和竖带、暗带、源裁片边缘、`right_frame_continuity`、`layer_order_integrity` 和 `card_body_opacity_probe`，才能写视觉通过。修边不得直接擦除整条边缘带，必须先证明该区域不是合法 shell / frame / bevel；每轮还必须单独列出并放大检查所有新增可见区域。QA 判据若要改，必须在 manifest 写明新旧口径和原因，禁止改到能过为止。
- **可见美术窗口与合同槽冲突时先裁决语义（2026-07-08）**：`left_region_card` B1.3 证明“透明洞修好”仍可能视觉失败：`x390..408` 透明像素为 0，但补上的是状态色程序带，不是壳体纹理，照片仍没有贴到 B 版内框。若源壳可见窗口、图片槽、文字安全槽或 hit 槽不一致，不得用纯色带、蒙版、擦除、阈值放宽来满足局部 gate；必须先上报冲突并让用户 / 设计记录裁决语义（例如“照片美术层填满可见窗口，`photo_slot` 只管运行时 safe / hit”或“重建壳体使可见窗口等于槽位”）。alpha / nonblack / greenish pass 不得自动推出 `art_shell_texture_integrity` 或 `composite_cleanliness` pass。

- **实测优先：几何值、判定式、容差都是假设（2026-07-09）**：WMW 左卡复盘确立。传闻几何值（"18px 残带到 x408"）层层转述五轮，一次探针实测即推翻（真实窗口右界 x366）；单帧调参的颜色判定式部署到四帧后测量偏差达 101px；gate 容差 ≤2px 无依据必然失败。判断器：凡脚本或规程里出现具体数字 / 颜色阈值 / 判定条件，先问"这是量出来的还是听说的 / 拍的"；写 brief 必须区分"已实测事实（附证据）"和"待验证假设（附验证步骤）"，执行方开工第一步跑探针。全文见 harness §6.3（brief 双栏制）与 gates 文档 §5.1 配套规则。

## 7A. 设计采纳沉淀机制（长期固定机制）

> 自 2026-04-27 起，本机制纳入长期协作约束，所有后续 AI / 新对话都必须遵守。

### 7A.1 沉淀文档

- **总索引位置**：[`docs/设计采纳记录.md`](../设计采纳记录.md)
- **分册位置**：[`docs/design-decisions/`](../design-decisions/)
- **文档定位**：用户在讨论中**已采纳 / 待定 / 进阶 / 合并 / 撤回** 的设计意见的长期索引与分册；不是讨论原文，也不是规格文档，而是**决策留痕**。
- **读取原则**：先读总索引的“跨分类检索保护”和条目 cross-read tags，再读对应分册。分册用于降低噪音，不得成为漏检理由。

### 7A.2 何时写入（触发条件）

只要用户在讨论中出现以下任一**明确表态**，AI 在当次回复结束前必须把对应条目追加进该文档：

- 「这个采纳」「加入 …」「作为 …」「可以考虑作为 …」「合并到 …」；
- 「先留着」「待定」「回头再想」「加入待定区」；
- 「作为后期进阶」「作为某类型设计」「作为某角色特性」；
- 「撤回」「不要这条了」「改成 …」（撤回/修订路径，见 7A.5）。

**反例（不写入）**：

- AI 单方面的设想或推理（即使写得再合理）；
- 仅用户在发散讨论里"提到"但未表态的内容；
- 仅 AI 在回复里"建议"而用户未确认的内容。

### 7A.3 分类与编号

编号语义继续沿用，但正文按主影响域拆到分册：

| 编号前缀 | 含义 | 常见主分册 |
|----------|------|------------|
| `A` | 已采纳的通用设计 / 流程 / 视觉规则 | 按主影响域放入机制、UI、美术或流程分册 |
| `B` | 特殊任务 / 特殊角色类型采纳 | 通常放入 `core-mechanics.md` |
| `C` | 后期进阶选项 | `backlog-and-deferred.md` |
| `D` | 待定区 | 按内容放入流程 / 美术 / backlog 等主分册 |
| `M` | 机制库备查，未采纳 | `backlog-and-deferred.md` |

新条目编号沿用前缀 + 自增数字（如 `A63`、`B5`）。主分册按“最主要影响域”选择，但必须在总索引写 cross-read tags。

跨分类读取硬规则：

| 任务类型 | 必读 | 条件补读 |
|----------|------|----------|
| 骰子 / 派遣 / 达标率 / 黑骰 / 任务规则 | `core-mechanics.md` + `ui-ux-decisions.md` | 涉及界面视觉、PNG、生图、像素、半调、纸质或地图包装时，补读 `art-direction-decisions.md` |
| UI / 原型 / 截图 / 交互 / 布局 | `ui-ux-decisions.md` | 涉及规则、概率、任务类型、资源流时，补读 `core-mechanics.md`；涉及视觉风格或资产化时，补读 `art-direction-decisions.md` |
| 资产化 UI / bitmap / PNG / atlas / manifest | `ui-ux-decisions.md` + `art-direction-decisions.md` + `assetized-ui-production-chain.md` | 如果组件承载任务规则、状态机或玩法语义，补读 `core-mechanics.md` |
| 美术资源 / prompt / 风格守门 | `art-direction-decisions.md` | 要落到可交互 UI 时补读 `ui-ux-decisions.md`；视觉承载玩法语义时补读 `core-mechanics.md` |

例：任务虽然叫“骰子界面”，也不能只读骰子机制或 UI 分册；如果这次要决定骰子如何像 Angus、是否使用像素 / 半调 / 纸质资产，就必须补读美术方向分册。

### 7A.4 条目格式

总索引每条至少包含：

- **ID**：如 `A62`；
- **标题**：一句话说明决策；
- **主分册**：完整条目所在文件；
- **Cross-read tags**：例如 `dice, dispatch, ui, art, assetized-ui`。

分册正文每条至少包含以下字段：

- **来源**：会话日期 / 上下文，例如 `2026-04-27 骰子机制讨论`；
- **机制**：一段话说明该机制本身；
- **应用范围**：通用 / 特定任务类型 / 特定角色 / 进阶 / 待定；
- **状态**：已采纳 / 待定 / 进阶 / 合并 / 已修订 / 已撤回；
- 如有合并、撤回、修订，再追加 **合并备注** / **修订备注**。

具体写法示例参见现有条目（如 A1、B1、C2）。如果条目跨域，主分册只放一份完整正文；总索引用 tags 和必要回链保证后续能跨读。

### 7A.5 修订与撤回

- 用户调整或撤回某条意见时，**保留分册原条目**，在条目末尾追加：
  - `已修订（YYYY-MM-DD）：…新表述…`
  - 或 `已撤回（YYYY-MM-DD）：…原因…`
- **不允许直接覆盖**或删除原条目，确保决策路径可追溯。
- 引用关系（如 B2 与 B1 合并）也应保留并标记。
- 如果修订导致影响域变化，必须同步更新总索引的主分册或 cross-read tags。

### 7A.6 与其他文档的关系

- 本机制与 7 节「新增反馈模板」**互不替代**：7 节记的是"AI 偏差与用户偏好"，本机制记的是"具体玩法/机制的采纳决策"。两者并存。
- `docs/设计采纳记录.md` 与 `docs/design-decisions/` **都不是规格文档**；总索引用于路由，分册用于保存决策正文。某条目要落地为代码或字段时，应另起规格文档（或直接落到 `design/gdd/`），并在采纳条目里**回引规格文档**。
- 如果用户后续要求把某条采纳"转为正式真源"，AI 应把该条同步到对应 `design/gdd/` 文档，并在原条目里标注 `已升级为真源：路径`。

### 7A.7 编外内容先确认

- 用户明确纠偏（2026-05-07）：明显属于编外内容、外部商业化素材、活动外观命名、临时文案方案，或与 Angus 当前项目风格 / 玩法真源关系不明确的内容，**不要默认写入** `docs/设计采纳记录.md`。
- 这类内容即使用户选定了名称或文案，也应先判断是否属于项目长期设计决策；若不确定，先询问用户“是否需要沉淀到项目记录”，得到明确同意后再追加。
- 若已经开始准备写入但用户说明“这是编外内容”，应立即停止写入；已写入的需按用户要求修订或移除。

### 7A.8 待细化工作流点子：美术风格稿与视觉组件词典

- 用户明确留档（2026-05-07）：先作为点子记录，后续再详细制定正式美术风格稿和“视觉组件词典”的规则。
- 初步方向：先确立一份可复用的美术风格稿；后续每次玩法改动先在玩法 UI 原型中落地，暂不做完整 GUI 视觉包装；再基于新的玩法原型截图和美术风格稿生成目标效果图；最后把效果图拆解为可实现的视觉组件、状态、符号和布局规则。

- 记录边界：当前只记录工作流点子，不把本轮临时生图尝试或具体风格图本身写入 `docs/设计采纳记录.md`。

## 7B. Steam 第一眼素材反馈：不要把“缩略图可读”误判为“正式完成”

用户明确纠偏（2026-06-01）：在《世界未解之谜周刊》Steam 头图讨论中，AI 曾把一张能在 `120x45` 下读出 Logo / 报纸 / 异常焦点的图误判为“成品候选”。用户指出它和前几轮草图相比没有本质区别，风格、字体、内容和第一眼吸引力都达不到竞品完成度。

后续处理 Steam 头图、商店页首图、宣传片首帧、主视觉或类似商业素材时，必须区分两件事：

1. **缩略图识别**：小尺寸下能看出大形、Logo 区和主物件。
2. **正式美术完成**：大图有品牌字标、主视觉、材质、光影、情绪钩子、细节密度和商业可信度。

缩略图识别只是一项压力测试，不等于正式完成。尤其不能因为一个设计在 `120x45` 下“能看懂”，就忽略它在 `460x215` 或商店页首屏中仍像线框、图标、内部概念稿或 prompt 草图。

后续 AI 在评估或生成 Steam 头图时，至少要做三步：

1. 与成熟独立游戏头图并排看完成度，不只看构图是否清楚。
2. 明确指出当前图属于哪一阶段：草图、方向样张、准正式图、成品候选、可投放图。
3. 若用户要求“成品”，必须检查 Logo 定制感、主物件实体感、材质层次、光影焦点、异常钩子和竞品旁排预算感，不能只做大形和颜色。

这条反馈也适用于未来所有“概念图 / 宣传图 / capsule / key art / 首帧”任务：AI 不得把“表达了设定”当成“具备商业完成度”。

### 7B.1 Steam 头图的 Logo 和色彩不能用普通排版糊弄

用户继续纠偏（2026-06-01）：第十一轮头图底图比第十轮更完整，但标题字体仍非常普通甚至难看，没有专门艺术设计过；整体色调灰土，缺乏吸引力，也不够贴合主题。与成熟独立游戏头图并排时，差距主要体现在 Logo 和色彩系统。

后续处理 Steam 头图时，必须把以下内容作为硬检查：

1. 标题是不是游戏 Logo，而不是普通字体排版。
2. 字形是否有主题化处理，例如断裂、错印、压印、故障、符号融合或专属轮廓。
3. 主色是否是可记忆的品牌色，而不是自然材质的平均色。
4. 画面是否有高饱和或高对比的视觉抓手。
5. 与竞品并排时，Logo 是否能先被看到。

如果标题只是宋体 / 黑体 / 普通字体加色块，即使底图完成度提高，也不能判断为正式头图候选。

### 7B.2 不要把 Angus 做成旧报纸 / 旧档案气质

用户继续纠偏（2026-06-01）：字体仍没有设计，同时图片依然显得老旧；需要重新思考 Angus 自己应该采取什么风格，以及其他游戏头图的丰富和游戏风格之间的关系。

后续处理《世界未解之谜周刊》的 Steam 头图时，必须记住：玩家不是在观看旧案，也不是在考古旧报纸，而是在经营一份会通过解释和传播影响现实的周刊。因此头图的基调不应是“旧档案 / 泛黄报纸 / 灰褐复古悬疑”，而应更接近“异常新闻设计”：新鲜发刊、高对比编辑设计、强 Logo、印刷错位、现实被版面污染。

如果画面主要感觉是老旧、灰土、档案、历史案件、怀旧报纸，即使它有周刊元素，也应判为方向偏差。

## 7I. 资产化 UI 的常见误判：把 safe-zone 通过当成正式完成度

用户在 2026-06-16 明确指出，世界地图 v6g 预览相较正式游戏质量仍有明显差距，尤其是图、文、功能配合不好，文字像简单贴在界面上，字体也不成立。后续 AI 需要把这次作为资产化 UI 链路的关键错题。

这次误判不是单个字的位置问题，而是 AI 把工程验证当成了产品质量验证：

1. `dynamic_text_rects` 没越界，只说明程序层能放字，不说明文字已经属于纸面、档案、按钮或地图。
2. `review-overlays` 通过，只说明禁入区没有被压，不说明玩家能理解当前选中、风险、行动和后果。
3. 生图组件像 Angus，只说明美术语言有潜力，不说明字体、状态、pin、CTA 和交互反馈已经成为同一套系统。
4. Godot 预览能跑，只说明链路打通，不说明可以替换正式界面。

后续处理类似任务时，AI 必须先把“组件验证稿”和“正式 UI 候选”分开汇报。凡是文字仍像贴图上的 Label、字体没有 token、状态没有统一语法、主 CTA 不像职业动作、当前对象没有跨列表 / 地图 / 详情 / 按钮联动，都不得对用户说“已经没问题”或“可以上线替换”。

更可靠的推进方式是：先用一个真实状态做单屏 mock，例如“北美禁区带 selected + 红线升温 + 可进入”，让 SIA、像素艺术、UX 老哥和 UI Designer 分别从商业第一眼、Angus 风格、操作链和布局系统复审；只有这个单状态的图文功能融合通过后，再扩展全状态、全地区和 live replacement。

这条是协作错题；具体执行规则见 `docs/onboarding/ui-interaction-guidelines.md` 的“资产化 UI 正式质量门槛”和 `docs/onboarding/assetized-ui-production-chain.md`。

## 7J. 资产化 UI 交付不能把“旧承载页逻辑截图”冒充“目标界面效果”

用户在 2026-06-17 明确指出，派遣签批台的交付截图虽然跑出了 Godot 逻辑状态，但和之前确认的图文填充风格稿 / 资产化目标界面差距巨大，甚至功能分区也不像同一个界面。这次问题不是截图没生成，而是 AI 把不同阶段、不同载体、不同用途的产物混在一起交付。

这次误判暴露了三层错误：

1. **产物类型混淆**：旧 Godot 三栏逻辑验证截图只能说明 P0 条件、按钮状态和阻断文案能跑，不等于目标派遣签批台的视觉 / 功能分区已经落地。
2. **目标锚点丢失**：用户要对照的是图文一体的 filled-state 效果稿和已认可的资产化界面语言；AI 却用现有世界地图 / 周循环框架里的开发态页面截图作为验收对象。
3. **功能分区漂移**：资产化 UI 的功能分区应先冻结再落地。若截图里的左 / 中 / 右职责、主物件、候选区、骰池区、签批复核区和 CTA 位置已经和目标分区不一致，不能用“功能可用”解释为通过。

后续处理类似任务时，AI 必须先给每张图贴清楚产物标签：

- `目标效果稿 / filled-state mock`：用于看图文融合、风格、真实内容填充和商业截图感。
- `组件验证稿`：用于看某个资产、safe zone、状态 atlas 或局部承载能力。
- `运行截图 / runtime screenshot`：用于看真实引擎 / 网页里功能和交互是否跑通。
- `逻辑烟测截图`：只用于证明某个 P0 条件、阻断或状态机被触发，不可作为视觉验收。

如果运行截图与目标效果稿不是同一个页面职责或同一套功能分区，最终回复必须明确说“这是逻辑烟测，不是视觉验收”，并同时给出下一步补齐目标界面的计划。不得把旧载体里的最小功能补丁包装成资产化 UI 落地效果。

## 7K. 资产化 UI 重构不能把旧骨架换皮冒充底层重思考

1. 第一眼大块布局是否真的不同于上一版，而不是只换了皮。

## 7L. 美术资源交付不能把程序化示意板冒充风格稿

用户在 2026-07-06 指出骰子“风格稿”显得简陋，并追问是否是 Image2 生图。这次问题不是单个骰子图标画得粗，而是 AI 把程序化 SVG 信息映射示意板包装成了可审美术风格稿，导致用户按正式美术完成度验收时看到的是工程草图。

这次误判暴露了三层错误：

1. **产物阶段误判**：SVG / Canvas / CSS 快速画出的规格图只能验证信息映射、字段、布局和状态，不等于美术资产方向通过。
2. **目标锚点降级**：用户要求参考图3 / 图4 真实美术标杆时，交付物必须继承材质、光照、低多边形块面、印刷颗粒、物件质感和整体完成度；不能只抽取颜色和标签。
3. **命名误导验收**：一旦 AI 称它为“风格稿”，用户自然会按美术稿标准审。若实际只是低保真示意，必须在第一屏明确降级，不得让用户自己发现“怎么这么简陋”。

后续处理骰子、美术道具、动效资产、UI 组件视觉或其他美术资源时，必须先区分：

- `信息映射稿 / 结构示意`：验证真实数据、规则含义、状态层和接口字段，可用 SVG / Canvas / 低保真图。
- `美术风格稿`：验证是否像 Angus、是否继承标杆图、材质和完成度是否成立，应使用生图、建模渲染、精修位图或同等高保真手段。
- `生产候选 / 资源标杆`：必须经过美术指导复审，并能支持后续切图、贴图、动效和 runtime 验收。

如果用户要“符合真实美术风格的骰子”，第一轮可以先做信息映射，但必须明确说“这是低保真规格图，不审美术”；真正给用户看美术时，应至少交 1-3 张高保真候选图，包含普通骰、黑骰、真实骰面和与标杆图的可见继承。

## 7M. 动效 blockout 不能冒充 Image 资产落地

用户在 2026-07-06 进一步指出：上一版 Godot 3D 骰子虽然按风格稿的大致配色做了程序实现，但没有真正走“用 Image 生成美术资源（骰面）-> 切图 -> 拼接 / 贴图 -> Godot runtime 动态验收”的路子，所以看起来仍然简陋。这次问题不是动效参数单独不好，而是 AI 把“程序能动”误当成了“美术资产已落地”。

后续处理骰子、UI 动效、2D 角色动作、特效、道具或其它动态美术资源时，必须把交付物分清：

- `motion_blockout`：只验证节奏、位移、触地、回弹、停顿和是否抢主操作；可以用临时模型、临时色块、临时 Label。
- `bitmap_or_model_asset_runtime_preview`：必须有实际美术资源进入引擎，例如 Image 生成图集、切出的 tile、GLB / Blender 模型、Sprite 帧序列、材质贴图或 rig；并提供 Godot / HTML / Unity 等真实 runtime GIF / 视频。
- `production_candidate`：在 runtime 预览基础上，还要有状态矩阵、命名、替换范围、已知缺陷和正式接入边界。

如果用户明确说“用 Image 生成美术资源 / 骰面 / 拼接落地”，交付前至少要拿出四件证据：源图或图集、切出来的资源文件、引擎绑定后的真实运行画面、动图或视频。只有程序材质和运行时文字时，必须主动降级为 blockout，不能让用户按正式美术验收。

2026-07-06 追加硬规则：美术资源进入切图前必须先过“几何不变量 Gate”。方形物体的源资源必须是方形，不能只让导出的 tile 或 Godot plane 最后看起来是方形；4x3 图集如果每格要方形，源图总比例必须是 4:3。后处理把长方形 cell 压成方形，是失败修饰，不是通过。后续骰面、方形 icon、头像、sprite sheet、角色动作帧、特效帧和 UI atlas 都必须先验证源图比例、网格比例、pivot 和裁切边界，再进入 runtime 动图验收。

## 7N. 并置卡牌不能只锁容器高度，还要锁活跃图像基线

用户在 2026-07-06 公信线好 / 坏结局双卡图中连续指出：坏结局图先是用深色蒙版压原图，导致上方图片不完整、文字区被底图污染；之后虽然用 `1024x835` 上图框严格合成，但坏图组件内部有大段底部空黑，导致图片主体位置仍和好结局不一致。进一步并排检查时，用户又指出两张图的可见下缘线不在同一水平线，且中文字体存在细微差异。

这次错题的本质是 AI 把“容器尺寸一致”误当成“视觉位置一致”，随后又把“工程对齐”误当成“版式成立”。对于要并排对照的卡牌、海报、UI 组件或图文页，只锁 canvas、卡宽、图框高还不够；如果图像内容在框内漂浮、主体下沿 / 地平线 / 物件基线不同，玩家第一眼仍会觉得两张图没有配套。但修正基线时也不能牺牲已被用户认可的文字呼吸、段落节奏和情绪留白。

后续做好 / 坏结局卡、状态对照图、before / after mock、双图宣传稿、成组 UI 组件时必须执行：

1. 先定义固定模板参数，例如整卡尺寸、图像框、文字区起点、标题和正文坐标。
2. 再定义“活跃图像基线”：主物件下沿、地面线、塔基 / 档案堆 / UI 壳底边应落在哪个 y 坐标附近。
3. 生图只生成上方组件时，要检查组件内部是否有过多空黑或空白；有则用明确源裁切框 / 缩放参数处理，而不是只等比塞进容器。
4. 不得用深色蒙版、遮罩、半透明面板把不合格整卡图补成候选；这只能算临时排版验证，不能作为可审美术稿。
5. 文字层必须同源渲染：同一字体族、字号策略、粗细、抗锯齿、行高和居中函数；长句只能在同一最大宽度规则下微缩，不能为其中一张卡手动换一套字体参数。
6. 若用户已经认可某张卡的松弛排版，后续修对齐应优先保留该卡的字号、行距、段落间距和成就位置；不能为了让基准线更漂亮，把文字区压短或把标题 / 正文整体放大。
7. 对已认可卡牌做配套卡时，必须先抽取已认可卡的文字层 bbox：标题、route、slogan、正文每行、成就分别记录 top / bottom / height / center x / 颜色覆盖行。后续候选不得只说“光学字号匹配”，必须用 bbox 或覆盖线证明 route、标题、正文、成就的真实视觉高度和位置一致。注意：QA 图不能只把左卡 bbox 复制画到右卡上，还必须检测右卡实际文字 bbox 并给出差值；如果右卡成就、route、标题等真实高度超出母版，即使字体族和 point size 相同也判失败。
8. 交付前必须把成组图并排展示，检查容器边界、可见图像下缘线、图像主体基线、标题 y 坐标、文字区起点、字体观感、段落呼吸和成就位置是否一致。只要“框高一致但主体位置不一致”“文字像两套模板”“对齐修好了但原本的松弛感没了”或“route / 成就 / 标题明显不同号”，仍判定失败。

这条是协作错题；具体结局双卡口径已写入 `docs/design-decisions/art-direction-decisions.md` 的 A136。

## 7O. 用户说“生图”时，不得用程序绘图代替真实生图

用户在 2026-07-06 进一步明确纠偏：当他说“生图”“生张大图”时，意思是调用真实生图软件 / 图像生成模型生成图片，而不是让 AI 用 PowerShell、C# `System.Drawing`、SVG、Canvas、HTML/CSS 或其他程序化绘图方式画一张示意板。即使这张图的目标是看配色，AI 也不能擅自把“生图”降级成“程序生成色卡 / 缩略板”。

这次误判暴露的问题是：AI 把“产物看起来是一张图片”误当成“满足了生图请求”。但对用户来说，“生图”不仅描述输出格式，也明确描述生产手段和预期完成度。程序化缩略图可以用于参数表、结构示意、排版 QA、文字 bbox 检测或色彩规范沉淀，但不能冒充生图结果。

后续硬规则：

1. 用户说“生图 / 生成图片 / 再生一张 / 生张大图 / 按这个生图”时，默认必须调用真实生图工具或图像生成模型，例如 `openrouter-image-gen` 或 `$imagegen`。
2. 不得用 SVG、Canvas、HTML/CSS、PowerShell、C# `System.Drawing`、脚本绘图、程序色卡或程序缩略板替代生图，除非用户明确说“程序画 / 示意图 / 结构板 / 色卡表 / 可编辑模板 / 不用生图模型”。
3. 如果任务同时需要精确文字、拼版、尺寸一致、bbox QA 或并排检测，正确流程是“先真实生图得到图像层，再用程序做文字排版、拼版和 QA”；程序只能做后处理和检测，不能替代图像生成本身。
4. 如果当前工具无法生图，应直接说明“生图工具不可用 / 当前无法真实生图”，不要静默改成程序绘图。
5. 若 AI 判断程序化色卡更适合沟通，也必须先明说“这不是生图，是低保真配色示意；是否先用它看配色”，不能在用户已说“生图”后擅自切换。

## 8. 建议后续 AI 的开场动作

当后续 AI 接手本仓库，尤其接到玩法、原型、交互、UI 感知类任务时，建议顺序：

1. 先读本文。
2. 再读 `design/gdd/core-experience.md`，先确认本次任务服务的核心体验和玩家感受。
3. 若涉及玩法、规则、任务、骰子、黑骰、深度链或路线设计，再读 `design/gdd/gameplay-design-principles.md`。
4. 若涉及 UI / 交互 / 原型呈现，再读 `docs/onboarding/ui-interaction-guidelines.md`。
5. 再读 `docs/onboarding/repository-map.md`。
6. 再确认当前任务讨论的是哪种载体：
   - `design/prototypes/html/`  
   - `gd_project/`  
7. 明确回答自己三个问题：
   - 用户要的是规则层，还是体验层？  
   - 用户要的是最小补丁，还是重做？  
   - 用户最早想在哪个区域 / 界面玩到它？

重要：`design/gdd/core-experience.md` 是最高层体验锚点。后续任何新增或修改该文档的内容，都必须先向用户确认；不能仅凭 AI 自己判断“这很核心”就自动写入。其他设计意见仍按 `docs/设计采纳记录.md` 的规则先沉淀。

如果这三个问题没有答清楚，不要急着改。
