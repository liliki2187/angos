# UI 与交互执行规范

> **用途**：给后续 AI / 新对话在处理 Angus 的 UI、交互、原型呈现、视觉实验页时使用。
> **定位**：这是执行规则手册，不是错题本，也不是玩法真源。
> **最后更新**：2026-07-08（尾部 17 条日期补充归并为 §12 派遣签批台专项 / §13 跨页面几何规则；几何正交阈值收敛到 `docs/workflows/ui-geometry-and-text-safety-gates.md`，原文归档至 `_obsolete/ui-interaction-guidelines-legacy/`）
> **重构说明**：本文按“母原则 -> 审计清单 -> 通用规则 -> 场景规则 -> 验收与更新 -> 专项规则”组织；既有规则不应因重排而省略。后续新增规则按 `docs/workflows/angus-workflow-harness.md` §7.1 沉淀去重律先查重，归并进对应章节，不再在尾部按日期追加补丁段落。

## 顶层硬规则：Angus 不做移动版

- Angus 当前所有游戏 UI、HTML / Godot 原型、视觉实验页和截图验收默认只面向桌面 16:9。
- 后续 AI 不得主动设计移动端、触屏版、窄屏版、移动端断点或移动端专用布局，也不得把移动端截图作为默认交付项。
- 只有用户在当前任务里明确要求移动端时，才可作为一次性例外处理；交付时必须说明这是临时例外，不改变“不做移动版”的顶层规则。
- 桌面 UI 验收优先覆盖 `1920×1080`、`1600×900`、`1366×768` 这类 16:9 桌面视口；若使用非 16:9 开发窗口，只能作为辅助观察，不作为默认结论。
- Godot / 游戏本体 UI 不得为了移动端或保守兼容假设牺牲桌面视觉效果。默认按桌面效果优先选择渲染方式、材质、shader、灯光、动效和截图验收；只有用户明确要求移动端或低配兼容专项时，才把保守渲染作为独立分支处理。

## 0. 文档使用方式

### 0.1 与 `ai-collaboration-guidance.md` 的分工

- `ai-collaboration-guidance.md` 是大的协作错题本，记录用户偏好、AI 误判原因、宏观工作方式问题。
- 本文是 UI / 交互执行规范，记录做界面时必须遵守的具体规则、槽位、检查项。
- 看似 UI 的反馈，如果本质是范围失控、需求理解偏差、验证方式错误，应继续写入 `ai-collaboration-guidance.md`。
- 可执行的 UI 规则应沉淀到本文。

### 0.2 触发阅读

凡是任务涉及以下任一内容，必须先读本文：

- HTML / Godot 原型界面；
- 任务卡、地图点、派遣配置、角色详情、骰子表现；
- UI 信息层级、交互动效、视觉符号、截图验收；
- 实验页、生图对照、视觉组件词典。

### 0.3 使用顺序

处理 UI 任务时，先按以下顺序使用本文：

1. 涉及 UI 设计、布局方案、wireframe、mock 或可见原型落地时，必须让 `ui_designer` 与 `ux_laoge` 都参与并互相校验：新 UI / 新布局从 brief 出稿时，先调用 `ui_designer` 生成元素对照表、桌面 16:9 mock 和交接摘要，再调用 `ux_laoge` 做落地前评审；已有 UI / 截图 / 原型改进时，先调用 `ux_laoge` 做诊断，再把诊断交给 `ui_designer` 出改进稿。若当前环境不可调用某个 subagent，则按对应 `skills/ui-designer/SKILL.md` 或 `skills/ux-diagnosis/SKILL.md` 在当前线程执行同等流程。
   - 若 UI 任务的主要问题是美术风格、像素 / 半调 / 印刷材质、参考图转译、视觉 prompt 或“像不像 Angus”，再让 `angus_art_director` 参与风格守门。它不替代 UI Designer 的布局方案，也不替代 UX 老哥的可读性与操作链诊断。
   - 做风格差异分析时必须先声明本轮判断维度。若用户问“视觉层面 / 美学层面有什么区别”，只能比较构图重心、明暗比例、色相与色彩占比、形状语言、边缘处理、材质丰富度、颗粒分布、半调 / 套印结构、物件密度和字体图形化程度；不得用“这个区域代表什么功能 / 叙事 / 内容”替代视觉判断。
2. 先读 §1，确认这次界面是否符合用户的 UI 设计母原则。
3. 再用 §2 做改动前审计，明确页面职责、主操作、状态语义和不做范围。
4. 然后查 §3-§4 的通用规则，确认信息层级、控件语义、状态距离和位置稳定。
5. 最后查对应场景规则：任务卡看 §5，地图 / 区域看 §6，派遣看 §7，骰子判定看 §9，实验页看 §10。
6. 如果父级 Codex、`ui_designer` 与 `ux_laoge` 意见冲突，必须把分歧点、取舍成本和建议交给用户判断，不能擅自按其中一方继续落地。
7. 交付前必须按 §11 做截图、入口和版本验收；若用户纠偏，按 §0.4 检查是否需要沉淀。

### 0.4 更新规则

后续用户给出 UI / 交互反馈时：

- 如果是“为什么 AI 会这样误判”，写入 `ai-collaboration-guidance.md`。
- 如果是“以后界面具体怎么做”，写入本文。
- 如果两者都有，两边都写，但不要复制同一段：协作指南写偏差原因，本文写执行规则。
- 如果用户要求修改、纠偏、返工，或指出某个 UI 判断不合理，不能只改实现和截图；最终回复前必须检查是否需要同步本文、`ai-collaboration-guidance.md`、`docs/设计采纳记录.md` 总索引及 `docs/design-decisions/` 对应分册、相关 GDD 或 `docs/会话交接_当前状态.md`。
- 如果判断本次 UI 反馈不需要新增规则，也必须在最终回复里简短说明“不写入规则文档”的原因，避免把沉淀遗漏伪装成默认处理。

## 1. UI 设计母原则

这些原则是后续做界面前的最高优先级判断。具体组件规则若看起来互相冲突，先回到本节判断“玩家此刻到底在做什么决定”。

### 1.1 界面先服务玩家当前决策

- 每个页面先明确唯一主要职责：选地区、选任务、组骰池、查看结果、推进日程，不能混成同一个层级。
- 信息、控件和容器必须围绕当前决策组织，而不是把系统里存在的信息都摆出来。
- 玩家界面只显示会改变当前决策的信息；系统知识和默认规则不主动占用界面。

### 1.2 主操作必须是视线终点

- 当前界面的核心功能按钮必须足够大，并放在玩家视线流程的终点。
- 桌面布局里，单步确认 / 进入下一层 / 开始执行这类最关键动作，默认放在右下角；不要藏在面板右上角、标题旁或小尺寸附属按钮里。
- 核心功能按钮的图标 / 箭头必须明显大于普通标签和辅助图标，能一眼指向“下一步”。
- 次级动作如 `下一天`、`返回`、筛选、预览，只能在视觉重量上低于主按钮。

### 1.3 信息按作用域分层

- 全局资源、任务常规属性、特殊约束、操作可行性和解释性文字属于不同层级，不能偷懒做成并列大模块。
- 探索周剩余天数是全局资源，不应伪装成当前任务属性。
- 耗时是行动成本，不是倒计时；红色截稿是特殊约束，不是常规属性。

### 1.4 常规信息和特殊机制分槽

- 耗时、需求、对手骰是常规 meta。
- 红色截稿、深度调查、黑骰、已派遣、日程推进是特殊机制，必须有专属位置。
- 特殊机制如果是当前卡片或页面的视觉主语，就不能降级成普通 chip 或说明句。

### 1.5 可操作性必须一眼可见

- 可点击、不可点击、只读、执行中、已完成不能只靠小字或轻微色差区分。
- 控件长什么样，就应该表达它能不能被操作；可用对象要有主动邀请感，不可用对象要有明确阻断感。
- 只读预览不能复用可操作任务卡语法。

### 1.6 玩家空间记忆不能被破坏

- 玩家会用空间位置记住角色、任务、地区、卡牌。
- 点击、选中、取消、hover 或展开详情，不应让原对象在同一列表里自动换位置。
- 选择状态靠高亮、槽位、详情和队列表达，不靠重排候选池表达。

### 1.7 UI 不能粉饰玩法问题

- 风险、成功率、推荐和达标率必须和真实结算一致。
- 如果真实达标率暴露出适配队伍仍几乎不可能成功，不能只改风险标签或文案；要检查任务需求、目标公式、骰面密度和支援资源。
- 普通任务不能以满编为默认难度；高风险任务也应保持“可搏”，而不是不可玩。

### 1.8 新增强表达时必须清理旧表达

- 加了高权重倒计时块，就不要再保留重复红标签或重复警戒条。
- 整卡已经可点击，就不要再塞重复的小动作按钮。
- 特殊状态进入专属槽后，旧 chip、旧说明、旧按钮要同步下线或降级。
- 删除信息后必须回收空间，不只是让文字消失。

### 1.9 去视觉功能化与简洁拟物

Angus 的 UI 默认不追求“漂亮的功能面板”，而是追求“可点击的编辑部工作物件”。在保证功能清楚、点击区域稳定、文字可读的前提下，应尽量去掉传统软件界面的视觉功能化痕迹，让功能由拟真 / 拟物承载物解释。

- **组织形式**：优先把功能放进玩家能理解的工作物件里，例如黑板、便签、电视、窗、印刷机、地图墙、索引册、剪报、签批文件、印章、档案夹、桌面器具。不要先做三栏后台面板，再给面板加纹理。
- **线条**：线条优先来自物件边缘、纸张压层、屏幕框、黑板框、贴纸边、文件夹边、印刷错位或光影分割。避免层层 `Panel` 描边、等粗细矩形框、调试表格线和把每个模块都完整框起来。
- **纸面中文可读性**：纸质面板、索引卡、选题夹、票据和回条里的正文默认使用常规 / 中等字重的纸面油墨色，不使用大面积粗黑中文。小标题可以用颜色、短标签、压章或字号区分，但不要把整段说明写成粗体公告。截图验收必须裁切到 100% 局部检查，不能只看整屏远景。
- **彩色框与文字安全区**：红条截稿、青条追踪、状态票据、角标和印章必须有独立槽位或足够内边距。色条只做左侧 / 顶部短标签时，文字区要从色条后重新起排；不得让 `!`、`~`、长状态词、倒计时或两位数字贴着彩框边缘，或与边框、章、标题共享同一片未预留空间。
- **行动日志 / 回条安全区**：底部行动日志、回条、已选题、下一步提示这类横向纸签不得用满框高饱和描边承载正文。默认使用窄色签或短色条表达状态，正文限制为 1-2 行短句，文字区至少从色条后 10px 以上重新起排，顶部 / 底部留出可见纸边；超过两行的信息应折叠到详情区或行动日志正文，不在横向纸签里硬塞。
- **线框降噪**：当截图里出现多个等粗硬矩形、编号框、状态章和按钮框并列时，应优先把它们改成纸片压层、索引签、压章、短色条或低透明边缘。若一个索引卡 / 地图 pin / 票据第一眼像后台列表控件、disabled 表单或调试框，即使文字正确，也视为拟物语法未通过。
- **按钮**：按钮必须可点击、可识别，但视觉上应像场景内动作入口：频道切入条、签批区、贴纸标签、印章按钮、文件页脚动作、机器开关。不要把所有可点击项都做成相同的标准矩形按钮。
- **现代纸品按钮必须有体积感**：现代印刷纸品风格不能被误做成全扁平海报。可点击按钮、地图 pin、任务卡、ticker 详情入口、筛选签和主 CTA 必须有独立抬升层、短投影、纸边厚度、内边高光、pressed 下压和 hover / selected / disabled 状态矩阵。体积感应来自纸层、裁切、压印、套印和可按压结构，不来自写实金属、锈蚀螺丝、厚重旧办公器具、旧档案污渍或通用手游 3D bevel。若截图里玩家不能第一眼区分“可点纸品”和“只读纸面 / 装饰纸片”，即使风格更现代，也应判定交互语法未通过。
- **颜色**：颜色服务叙事和状态，不服务控件分类。默认收敛到黑底、米白纸媒、青蓝信息 / 主行动、红色异常 / 截稿 / 危险；金色只做选中、签批或重点。若某个颜色只是在区分控件类型，应优先改成图标、位置、物件形态或文案。
- **信息承载**：重要信息应被物件吸收，例如写在便签、剪报、档案条、电视字幕、签批单字段里；不要让信息漂浮在抽象容器中。若一个界面看起来像后台列表、KPI 仪表盘或数据配置页，即使功能正确，也应视为包装未完成。
- **清爽感来源**：清爽不是只减少元素，而是让主视觉承担大部分题材表达，让控件退后。每屏只保留一个主视觉承载物和一个主动作路径，其他状态以标签、章、贴纸、短字段辅助。
- **拟物不等于纯复古**：Angus 已确认的好方向是“职业物件 + 现代图形设计”的混合，而不是单纯旧报纸、旧地图、旧办公室。美术资源和 UI 覆盖层应保留青蓝 / 红色高对比、斜切多边形、套印错位、半调网点、像素边缘、干净按钮和清晰负空间，让界面既像编辑部物件，又有现代游戏 UI 的设计感。
- **现代感来自品牌主场，不来自纸张堆叠**：当参考图显得更现代，而新稿显得老旧时，优先检查深海军蓝是否仍是画面主场、红橙 / 青色是否只承担高能状态、米白纸面是否只作为真实工作物件。若米黄纸面大面积铺满、红色变成旧表格标题条、青色变成后台分区描边、等粗矩形框和字段行主导画面，即使有夹子、票据、印章和纸纹，也应判定为滑向旧档案 / 后台表单。正确做法是强化主物件、冷深蓝负空间、结构化半调 / 套印 / 像素边缘，并让纸面、票据和卡片各自承担明确职业动作。
- **周刊内图不能走正剧摄影，也不能堆细节**：报道重组、周刊样张、杂志母稿里的“报道图”应接上已确认的 Q 版黑色幽默角色气质，而不是写实庄重的法院、军舰、历史新闻摄影。优先使用“概括像素异常符号图”：一个低细节场景剪影、一个中央异常符号、一个红 / 青几何侵入、少量半调和像素颗粒。Q 版主编 / 编辑更适合作为角落反应贴纸、批注图标或荒诞注脚，不应每次占据主图主体。真实场景只能保留为剪影或低细节底图，不允许变成照片质感主体。避免密集证据墙、复杂拼贴、高细节插画和满屏小物件。
- **发刊前报道板必须是像素美式周刊物件，不是玻璃后台**：报道重组 / 发刊前报道板的控件应读成打开的厚纸杂志、稿件夹、剪报、签批纸、状态章和印刷机开关。禁用或强降级半透明玻璃面板、`backdrop-filter`、柔软渐变按钮、写实软阴影、圆角胶囊 chip、现代 KPI 卡、发光描边和写实材质按钮。候选卡应像米白稿件 / 剪报，版位槽应像纸面裁切框，右侧确认应像主编签批夹，送印主动作应像粗像素印刷机按钮或章，而不是 SaaS CTA。
- **发刊前签批纸不能压成表格控件**：送印是不可逆动作，右侧签批纸必须先让玩家确认“签哪一期、签什么头版、传播预估多少、是否有公开冲突、是否可送印”。动态字段应使用签批语言和纸面字段，例如“本期头版定稿 / 预计扩散 / 公开冲突 / 批注”，不要把核心确认压成多行后台表格，也不要让三枚以上状态章、重复不可撤提示或强表格线抢走头版定稿的视觉权重。
- **纸纹不能穿过动态文字**：纸张横线、半调颗粒、污点、折痕和装订线只能作为字段外的材质层或极低权重背景。标题、数值、批注、按钮文案和可点击标签必须放在干净底托或足够安静的安全区上；若玩家截图里看起来像文字被划线、压纹、污点或底图线条穿过，应判定可读性未通过。
- **报道重组风格稿只能指导保守物件化，不能整页吞掉交互**：若用生图风格稿推进报道重组 / 发刊前报道板，采纳方向是“暗色编辑桌、暖光、稿件夹、打开厚纸杂志、签批夹、红笔 / 印章 / 印刷机按钮、一度异常”，不是把整张 UI 画成一张位图。位图只承担桌面材质、空白杂志、纸张厚度、书脊、中缝、签批夹、稿件卡底、印章框、半调颗粒和无文字主图；报道标题、期号、版位名、计数、预计扩散、公开冲突、按钮文案、拖拽槽、hover / drag-over / disabled / 二次确认必须继续由 DOM / Godot UI 承担。异常表现只允许作为一处低频预兆，例如主图边缘错印、异常漏墨或红青套印偏移，不得变成全屏故障、额外仪表盘或遮挡排版判断的视觉噪音。
- **必须对照已认可标杆截图**：当用户明确说某个界面应接上“前两个界面”或某张概念图时，返工前必须逐项对照标杆的主承载物、灯光、材质、物件密度、现代几何层和主动作入口。不能只继承颜色、切角和深色背景；如果最终仍像后台三栏、KPI 面板或配置表，即使清爽也视为风格未通过。
- **包装不能阉割功能**：视觉返工只能压缩、重组或物件化表达，不能删除会影响当前决策的信息。若旧版已经提供地区锁定、解锁缺口、可见任务、截稿、追踪、行动日志、宏观状态等功能，新的拟物版本必须以更合适的槽位恢复这些信息；不能为了截图清爽把玩家判断所需的信息拿掉。

### 1.10 资产化 UI 必须先定义视觉可使用区域

拟物 / 资产化 UI 落地时，不能把 Godot / DOM 控件矩形直接当作可排版区域。PNG 里的书签、折角、螺丝、铆钉、箭头、斜纹、色块、强半调、纸边、夹子和装订结构都是视觉物理结构；它们可能仍在控件矩形内，但属于动态文字禁入区。

大角度斜透视、扑克牌式斜纸片、摄影感烘焙图和上下宽度不一致的梯形纸面，默认不得承载任务标题、长正文、倒计时、CTA 等核心动态 UI。若必须使用斜桌面或斜纸张，它只能作为背景 / 氛围 / 低权重装饰；核心内容必须放在近正交、矩形、可测量的 `content_rects` 上，或改为分层资产（底板、干净纸面、装饰覆盖层、CTA plate、安全区 mask）。

若已发现资产没有可写区，不能用一整块普通矩形面板或半透明网页卡片直接盖在美术图上“修安全区”。这会把资产化 UI 退回后台面板贴图。正确做法是回到资产分层：重出空白纸面、纸边、夹具、阴影、CTA plate 和状态章，或临时回退到低装饰、低拟物的正交功能布局；不要在高完成度底图上叠几套互不相干的临时控件。

地图 / 区域板上的任务节点必须使用一套统一的节点语法。常态地图不应常驻多个大白框、空标签、便利贴、黄色提示框和青色状态框；这些会被读成“奇怪方块”或调试占位。默认只显示图钉 / 锚点 / 短编号，选中或 hover 时才出现一个短任务签；完整任务名、需求、耗时、风险应回到左侧任务卡或右侧确认单。

顶部 HUD / 功能条不得为了展示标题、宏观数值、返回按钮和频道路径而压缩主舞台。地区任务台、世界地图、发刊前工作台等主物件页面应优先保证主背景 / 主资产以正确比例和足够高度呈现；全局状态默认压成一行低权重状态带或角标组。若 HUD 高度导致主资产被等比压扁、裁切或失去风格稿比例，应判定布局未通过。

风格稿不能直接进入“整屏生图 -> 叠动态 UI”的流程。资产化 UI 的正式链路必须是：先冻结页面职责、功能分区、信息容量、最长文案和状态矩阵；再据此推导组件尺寸、`content_rects`、`no_text_rects`、`hit_rects`、九宫格边界和动态字段；然后才用这些约束写风格稿 / 组件 prompt。风格稿只确认美术语言与主物件，不能反向决定字段数量和框体容量。地图底图、纸纹、夹具、半调和无文字装饰可以烘焙；地点标签、任务名、状态、按钮文案、标题、筛选、倒计时和所有会随数据变化的信息不得烘焙进底图。

无字风格稿确认后，允许额外生成一张“有字效果预览稿 / filled-state text mock”，用真实 UI 文案和代表性真实头像 / 角色数据检查字体气质、头像裁切、信息密度、图文融合、CTA 可读性和商业截图效果。该图只作为目标截图和动态层参考，不得切组件、不得进入 manifest、不得作为 Godot / HTML 运行时底图；正式资产仍必须回到无字组件、头像槽、状态 atlas、`content_rects / no_text_rects` 和动态文字 / 动态头像渲染。若只是用程序把文字或头像叠到既有底图上，只能作为安全区 / 容量验证稿；用于视觉评审的效果图必须图文一体重绘或同等精修，不能像开发期 Label 贴在 bitmap 上。

所有可交互对象必须从底图中拆出来。按钮、地图 pin、任务卡、筛选签、返回签、开关、hover tooltip、可拖拽槽、可选/不可选卡片等，只要需要点击、hover、pressed、disabled、selected、focus、drag-over、locked、completed 或 loading 反馈，就不能只烘焙在背景图里；它们必须拥有独立资产、状态贴图或等价的状态层，并在 manifest 中写明热区、锚点、状态名和文字安全区。

后续任何世界地图、区域地图、签批夹、票据、回条、按钮、索引册、稿件卡等资产化 UI，必须先做以下分析，再接入动态文字和交互：

1. **资产外框**：明确组件实际显示矩形、九宫格拉伸边界和不会被裁切的外框。
2. **禁入区 `no_text_rects`**：标出书签、折角、螺丝、箭头、色条主体、边框、强纹理和装饰凸起。
3. **真实颜色模块 `visible_color_module_rects`**：先标出图像里真实存在的深色条、浅色标签、按钮内板、票据色块、状态章槽和标题底条。动态文字必须落在这些可见模块里，不能只落在自画的理想 safe-zone 里。
4. **承载区 `carrier_rects`**：从真实颜色模块推导每个字段的功能承载面，并声明 role，例如 `receipt_field_lane`、`header_title_lane`、`button_label_plate`、`card_title_plate`。不同 role 不得共用一个万能文本框。
5. **可写区 `content_rects / inner_rects`**：标出标题、正文、计数、状态、CTA 文案、ticker 文案各自的安全槽；它们必须是 carrier 的内缩结果，而不是独立手画区域。
6. **最长文案**：用当前语言最长区域名、最长按钮文案、两位数计数、锁定缺口和禁用态验收，不只看默认短文案。
7. **状态矩阵**：至少检查空态、默认态、锁定态、hover / pressed / selected / disabled / focus；按钮换状态贴图后文字必须仍在同一安全区内。
8. **交互热区**：标出点击热区、hover 扩展区、tooltip 锚点、手柄/拖拽区和不可点击装饰区；热区不能依赖底图里不可分离的视觉按钮。
9. **反馈契约**：写明点击后是按下凹陷、印章压下、纸签位移、灯条点亮、还是音效/震动/短动效；交互反馈必须能被截图或录屏验证，不能只存在于代码事件里。

验收时必须区分两种通过：

- **控件通过**：Control / DOM rect 没超父容器，只说明程序布局没炸。
- **视觉通过**：文字 rect 没碰 `no_text_rects`，且在 100% 局部裁切下看起来稳稳写在可用纸面 / 按钮 / 票据上。

只有第二种才算资产化 UI 通过。若文字看起来贴边、压装饰、被半调/纸纹穿过、贴近按钮下沿、或像硬塞进贴图，即使控件测试通过，也必须返工。

对拟物 / 生图 UI，新增一条更高优先级的文字落地判断：**文字必须先属于真实颜色模块，再属于 safe-zone。** 如果文字视觉上没有在深色条、浅色标签、按钮内板、票据色块或标题底条内居中，而是偏到模块上缘、下缘、模块外或另一个颜色区，即使 `inner_rect`、字体尺寸和 overlay 指标显示通过，也按 `module_match` 失败处理。先修模块识别和 carrier，再修字号、字重、行高和文字内容。

UI Designer 出稿时必须给拟物组件附“文字安全区表”；UX 老哥评审时必须检查视觉可使用区域；父级 Codex 落地时必须把关键安全区变成测试或截图 overlay；美术指导审资源时必须判断资产是否留出足够干净的动态文字区。

### 1.11 资产化 UI 正式质量门槛：图文功能必须融合

`content_rects`、`dynamic_text_rects`、`forbidden_zones` 和 safe-zone overlay 只能证明动态层没有压到明显禁入区，不能证明正式 UI 已经成立。资产化 UI 还必须让文字、状态和操作像同一个游戏物件系统的一部分，而不是在高质量 bitmap 上贴开发期 Label。

后续世界地图、地区任务台、派遣签批台、发刊前报道板等资产化 UI，进入正式候选前必须额外通过以下检查：

1. **字体系统**：至少定义标题、当前对象标题、正文、状态 / meta、CTA 文案和数字的 token。中文正文默认保持现代清晰，不把所有文字做成粗黑或低清像素字；像素感主要来自边缘、图形、半调、套印和局部状态符号。
2. **文字归属**：每个动态文字槽必须声明 `content_role`，例如 `region_title`、`status_badge`、`route_summary`、`cta_label`、`ticker_broadcast`。验收时检查文字是否像写在纸面、票据、档案字段、频道字幕或签批区里，而不是浮在底图上。
3. **状态语法**：`normal / hover / selected / locked / urgent / completed / disabled / loading` 等状态必须在同一套物件语言中联动。不能只让一个角标变色，也不能让 pin、卡片、右详情和 CTA 各自像不同素材包。
4. **当前对象链路**：地图选择类页面必须让当前选中对象在“列表 / 地图 / 详情 / 主 CTA”之间形成同色、同形或同章签的联动链路。玩家不应靠重复读四处文字来确认系统选中的是谁。
5. **主 CTA 物件动作**：主按钮必须像场景里的职业动作入口，例如签批、送印、频道切入、派遣控制台或印章压下。只把大字居中放在漂亮底板上不算通过。
6. **信息职责收敛**：同一事实只能有一个主承载位。红线、青线、可进入、锁定缺口、剩余天数等信息如果在地图、左卡、右详情和 ticker 多处重复出现，必须明确哪个是主语义、哪个是低权重回执。
7. **局部完成度截图**：除整屏截图和 safe-zone 图外，必须提供左卡、地图 pin、右详情、CTA、ticker 的 100% 局部截图；局部看起来像临时贴字、系统默认字体或旧控件混层时，整屏再漂亮也不得通过。
8. **单状态优先验证**：新资产方向先用一个真实状态验证，例如“北美禁区带 selected + 红线升温 + 可进入”。这一状态通过后再扩全局、多地区和全状态矩阵；不要用满屏内容掩盖字体和物件语法未成立。
9. **目标载体一致性**：运行截图必须和本轮要验收的目标界面属于同一个页面职责、同一套功能分区、同一条玩家操作链。若只是把 P0 逻辑塞进旧承载页或开发态三栏框架，只能标为“逻辑烟测截图”，不能标为“资产化 UI 落地截图”。
10. **目标锚点回看**：交付前必须把本轮目标风格稿 / filled-state mock / 用户认可截图与真实运行截图并排检查。至少确认主物件、左中右职责、候选区、当前选择区、复核区、主 CTA、信息密度和视觉语言没有漂移成另一个界面。

若以上检查未通过，界面最多称为“风格验证稿 / 组件验证稿 / 功能原型”，不得称为正式 UI、生产标杆或 live replacement。

## 2. UI 改动前审计

### 2.1 工作合约

每次动手前，先在心里或回复中明确三件事：

- **保留**：用户已经认可的结构、位置、交互、视觉重点是什么；
- **修改**：这次只解决哪个具体问题；
- **不做**：哪些相邻问题暂不扩展，避免把局部修正变成整体重构。

默认原则：

- 用户指出“某个元素不明确”时，第一轮只改该元素的文本、图标、提示或状态表达。
- 不要因为一个标签不清楚，就重排整张卡片。
- 不要把用户认可的亮点丢掉，例如右侧大倒计时块、规整深度链叠层、熟悉的 HTML 原型壳层。

### 2.2 改动前 10 问

任何 UI 改动前，先快速过一遍：

1. 这个页面的唯一主要任务是什么？
2. 玩家完成判断后，下一步应该点哪里？
3. 这个主按钮是否足够大、足够靠近流程终点？
4. 页面里哪些东西能点，哪些只是看？
5. 有没有只读信息长得像按钮？
6. 有没有系统动作混进任务 / 选择容器？
7. 有没有特殊机制被塞进普通标签流？
8. 有没有关键数值被低权重文案淹没？
9. 点击、选中、取消后对象位置是否稳定？
10. 新增 UI 后，有没有旧按钮、旧标签、旧说明变成冗余？

## 3. 信息层级与视觉主语

### 3.1 玩家信息过滤规则

玩家界面只显示会改变当前决策的信息。

应显示：

- 耗时、成本、人数限制；
- 需求属性 / 需求骰面；
- 对手骰、黑骰、危险后果；
- 倒计时、截止、即将消失；
- 当前可用操作；
- 当前任务链阶段和下一步可见信息；
- 角色与当前任务的适配结论、相关骰面、明显缺口。

不应显示：

- 内部任务类型说明，例如“白色调查”“红色截稿”这类开发分类；
- 默认规则说明，例如普通任务“可反复追踪”“失败保留”；
- 已由另一个 UI 元素表达过的重复说明；
- 含义不明确的标签，例如没有明确玩法后果的“高压”；
- 为了解释系统而写的说明句，除非玩家必须凭它做选择。

### 3.2 一语义一位置

同一语义只保留一处表达。

处理任何 UI 前先做“信息归属”判断：当前决策事实是什么、哪个位置是主承载位、其它位置是否真的改变职责。合法的二次出现只能承担摘要、引用、对比、解释、阻断或反馈之一；如果只是用相近文案、相近权重、相近粒度再说一遍，就必须删除或降级。不要为了保留重复信息再新增解释。

示例：

- 右侧倒计时已经写“剩余 2天”，就不要再写“过期消失”。
- 线索卡已有“调查 -> 新任务”示意，就不要再写“可能发现新任务”。
- 危险已经有“危险”标签，就不要再放孤立感叹号。

### 3.3 信息层级不能用并列模块偷懒

不要把不同性质、不同作用域、不同触发条件的信息做成同一排同等重量的卡片或按钮。并列布局会暗示这些信息同级、同类、同等重要；如果事实不是这样，就会误导玩家。

设计任何信息组前先判断每项信息属于哪一层：

- **全局资源**：例如探索周剩余天数、资金、宏观指标。应放在全局状态区，不伪装成当前任务属性。
- **任务常规属性**：例如耗时、基础需求、主要奖励 / 风险摘要。用轻量 meta 或任务头部表达，不为低频字段单独开大模块。
- **特殊约束**：例如红色截稿截止、突发任务关闭条件、黑骰介入、危险后果。只在条件成立时用警戒条、状态徽章或局部提示表达，不能和普通属性并列成常规字段。
- **操作可行性**：例如能否开始、还缺什么、谁被占用。应靠近主操作和需求覆盖面板。
- **解释性文字**：只在玩家必须凭它做选择时出现；能由结构、标签、按钮或反馈表达的，不另写说明。

宏观五维属于全局世界状态，不是当前页面的主操作对象。`公信 / 诡名 / 声望 / 守序 / 狂性` 默认压缩为边缘化状态徽记、舆论仪表、警戒灯组或微型进度条；除非当前页面专门要求玩家调节宏观属性，否则不要做成五张等宽大卡、五个大面板或五个同级按钮。地图、编辑桌、来信墙、刊物头版等页面主视觉已经成立时，五维只负责提供世界气氛和长期倾向提示，不能抢走主视觉面积。

典型反例：派遣页把 `耗时 2天`、`剩余 7天`、`截止 3天`、`需求 探索5 / 生存3` 做成四个并列大框。这里“剩余”是全局资源，“截止”是红色任务特殊约束，“耗时”只是执行成本，“需求”才是本页配骰决策核心。正确做法是把全局剩余移回全局状态，耗时压成轻量 meta 或按钮文案，截止做成红色截稿警戒提示，需求与需求覆盖面板形成主线。

删掉重复信息后，必须重新指定“视觉主语”。不要只把重复标签合并成一句低权重说明；若该信息是玩家当前最该看的数值，例如截稿剩余天数，就要给它独立且明确的视觉承载。信息去重的目标是让关键值更突出，不是让关键值变成说明句的一部分。

同形控件不等于同语义。把多个数值做成同一行、同一组卡片或同一种进度条前，必须先能说清它们共同回答的是同一个玩家问题，且拥有同一对象、同一口径和同一判断结果。若一个数值是总结果 / 达标目标，另一个数值是组成来源 / 属性拆解，两者应做成父子结构，而不是同排同权重。典型反例：在角色骰判定中把 `有效点` 和 `理性 / 洞察` 做成三个同级进度条；`有效点` 回答“本次判定是否过线”，属性条回答“哪些属性贡献了有效点”，它们不是同一类信息。

### 3.4 常规标识和特殊机制必须分槽

常规信息放在常规槽位，特殊机制放在特殊槽位。不要把“耗时 / 需求 / 对手骰”这类每张任务卡都可能出现的普通 meta，和“红色截稿倒计时 / 深度调查当前环 / 黑骰终局 / 已派遣占用”这类会改变玩家理解的例外状态混在同一排标签里。

硬规则：

- 常规槽位只承载常规字段：标题、耗时、需求、对手骰、危险等压力信息。
- 特殊槽位承载例外机制：右侧倒计时块、右侧当前环标识、标题旁状态标记、主操作附近的可执行性提示。
- 特殊机制如果是当前卡片的视觉主语，就必须有高权重专属承载；不要把它降级成普通 chip，也不要和多个普通标签并列。
- 同一种特殊机制在同一类界面中必须固定位置。例如红色截稿用右侧倒计时，深度调查用右侧“深度调查 / 当前任务 N”，已派遣靠近任务名或头像组。
- 选择特殊槽位前先问：这个信息是默认规则，还是少数任务才有的例外？默认规则不显示；例外机制用专属语法显示。

### 3.5 视觉重量

- 高频普通信息用轻量标签。
- 强时效、强危险、当前操作状态可以使用更高权重组件。
- 不要把普通信息做成像按钮的大块。
- 不要让辅助信息抢过标题、倒计时和操作按钮。

## 4. 控件语义与状态距离

### 4.1 标识必须绑定本界面的真实对象

图标、标签、徽章、图例、颜色摘要、数字角标都属于“标识”。标识不是装饰，必须回答：它在这个界面里标记了哪个真实可见对象，表达了哪个当前状态，玩家能否凭它做本界面的决策。

新增任何标识前必须检查：

- **对象是否在本界面可见**：标识必须贴近或解释当前界面里的对象，例如地图点、任务卡、角色、按钮、区域详情；不能借用另一个面板或下一层页面里的对象。
- **状态是否在本界面成立**：当前选中、锁定、已派遣、剩余时间、危险、黑骰、深度链等状态，只能出现在真正承载该状态的界面层。
- **编码是否有对应视觉**：图例只能解释同一层里真实出现的颜色、图形、点形、线型或角标；没有对应编码时不放图例。
- **是否影响当前决策**：如果标识只是在说明系统知识，不能帮助玩家在当前界面选择、进入、派遣、排序或判断风险，就不要显示。

常见分层：

- 地图层：只显示地图点、区域锁定 / 当前选中 / 地图点已有的事件数或状态。
- 详情层：显示选中对象的摘要，例如可见目标、限时机会、线索、深度链。
- 任务卡层：显示该任务自己的耗时、倒计时、需求、风险、链条下一步与操作。
- 派遣层：显示当前队伍、骰池、缺口、风险和可执行性。

同一个词在不同界面出现时，必须语义一致；如果只是聚合摘要，应明确放在摘要面板里，不能伪装成地图或任务卡图例。

状态标识必须贴近被状态化的对象。`已派遣`、`已完成`、`待结算`、`占用中`不是任务类型，也不是危险 / 对手骰这类任务压力，不应混进任务类型或机制标签行。若状态表达的是“谁正在占用这个任务”，地图点优先用角色小头像组，任务列表优先在任务名称旁放状态标记；微型文字角标只能作为辅助，不应承担主要识别。

### 4.2 只读预览不能复用可操作卡片语法

同一套视觉语法会让玩家推断同一套操作。若当前页面的真实任务是“先选择地区 / 对象，再进入下一层”，右侧预览区不能复用下一层的任务卡、主操作按钮、hover 高亮或 `interactive` 类；否则玩家会自然先去点预览条目。

硬规则：

- 可点击对象必须比只读预览更像按钮：有明确选中态、hover 反馈和主操作承接。
- 只读预览最多展示少量摘要行，默认 2 到 3 条；不要纵向铺成完整任务列表。
- 只读预览不放任务操作按钮，不使用任务卡的强边框、倒计时块、可派遣按钮或展开交互。
- 若预览内容来自下一层页面，必须用摘要语法，例如“地区情报概况 / 进入地区后选择具体任务”，而不是直接复刻下一层任务卡。
- 验收时检查预览容器内不应存在 `button`、`a`、`role=button` 或项目内表示可交互的类名，除非该预览本身就是当前页面的真实操作对象。

### 4.3 父级选择器与从属详情不能同级化

带有“选择对象 -> 查看对象信息 -> 确认进入 / 执行”的界面，必须先区分控制器和输出结果。选择器是玩家正在操作的父级控件；详情、数值、预览和说明是当前选中对象的从属信息。两者不能做成同一重量、同一边框、同一 hover 语言的并列卡片组。

硬规则：

- 父级选择器可以像按钮：允许明确选中态、hover 反馈、焦点边框和点击手势。
- 从属详情必须像属性面板或只读内容：降低边框和背景权重，不使用按钮式 hover，不出现 `cursor: pointer`，不与选择器共享强交互类。
- 如果某块信息会随选中对象改变，它应通过标题、缩进、分组标题、连接关系或内嵌位置表达“这是当前选中对象的详情”，而不是另一个可选项集合。
- 摘要数值、只读情报、风险说明和进度信息不得拥有和父级选择卡相同的卡片视觉重量；需要时可改为表格、属性行、轻量列表、分隔线内信息或折叠在选中对象下方。
- 不能只把从属详情“稍微降权”后仍保留卡片语法。可点击选择区和从属详情应使用不同控件语言：选择区像按钮组，有箭头、选中态、hover 和明确指向；详情区像注释 / 属性表 / 普通列表，用缩进、细线、轻量文字和透明背景表达附属关系。
- 设计验收时必须标出当前界面的四类角色：控制器、当前选中对象、从属详情、主操作。四者若看起来同级或同样可点，就必须重排层级。

### 4.4 可用与不可用状态必须拉开行动距离

可点击 / 可进入 / 可执行不是普通状态色差，而是玩家下一步行动的许可信号。不可用对象如果仍保留同等按钮边框、箭头、发光、饱和颜色或 hover 手感，玩家会把它理解为“也能点，只是状态不同”。可用对象必须有主动邀请感，不可用对象必须有明确阻断感和原因。

硬规则：

- 可用对象使用主动按钮语法：更高对比度、更饱和的主色、明确箭头 / 进入图标、hover 抬升、可聚焦边框和可点击光泽。
- 不可用对象使用锁定 / 幽影语法：降低不透明度与饱和度、去掉主箭头或换成锁 / 缺口图标、禁用 hover 抬升、弱化边框，并显示明确原因，例如 `未解锁 · 82%`、`缺口 18%`。
- 同一组里，不能只靠一行小字区分可用与不可用；形状、图标、对比度、hover、光效和文案至少三项同时拉开。
- 地图点、地区按钮、任务卡、道具、角色和主操作按钮都适用。只要某项当前不能执行，就不能保留和可执行项相同的按钮邀请感。

### 4.5 执行中对象应从主操作流下沉为队列

当一个对象已经被派遣、提交、锁定、等待结算或正在执行时，它不再属于当前主操作候选。此时不能只在原卡片上加 `已派遣` / `执行中` / `待结算` 小标识后继续留在可点击列表里；玩家会按原列表语法误以为它仍可作为下一步行动。

硬规则：

- 主列表只放当前可执行 / 可派遣 / 可选择的对象，保持最强按钮感、hover 和整卡点击。
- 已执行对象统一下沉到次级区块，例如 `已派遣 · 执行中`、`执行中队列`、`待结算`；这个区块应有弱框体或收纳语法，和主列表拉开层级。
- 不要默认使用 `等待回收` 这类会暗示玩家应该撤回外派的文案；正常派遣状态优先表达“谁在执行、几天后结算”。
- 已执行对象卡片应降低饱和度、去掉主按钮感和 hover 抬升，默认只读；如果需要查看详情，入口必须弱于主操作，不能和派遣 / 进入等主动作同权重。
- 次级队列里优先显示“谁在执行、还剩几天、何时回收 / 结算”，而不是继续强调任务需求、可派遣压力或主操作文案。
- 地图点可以保留头像组等占用状态，但右侧任务列表必须通过布局分区承担主要区分；不能只靠地图或标题旁小标识解决误点问题。

### 4.6 可识别对象的空间位置必须稳定

玩家会用空间位置记住对象。候选角色、道具、任务、地区、卡牌等列表 / 网格，一旦玩家开始比较和选择，点击、选中、取消、hover、展开详情、容量替换等状态变化都不应让原对象在同一列表里自动换位置。

硬规则：

- 选择状态只改变高亮、勾选、槽位摘要、按钮文案或详情预览，不参与候选列表排序。
- “按贡献 / 相关度 / 推荐度排序”应在进入页面、切换任务或玩家显式切换排序模式时确定；点击某个候选项后不得因为它已选中而移到前面。
- 若需要展示已选对象顺序，应使用单独的已选槽 / 本次骰池 / 队列区，而不是重排候选池本身。
- 排序比较必须有稳定兜底，例如角色基础顺序、创建时间或固定 id，避免同分对象在重渲染后漂移。
- 容量上限不能触发隐式替换。若已选人数 / 道具 / 卡槽达到上限，继续点击新候选时必须提示“已达上限，请先手动撤下一个已选对象”，并保持当前选择不变。不要用 `shift()`、自动撤下最早选择、替换最低贡献对象等方式替玩家决策。
- 悬停预览也要尊重容量上限：已满时只提示无法加入和解除方式，不模拟“自动替换后”的覆盖率、风险或收益。
- 悬停预览不能改变候选列表、卡片网格或鼠标命中区的位置。若预览内容会从一句话扩展成详情面板，预览容器必须按详情态预留高度；鼠标移出单张卡时不要立刻缩回导致布局跳动；连续划过卡片时应有短延迟或保留上一次预览，避免 `mouseenter` / `mouseleave` 循环触发闪动。

### 4.7 操作按钮

- 同一列表中的主要操作按钮应对齐。
- 固定宽度时必须保证文字不换行。
- 移动端触觉热区必须同时满足两套常用标准：iOS HIG 最小 `44×44px`，Material Design 最小 `48×48dp`。做移动端或触屏原型时，不要只按其中一套回答或验收。
- 按钮文字应是动作：`派遣`、`抢派`、`继续调查`、`进入任务`。
- 行动按钮文案必须描述玩家要执行的中性动作，而不是系统预测的负面结果。不要把 `失败`、`惩罚`、`损伤`、`未达标` 这类结果词直接写进主按钮，例如不要写 `提交失败判定`；按钮应写 `提交判定`，当前会成功、未达标或产生代价放在状态区、结果预览或确认弹窗里说明。例外只限真正危险、不可逆且需要玩家确认的操作，例如 `删除存档`、`放弃任务`。
- 层级返回按钮不是普通标签。`返回区域`、`返回世界探索层`、`返回回合简报` 这类会把玩家带回上一层工作台的按钮，应有稳定的最小点击面积和清晰边框 / hover，不要缩成小型次级胶囊；它们可以低于当前页主动作，但不能低到难以发现。
- 放大返回按钮时优先调整按钮自身的 `min-width`、`min-height`、padding、字体和边框，不为了它重排页面容器、候选列表或主流程按钮位置。交付前要顺手检查同类返回按钮是否一致，避免只修截图里被指出的一处。
- 已派遣、执行中、待结算等状态不应继续显示派遣类主动作按钮，也不应继续保留和可派遣卡片同等的整卡点击强度；应按 §4.5 下沉为队列或只读状态。
- 如果一张卡片只有一个主动作，且整张卡片已经承担点击进入 / 打开 / 派遣配置的交互，就不要再在卡片内部放重复的小按钮。整卡点击和内嵌按钮二选一，避免双入口抢空间、误导权重或挤压倒计时 / 当前任务等特殊状态槽位。
- 内嵌按钮只在以下情况保留：同一卡片有多个动作需要区分；动作不可逆或需要确认；玩家需要在卡片内锁定 / 重投 / 提交；或者整卡点击语义不成立。

### 4.8 角标与徽章必须有安全槽位

数字角标、进度徽章、状态徽章、头像叠层等小元素，只要贴在按钮、地图点、卡片标题或操作区上，就必须有自己的布局槽位或明确预留安全区。不要用 `position:absolute` 直接压在右上角后只靠肉眼调偏移；如果元素可能变成两位数、百分比、长状态词或多头像，默认会遮挡文字。

硬规则：

- 角标表达的信息必须绑定当前对象，遵守 §4.1；不能为了装饰而贴角标。
- 角标和主文字不能共享同一片未预留空间；优先使用 flex / grid 的独立槽位，其次才是带足 `padding` 的绝对定位。
- 角标、徽章、头像组与主标题 / 按钮文字 / 倒计时 / 操作按钮之间必须有可读安全区，不只是不相交。
- 截图验收时，必须检查 `getBoundingClientRect()`：主文字矩形、角标矩形、操作按钮矩形不得重叠；地图点和任务卡这类高密度界面尤其要做自动断言。
- 状态数量可能变化时，必须测试边界文本，例如 `9+`、`80%`、`100%`、`剩余 10天`、多人头像组。

### 4.9 即时反馈必须贴近触发对象

玩家点击某个对象后，系统反馈必须出现在该对象附近，或出现在同一组件的固定反馈槽里。不能把局部对象的失败原因、未解锁原因、不可用原因丢到页面右上角、日志区或远离视线焦点的全局 toast 里；那只证明系统有消息，不证明玩家能看见。

硬规则：

- 对象级反馈应锚定触发对象：地图点、任务环、卡片、角色、道具、按钮的失败 / 未解锁 / 不可用提示，应出现在对象旁边或对象内部。
- 全局 toast 只适合全局结果：保存成功、报刊替换、阶段切换、后台结算等不依赖具体局部对象的位置反馈。
- 如果触发对象和提示之间跨越大半个屏幕，视为未通过验收；截图时必须按玩家真实视口检查反馈是否在第一眼可见范围内。
- 自动验收不能只查文案存在，还要检查提示框与触发对象的距离、是否在同一滚动容器内、是否被裁切或遮挡。

## 5. 任务卡槽位规则

任务卡是当前最容易出错的 UI，必须固定功能槽位。

### 5.1 标准槽位

- 左侧：任务类型图标。
- 标题行：任务名。
- 标题右侧：只放状态、强时效倒计时或特殊入口标识，不放普通耗时。例如“已派遣”应在任务名右侧，而不是混入耗时 / 危险 / 对手骰标签行。
- 标题下方第一标签：耗时，格式为 `耗时 2天`。
- 同一标签行：对手骰、危险、黑骰等压力信息。
- 需求行：探索 / 生存 / 理性等任务需求。
- 右下角：主要操作按钮。

同一类功能标识必须固定在同一信息槽，不得随任务类型漂移。

### 5.2 耗时

- 统一写成 `耗时 N天`，不要只写 `2天`。
- 同一界面内必须固定位置，当前任务卡规范为“标题下方第一枚标签”。
- 耗时是派遣成本，不是倒计时，不要和剩余时间共用槽位。

### 5.3 截稿 / 突发任务

- 截稿任务的重点是“剩余时间”，应使用更高视觉重量。
- 当前任务卡可使用右侧大块倒计时：`剩余 2天`。
- 地图点可写 `剩2天`，避免被理解成耗时。
- 不额外写“临时”“过期消失”，倒计时本身已经说明会消失。
- 在派遣配置页，红色截稿只需要一个主视觉承载：高权重倒计时块，例如 `截稿关闭 / 剩余 3天`。不要同时再放“红色截稿”标签和红色警戒条；后果说明应降级为一行文字，例如“成功或失败后都会结束；失败可能造成队员状态损伤”。

### 5.4 普通任务

- 不显示“普通 / 白色调查 / 可反复追踪 / 失败保留”等默认规则。
- 只显示当前决策需要的耗时、需求、对手骰、操作按钮。

### 5.5 线索

- 线索不是任务，应通过“调查 -> 新任务”这类图形关系表达。
- 不重复写“可能发现新任务”。
- 如果线索需要派人调查，应显示耗时、需求和行动按钮。

### 5.6 深度链任务

- 不在一开始显示 `1/4` 这类总阶段数，除非玩家已经知道总长度。
- 默认只显示当前可做的一环。
- 不使用 `下一页` 这类 UI 翻页语言，也不把后续提示混进普通标签行。
- 区域任务卡中，深度调查应使用右侧专属块显示 `深度调查 / 当前任务 N`；这代表“当前可做的一环”，不透露总长度。
- 已完成的深度链旧环不能继续留在区域任务列表主流里。完成一环后，旧环应退出当前可派遣列表，只保留最新可做的一环；如果需要回顾旧环，另做日志 / 已完成记录，不用和当前任务同样的紫色任务卡语法。
- 若要暗示后续存在，只用不剧透长度的调查语义，例如 `线索未尽`、`仍有下文`、`前序线索`；不要显示 `1/4`、`下一页：?` 或完整后续关卡数。
- 地图上用规整叠层表达“当前入口 + 潜在链”，不要一次摊开整条链。

### 5.7 危险、黑骰、对手骰

- 危险是难度 / 后果标识，不是任务类型。
- 高危任务可以合并进普通任务，用危险标识表达例外。
- 黑骰应有独立图形语言，和危险分开。
- 对手骰必须带文字读法，例如 `对手骰 3`，不要只给一个孤立数字。
- 不使用含义不明的“高压”标签；若要保留，必须改成明确规则词。

## 6. 地图与区域界面规则

### 6.1 地图语义

- 地图类界面必须有可识别空间语义：世界地图、区域轮廓、经纬网、航线、地形或城市结构。
- 不要用抽象圆斑、彩色光区替代地图。
- 若只是临时占位，也要让玩家看出“这是地图”。
- 地图上的图例 / 标识必须遵守 §4.1：只能解释地图层真实可见的状态。不要把右侧详情面板里的任务分类摘要搬到地图上；如果限时、深度链只在右侧卡片里表达，地图图例就不能出现对应标识。
- 全球 / 上层地图页若承担的是“选择地区 / 进入地区”，默认不把 `下一天`、结算、结束探索这类时间推进动作做成右下角主按钮；主按钮仍优先服务 `进入选定地区`。若世界地图确需承载 `下一天 / 推进一天`，必须复用地区任务台的底部全局日程条语法：深青黑 / 金色日程按钮、独立 hit rect、`确认推进？` 二次确认态、与右侧进入地区 CTA 空间分离，不得作为右下角独立大机器按钮或红色 CTA 附属按钮。具体锚点可按页面结构放在底部中部或左下独立日程 dock，但必须明显属于全局日程系统，不得混入地区列表或 ticker。2026-06-23 修订：当 `推进一天` 固定到左下时，不应再包进普通米白纸卡或地区 / 任务同质卡片；它应读成独立实体日程器 / 时间闸门，例如日历推进器、排期拨轮、打卡钟式日期闸或小型印刷开关。纸面只可作为日期回执 / 小票 / 标签，真正可点击主体必须有更特殊的体积、按压、拨动或二次确认语法。
- 世界探索 / 全球地图页应优先采用“阶段导航 + 地图主语 + 选中地区详情 + 唯一主操作”的结构：顶部显示当前周流程阶段，地图承担首屏视觉主语，右侧只显示当前选中地区的从属情报预览，右下角主按钮进入地区 / 进入探索。右侧预览不能变成可点击任务列表；具体任务选择只在进入地区后发生。
- 世界探索右侧详情 / 选题夹必须读成一张独立的“深色纸面 / 档案夹”，而不是和地图黏在一起的同一片黑底。底色应比地图背景亮半阶或有更安静的纸面材质；边框优先用外侧深线 + 内侧微亮线 / 纸张叠层暗示厚度，避免单层 1px 网页线。面板内部按“标题区 -> 摘要徽章 -> 分隔留白 -> 详情列表 -> 底部 CTA”组织节奏：区域标题是最高文字权重，正文降到中性浅灰 / 油墨色，红条 / 青条只做小面积徽章，`消耗天数` 等关键数字用小数字框，主 CTA 固定为视线终点并高于状态标签。
- Angus 的世界探索首层应包装为“全球频道 / 世界线报总台”，不是普通地理菜单或抽象多边形地图。中央主视觉应有可识别的世界地图、经纬网 / 扫描线 / 新闻线缆 / 传真纸 / 区域高亮等频道语法；左侧只做区域级线报索引，右侧只做所选区域档案与进入 CTA。不要在世界层铺满具体任务点、完整深度链或派遣数值；这些内容进入 `region` 与 `dispatch` 后再显示。
- 全球地图页不能只让中央地图拥有美术包装，周边 UI 仍停留在默认面板。顶部状态、左侧索引、右侧档案、地图 pin 和主按钮必须继承同一套周刊 / 剪报 / 频道 / 红蓝套印 / 半调像素语言：左侧像取材索引册或监听清单，右侧像区域频道摘录或档案纸，主按钮像频道切入条或签批动作。若周边控件仍像后台列表、普通说明框或标准按钮，即使地图资源质量高，也视为包装未统一。
- 全球地图的“编辑部世界选题墙”必须优先继承标题页与编辑部入口的低细节像素标杆，而不是写实旧地图标杆。地图本体保留可识别世界轮廓、区域定位和必要航线 / 红蓝线索即可；不要用复杂海岸线、旧地图纸纹、写实墙面灯光或密集地理细节撑画面。高级感应来自像素边缘、半调、红蓝套印、多边形印刷块、索引卡、剪报夹、贴签和负空间。
- 像素化不能退回简陋占位图。若替换掉写实地图，必须同步补足成熟度：世界轮廓、地图板框、剪报、索引贴、红蓝线和边缘物件要形成稳定主画面；左右栏的空白要由索引柜底签、夹页槽、批注或状态摘要承载。空白可以作为负空间，但必须服务主地图或主操作，不能只是大块空黑面板。
- 世界频道 / 世界地图风格母稿应优先参考“概括像素杂志版式”口径：构成像现代杂志跨页或频道版面，使用大块深色场景剪影、中心异常符号、红 / 青几何侵入、半调网点、裁切线、少量粗线和 Q 版黑色幽默反应贴纸。颜色可以低饱和，但必须干净、清晰、有高级感；不能脏、旧、棕、灰蒙或靠真实纸纹做旧。细节密度应接近标题页标杆：大形先成立，小字和碎物件退后。
- 世界频道风格稿必须尽早落到完整界面骨架，而不只是一张杂志跨页或单个主视觉。评审图至少应覆盖顶部状态、左侧地区索引、中央世界地图、右侧区域预览 / 选题夹、底部日志 / 流程证明和进入区域 CTA；只有当这些区域都能继承同一套概括像素杂志语言时，才算风格方向可继续落地。
- 风格稿迁移到 Godot / HTML 时必须做整屏等价检查，不得只替换中央图片或贴几个同风格元素。至少对照：布局比例是否接近风格稿、主视觉是否仍占主舞台、周边面板是否同材质同语法、文字密度是否明显更低、按钮 / pin 是否像编辑部贴签而非系统标签、Q 版黑色幽默元素是否仍可见、底部日志 / 流程条是否服务同一版式。如果任一核心区仍像旧后台 UI，应继续返工。
- 全球地图里的地区情报标签按稳定语义分组：成本、收益、条件、挑战、信息、状态。不要让“可进入”这类入口文案重复占据标签位；地区选择卡应显示难度、推荐或解锁缺口这类能辅助地区决策的信息。行动日志默认折叠，避免压过地图和选中地区详情。
- 全球地图和地区情报预览里的 `条件` 只表示玩家需要满足 / 覆盖的需求，文案必须写成 `条件：探索2`、`条件：生存1` 这类“字段名 + 冒号 + 内容”。`对手骰`、危险、黑骰等是关卡挑战 / 压力，不属于条件，应写成 `挑战：对手骰2` 或进入专门压力槽位。
- 区域任务台只承担“选择当前地区里的哪个任务 / 线索入口”，不能同时承担完整派遣配置。区域页可以显示区域地图、任务列表、当前任务详情、链条进度、限时状态和 `进入派遣签批` 主操作；候选员工、已选员工槽、本次骰池、完整达标率拆解和真正消耗天数的执行按钮必须放到独立派遣签批页。
- 即使时间推进位于当前地区，也不能和任务列表 / 任务详情共用同一个选择容器或确认按钮槽。`日程推进`、`推进到第 N 天`、`结束探索周` 属于日循环系统动作，应作为区域面板底部或独立日程区的特殊动作呈现，并附带“已派遣 / 到期结算 / 倒计时变化”摘要；任务列表只承担“选择具体任务 / 进入派遣配置”。
- 区域页顶部不提供 `结束探索周 / 进入编辑部` 这类跨阶段跳转按钮；区域页的上层导航应返回世界探索层 / 世界取材地图，并按 §4.7 的层级返回按钮标准保持可见。真正结束探索周只能通过日程推进、周循环或明确的周末结算流程触发。

### 6.2 标签避让

地图层只要同时存在多种任务点、线索点或可展开入口，就必须有标签避让机制。

硬规则：

- 不靠手工坐标解决长期堆叠。
- 深度链、黑骰、截稿等高优先级入口优先保位。
- 普通任务和线索标签让位。
- 验收必须覆盖默认态、hover 态、展开态，以及宽 / 中 / 窄视口。
- 元素带 `transform` 过渡时，避让计算不能直接依赖动画中的 `getBoundingClientRect()`；应使用基础矩形 + 偏移量，或临时禁用过渡测量。
- 避让标准是“可读安全区”，不是“矩形刚好不相交”。叠层、阴影、描边光晕、hover 扇出范围都要计入保留区，标签之间应留出清晰空隙。
- 已派遣地图点应在任务点右上角显示派遣角色头像组。头像组属于任务点状态的一部分，需要参与视觉检查：不能太小到看不清，也不能遮住倒计时、任务名或邻近地图点。

### 6.3 深度链地图入口

- 地图只显示当前最新任务。
- 未完成第一环时，地图标识显示第一环。
- 完成第一环后，地图标识替换为第二环。
- 不在地图上同时显示整条链。
- 入口默认是规整叠层；hover 轻微错开；点击后可在同一对象中展开成线性链。
- 深度链地图入口的“展开 / 进入 / 收起”必须分离：第一次点击只展开链；展开后点击当前环任务直接进入任务界面；再次点击同一入口不负责收起。
- 收起属于退出上下文动作，应由点击任务之外的地图空白、切换对象或离开当前区域完成；不要把当前任务入口做成打开/关闭同一个 toggle。
- 展开态里只有当前环承担可执行入口，后续 `?` 环只表达潜在线索，不应有同等按钮感。
- 如果玩家点击未解锁的后续环，必须在该环附近弹出明确提示，例如 `该任务未解锁`；不能沉默，也不能把这次点击解释成收起、进入当前任务或远离对象的全局 toast。

## 7. 派遣配置与角色骰 UI

### 7.1 派遣配置页

派遣配置页是区域任务台下游的独立签批台，要让玩家感到“我正在组本次骰池并签批外勤”，不是只在读属性表，也不是继续在地图上选点。

必须优先表达：

- 已选人数，例如 `已选 2/3`；
- 本次骰池预览；
- 角色骰与道具骰进入同一个骰池；
- 与当前任务相关的骰面；
- 需求覆盖、缺口、空面；
- 临时线人 / 一次性道具是否占人数或占骰池。

追加资源必须保持同组语义一致，并避免把“获取入口”和“阵容管理”混在同一个按钮里：一次性道具仍可在追加区点击选择 / 撤回；临时线人这类会变成完整角色的资源，一旦雇佣成功，就应从追加区移除购买入口，作为候选角色出现在下方列表。后续加入或撤回本次骰池，都通过候选角色卡或已选槽完成，而不是让右侧购买按钮继续承担撤回逻辑。

任务头部必须遵守信息层级：

- 任务名、任务性质、关键需求和耗时可以作为紧凑标题 / meta 出现。
- 耗时是执行成本，不单独占一个 UI 模块；可写入 `耗时 2天` 标签，或体现在 `开始调查（2天后判定）`。
- 探索周剩余天数是全局资源，不放进任务摘要数值组。
- 截止日期是红色截稿 / 突发任务的特殊约束，只在对应任务上以警戒条、倒计时或状态提示出现，不和常规耗时、需求并列。
- 若截止日期是本任务的最关键决策值，优先用右侧倒计时块承载；不要把剩余天数藏在长句里。
- 需求可以在任务头部轻量提示一次；具体覆盖、缺口和风险判断以需求覆盖面板为准。

配置页主操作只能围绕本次派遣：`开始调查`、`开始线索调查`、`返回区域`、`撤销派遣`。其中 `返回区域` 是重要层级导航，不能做得像普通小标签；但视觉重量仍应低于开始调查。全局 `下一天` / `结束探索` 不应作为浮动按钮出现在配置页，否则会压过本页决策，并可能遮挡候选角色。

候选角色区可以提供明确的排序标签，例如 `任务贡献`、`达标提升`、`未派遣优先`，让玩家知道当前候选池为什么这样排列。新增排序标签时只改变候选区排序语义，不应顺手重做任务头、本次骰池、需求覆盖面板或整页壳层；这类大结构必须单独确认。Hover 只能临时提示，不改变选择、不触发隐式替换、不重排候选池。

派遣配置默认应是正式游戏界面，而不是实验页读数面板。宏观属性、公式解释、排序原因、贡献拆解和调试说明只有在影响当前组骰池决策时才显示；同一信息不要同时出现在骰面、文字摘要和右侧预览里。候选角色卡已有 dice net 时，不要再在骰面上方逐字重复“人脉+2 / 洞察+2”等骰面内容；卡片只保留姓名、简短适配等级和骰面本体，详细贡献默认进入详情页。右侧面板默认只做最终复核，例如“是否达标、还差什么、能否开始”；不要把 hover 候选时的变化做成常驻四格调试面板。若确需 hover 提示，也只能是短句，并且不能新增页面高度变化、重复骰面内容或开发口径标签。

派遣配置里的任务需求由“需求覆盖 / 判定目标”区域主承载；任务头只负责身份锚点、耗时和特殊后果，例如截稿倒计时或失败伤害。若右侧已经逐项展示 `人脉 / 洞察` 的覆盖和缺口，任务头不要再写 `需求 人脉2 / 洞察2`，否则同一需求事实会拥有两个视觉主语。

多人参判场景中，参判席的空间优先级高于覆盖拆解。若角色槽达到 5-6 人或更多，本次参判席应作为二级区域主承载，提供稳定槽位、头像、姓名、核心贡献和明确移出操作；不要让已达标的需求覆盖条占据与参判席同等甚至更大的面积。无缺口时，覆盖信息默认降级为紧凑摘要，例如 `已达标：6/6 · 96%` 与 `人脉 9/2` 这类小 chip；完整属性条进入折叠明细。只有存在缺口、失败边界或玩家必须凭属性拆解换人时，覆盖明细才展开或提高权重。

派遣配置页若是世界地图 / 区域任务台的下游，不应突然切换成另一套高权重视觉语法。上游是暗色地图与任务台，下游签批台也应延续暗色工作台、清晰分栏和稳定按钮；物件化美术只承担职业幻想、材质和截图包装，不能让任务文字、候选卡、已选槽、达标率和主 CTA 变成大角度斜纸片或透视控件。若要做斜桌面、纸件、印章等拟物资产，必须先确认整个交互系统能同角度承载文字、点击区和状态变化；否则一律降级为背景、装饰或低权重附属物。

### 7.2 风险提示

- 整体风险应优先看任务需求覆盖度和缺口。
- 不要用“相关骰面 / 总骰面”比例直接标整体风险。
- 加入低贡献角色不应让整体风险反向升高，除非规则明确规定会带来额外代价。
- 低贡献角色应提示“贡献低 / 无相关面 / 占用人数槽”，而不是让任务本身变危险。
- 如果界面显示“低 / 中 / 高风险”或“达标率”，必须使用与真实结算一致的公式。不要用整套骰面池的潜在覆盖、静态面值总和或候选排序分数替代实际掷骰概率；0% 或几乎不可达的组合必须显示为高风险 / 不可达。
- 风险标签不能只给粗粒度等级。若 `低 / 中 / 高` 会让明显不同的概率落在同一档，必须在高权重位置同时显示实际达标率，例如 `风险：中 · 54%`；多人队伍相对单人最佳的提升应在说明中显式写出，例如 `较单人最佳 +21%`。
- 角色骰当前口径：任务需求属性决定哪些骰面算相关；普通任务达标看相关骰面有效点是否达到任务目标，而不是每个属性在单次掷骰中逐项硬达标。UI 应同时显示有效点目标和实际达标率，属性条用于解释相关贡献来源。
- 角色骰判定 UI 中，`有效点 / 目标值 / 达标率` 是判定结果口径；`理性 / 洞察 / 探索` 等是属性贡献拆解。两者不能做成同一行同等样式的进度条。正确结构是先给玩家一个判定目标 / 当前结果摘要，再用次级属性条或展开明细解释哪些属性贡献了这些有效点。
- 如果真实达标率暴露出适配队伍仍几乎不可能成功，不能只改风险标签或文案。UI 规则要反向提醒设计：检查任务需求、目标公式、骰面密度和支援资源，让高风险任务保持“可搏”，而不是把不可玩状态包装成准确提示。

### 7.3 角色骰表现

- 角色骰 UI 必须让玩家联想到骰子。
- 可参考骰面展开、骰子网格、六面展示等方式，而不是普通资料面板。
- 派遣配置页里的候选角色卡、已选角色槽和角色详情，只要展示完整 6 面角色骰，就应优先使用骰子立方体摊开的“长尾十字架 / dice net”结构；不要退回普通横向 chip 行。横向 chip 行只适合极小摘要、日志或一次性道具简表。
- 角色卡默认只显示专精可以，但与当前任务相关的骰面必须更亮、更大。
- 角色详情应先给当前任务适配结论，例如“相关面 3/6，空面 1”。
- 不相关面降级显示。
- 升级分支默认折叠，避免干扰派遣决策。

## 8. 布局与间距规则

### 8.0 避免随意拉伸

除特殊说明外，界面元素不应因为选项变少、内容变短或某个槽位被消耗，就自动拉伸填满剩余空间。固定格式的按钮组、卡槽、资源格、工具条、骰池、候选区等，应优先保持稳定槽位、固定列宽或明确空位，让玩家感知“这里原本有一个位置，现在被使用 / 移除 / 空着”。随意拉伸会削弱品质感，也会破坏玩家对数量、消耗和空间关系的判断。

允许拉伸的特殊情况必须有明确目的，例如正文阅读区域、弹性表格主列、响应式单列移动布局，或内容本身就是需要填满容器的画布 / 地图 / 时间轴。做这类拉伸前要先判断：玩家是否需要感知固定槽位；如果需要，宁可留空也不要让剩余元素变宽。

### 8.1 删减后必须回收空间

删除信息后，必须同步检查：

- `gap`；
- `padding`；
- `min-height`；
- grid 行列占位；
- 绝对定位元素是否还在撑开正文；
- 操作按钮和需求行是否仍对齐。

不能只确认文字消失。内容少了，空间也必须变紧凑。

### 8.2 功能标识位置一致

- 同一类功能信息必须在同一位置出现。
- 如果某任务没有该信息，槽位可以缺省，但已有信息不能换位置。
- 不要因为某张卡有倒计时，就把普通耗时挤到另一侧。

## 9. 骰子判定与玩家控制

- 任何强调单颗骰子、锁定、干预、污染的玩法，应控制骰子总数，默认单次判定不超过 10 颗。
- 骰子判定页和骰子实验页必须显示当前任务需要哪些属性与几点；有效点、达标状态和结果结算必须按真实任务需求计算，不能把所有骰面数值简单相加。
- 骰子判定进入“停骰选择 / 计入选择”阶段后，骰面本身必须成为清晰可点击入口，且选择后固定计入槽、有效点、属性贡献拆解和提交前结果预览要同步变化。玩家不能先提交，才知道本次选择会成功还是失败。
- 骰子判定的提交按钮保持中性动作文案，例如 `提交判定`。不要因为当前未达标就把按钮改成 `提交失败判定` 或染成“不能点”的惩罚语义；未达标、成功、代价和后果应由判定目标、提交预览或二次确认承担。
- 骰子判定页必须为每类信息指定唯一位置：达标 / 差值只在判定摘要表达；属性需求与当前贡献只在目标拆解表达；重投次数只在控制区表达；重投对象只在重投范围附近表达；提交区只表达提交后的后果。不要在标题、顶部徽章、按钮、预览和进度条里反复显示同一个点数或同一句阻断原因。
- 计入槽位应保持固定数量和固定尺寸，空槽继续占位；不要因为已选骰面变少或变多就拉伸组件。空位本身用于表达“这里还可以计入 / 这里已经空着”，也是玩家判断容量的一部分。
- 骰子判定交互实验的首轮默认只验证骰面卡片、需求实时联动和提交前预览；一键推荐、黑骰扩展、完整投骰动效和结果演出要作为后续单独确认项，不要和基础选择入口混成一版整页重做。
- 玩家需要决策时，不自动推进。
- 锁定、重投、确认类动作必须有明确按钮。
- 不用 2 秒自动倒计时替玩家继续，除非用户明确要求快节奏。
- 新机制不能只在结算文案里出现，必须在玩家决策现场被看到、操作到或感知到。
- 骰子判定区是本页主舞台。有效点目标、属性贡献、黑骰说明、计入槽和按钮都必须服务骰子决策，不能把骰子盘挤到页面下沿或做成附属列表。
- 骰子判定弹窗适配 3 到 5 名参判角色时，讨论对象是“参判角色 / 可计入骰面”，不是派遣配置人数。优先使用最多 5 个固定参判槽：3 人判定显示 3 个可计入槽 + 2 个未参判占位，5 人判定打开全部槽位；骰面卡片也按同一 5 槽骨架展示，未参判角色降级为不可点击占位。人数变化不能拉伸卡片、挤压右侧判定目标，也不能自动取消已计入骰面。
- 摇骰表现不能只是数字 / 文案原地闪烁。至少要让玩家看到“实体骰子在盘面中运动”的线索：独立骰盘、骰子本体、位移、旋转、落地反弹、阴影或轨迹。停骰后再进入选择 / 锁定 / 重投阶段，避免像翻牌或刷新标签。
- 如果视觉目标是“投骰”，骰子本体不能做成只有一个面的薄片翻转。必须表达厚度和多个可见面：真实几何体模型、六面结构、侧面明暗、接触阴影、抛物线和多轴旋转至少覆盖其中几项；否则玩家会把它读成卡牌 / 令牌，而不是骰子。若 CSS 3D 仍被用户读成薄片，应停止继续微调 CSS，转向 Three.js / Godot / Blender 等真实模型路线。
- 当方案声称是“立方体 / 实体骰 / 建模骰”时，验收门槛是截图里能读出闭合体积，而不是“画了多个面片”。至少应看到互相连接的顶面与侧面、边线 / 角点能闭合、面与面之间没有漂浮缝隙、遮挡关系与投影一致；如果任一面仍像独立纸片、卡牌或散开的贴片，就必须判定为未通过，不能称为立方体模型。
- 实体骰的面内容必须贴合骰面。骰点、属性文字、符号、贴图、划痕和发光都应服从所在面的透视、旋转、遮挡和边界；不能像 2D 字幕一样浮在屏幕上，不能越过面边缘，不能和面角度相反，也不能为了闭合外轮廓牺牲已成立的贴面效果。若旧版或参考图中某一项已经表现良好，例如文字贴面、投影、落地阴影或材质厚度，返工前必须列入保留项并在新截图中回归检查。
- 实体骰的文字、骰点和符号应尽量在建模 / 材质 / 贴图阶段成为骰面的一部分，而不是投影完成后临时画在屏幕坐标上。Canvas 原型若不用真正 3D 引擎，也应使用离屏面贴图再映射到投影四边形；不能用独立 2D 标签模拟贴面，否则容易出现对位不准、文字角度与面不一致、被裁切或偶发不显示。
- 实体骰的面材质应优先保证可读性。默认骰面不能像透明线框盒；背面、内部结构线、调试线或被遮挡边不能穿过正面文字 / 骰点。除非用户明确要求“透明骰”风格，否则应使用不透明或高遮蔽度面材、暗色面底、清晰外轮廓和少量必要转角线，参考旧版骰子的“实心面 + 高亮边 + 文字在面内”效果。判断面是否不透明时只看截图读法：若背景网格、轨迹环、背面边或另一面的结构线在骰面内部仍清楚可见，或面主要靠线框而不是色块成立，就判定为透明 / 线框感未通过；不能用代码里 `fill()` 过多边形来替代视觉结论。
- 立方体骰子的视觉检查必须做反向提问：玩家第一眼会不会把它读成“薄片 / 几张面 / 翻牌”？如果答案有明显可能是“会”，即使动效、投影、发光、轨迹都存在，也不能继续交付给用户看作实体方案。
- 骰子视觉验收至少包含五类条件：盒体闭合、骰面不透明且可读、面内容贴合、光影投影一致、动作落地可信。只通过其中一类不算通过；尤其不能用“几何结构正确”替代“截图里读起来正确”。
- 如果用户要求“不改变原判定界面布局，只改骰子表现”，动效实验必须嵌在原判定弹窗的信息结构中验证：保留标题、判定摘要、计入槽、骰子判定区、侧栏状态和底部按钮的相对关系，只替换骰子盘内部表现。不要为了展示动效另起一个全屏大舞台，除非用户明确要求脱离原界面比较。
- 当用户只要求应用某个视觉对象、模型或动效时，默认改动边界是“替换该对象本身”，不是重排承载界面。若落地时发现模型尺寸、镜头或动效需要更大空间，必须先问用户是否允许调整布局；不能为了展示效果擅自把列表、卡片网格、进度面板、按钮区或弹窗信息顺序改掉。验收时要把“布局是否仍是原布局”作为独立可否决项。

## 10. 实验页规则

实验页不是低标准页面。

实验页也不是正式制作页。它的价值是用很低成本回答一个清晰问题，而不是提前做一套完整 UI。

### 10.1 快速实验页的时间盒

创建实验页前先写清楚三件事：本页只回答什么问题、只比较哪些局部状态、什么时候停止。若这三件事说不清，优先回到本体做最小切片，或先用文字 / 草图讨论。

快速实验页的默认约束：

- 默认只做局部组件，不复刻完整页面、完整流程、完整背景和完整数据。
- 默认复用现有 CSS 变量、组件类、真实截图或少量静态 DOM；不要为了实验页新写一整套视觉系统。
- 一次只验证 1 个核心判断，最多并排 2 到 3 个状态或方案。
- 交互只保留能回答问题的最小动作，例如 hover、选中、禁用反馈；不补齐正式流程、教程、日志、入口和全链状态。
- 截图默认 1 张关键桌面图；除非用户要求，不做移动端、长链路、汇总页和多状态全覆盖。
- 若实验页实现、验证和文档成本已经接近直接改本体，必须停止扩写实验页，改为在本体承载页做最小落地。

实验页交付时要明确标注“这是局部实验，不是本体已落地”。用户确认方向后，才把选中的局部语言迁移到主界面，并在主界面做真实路径验证。

### 10.2 是否需要独立实验页

默认不为已有游戏本体 UI 另起“假实验页”。如果方向已经明确，目标是修改现有试玩流程，应优先在本体承载页做最小切片，并用真实数据、真实入口、真实状态验证。

只有满足以下情况之一，才先做独立实验页：

- 方向尚未明确，需要并排比较 2-3 个视觉 / 交互方案；
- 新系统没有现成承载页面，必须先搭一个低成本操作面；
- 直接改本体会污染正式流程，且无法用参数、临时入口或本体 lab 模式隔离；
- 用户明确要求先做静态实验页或视觉草稿。

若只是担心风险，优先在本体增加临时参数、隐藏入口或 lab 模式，不默认另写一套假数据、假交互、假 CSS。独立实验页只能验证构图和局部手感，不能替代本体路径验收。

### 10.3 实验页质量底线

只要实验页复用正式 UI 语义，就必须继承正式原型的基础保护：

- 地图标签避让；
- 碰撞审计；
- 响应式检查；
- 状态截图；
- 操作按钮对齐；
- 文案去冗余；
- 信息槽位一致。

实验页可以粗糙，但不能把已经解决过的问题重新带回来。

### 10.4 动效演示页

当用户要求查看动效、动效语言、动画手感或多个动作方案时，应优先单独制作“系列演示页”，不要只把动效散落在正式流程里让用户反复触发。

动效演示页必须：

- 按动作类型分组展示，例如摇骰、停骰、计入飞入、黑骰介入、锁定 / 重投、结果收束；
- 每组都有可手动重播按钮，必要时提供“重播全部 / 暂停循环”；
- 明确标注这是视觉实验页，尚未套用到完整全链或正式流程；
- 按桌面 16:9 保留按钮可见、文字溢出和布局挤压验收；除非用户明确要求，不做窄屏 / 移动端截图验收；
- 用户确认某个动效进入主干后，再把选中的动作最小化移植到真实承载页面，不默认把实验页全部动效塞进正式流程。
- 实验页方案落地时，必须迁移“被用户认可的视觉主体和实现类别”，不能只迁移动作名、文案或参数名。若实验页通过的是 Canvas / WebGL / Godot / Blender 等实体模型，本体落地不能降级成 CSS 2D 方块、贴片、线框或屏幕标签来冒充同一方案；除非用户明确同意“只先做低保真占位”，否则这类替身实现默认未通过。
- 实验页落地验收必须做基准对照：至少同时查看“已通过实验页截图”和“本体落地截图”的同类局部，逐项比对视觉主体、材质 / 不透明度、内容贴面、动作轴向、节奏、停稳状态和原界面布局。只要本体截图第一眼不像实验页中被确认的对象，就应先返工，不得用“代码也叫横轴急转”“动画属性已变更”或“流程可运行”当作完成依据。
- 如果某个动效直接落入本体后被反馈“表现奇怪”，应优先撤回或隔离本体改动，回到独立动效实验页比较动作语言；不要在正式试玩里继续堆叠临时动画修补。
- 投骰动效实验页应优先用低成本程序化实体方案验证手感，例如 Three.js 程序化模型或 Godot 内置网格；CSS 3D 只能作为极早期草图，不能作为已被质疑薄片感后的主方向。只有当实体方向被确认且需要长期材质、破损、污渍、异化等细节时，才进入正式 Blender / GLB 资产制作。
- 动效实验页必须按用户实际打开方式验收。若交付的是可双击打开的 HTML，不要依赖会被 `file://` 拦截的 ES module、远程 CDN 或本地 HTTP 服务；除非最终同时提供并验证可用的预览 URL。截图脚本通过本地服务不等于用户直接打开也能显示。

### 10.5 实验落地与主线保护

完整全链试玩、Godot 主场景和其它用户日常打开的默认入口，都视为稳定承载页，不直接承接未经确认的实验成果。

- 视觉、动效、布局、模型、地图重绘、入口路由等实验，默认先放在 `labs/`、独立实验页、隐藏入口或明确 query flag 中；用户确认后，才允许迁移到默认试玩入口。
- 实验迁移到完整全链前，必须先留基准截图。HTML 全链至少覆盖：根入口、全球地图、地区页、目标配置 / 判定页；Godot 或其它原型按同等关键路径截图。改完后必须用同一路径、同一视口再截图对照。
- 单次落地只改用户确认的局部。若需求是“只替换骰子表现”，不能顺手改地图、派遣配置、主流程布局、入口版本号或全局视觉系统；确需扩大范围时，先向用户说明并等待确认。
- 高风险 UI 改动必须有隔离开关或回退路径。包括 3D / 实体模型、地图背景重绘、派遣布局重构、默认入口切换、内联 HTML 打包体改写、跨文件同步改动等。默认入口保持稳定，实验入口明确标注实验性质。
- 多文件承载页必须说明真源并保持同步。像 `world-mysteries-full-chain.html`、`world-mysteries-full-chain.js`、`world-mysteries-full-chain-head.htm` 这类拆分 / 内联并存的页面，不能只改其中一个文件造成主线与生成体分叉；若某个文件是产物，应通过既定脚本生成或在交付中明确同步结果。
- 若用户指出“主线界面乱了”，优先查入口是否被实验版本号、旧版 query、缓存或内联产物污染；在用户确认正确基准截图前，不直接回退或继续叠加修补。

## 11. 截图、入口与版本验收

### 11.1 截图文件

可见 UI / 原型改动必须交付真实截图。

- 不复用旧截图文件名，避免聊天端缓存旧图。
- 文件名应带日期和改动主题，例如 `2026-05-12-unified-duration-slot.png`。
- 1-3 张截图直接贴对话；超过 3 张整理汇总页。
- 直接贴图必须确认使用能被当前对话渲染的 Markdown 图片语法。Windows 本地截图用正斜杠绝对路径，例如 `![截图](D:/angos/docs/screenshots/.../01.png)`；不要只给 `D:\...` 路径文本，也不要把不可渲染的路径误当成已展示截图。
- 返工后的截图必须使用新文件名，并在最终回复前实际打开查看。自动化审计只能证明 DOM 条件，不能替代肉眼确认截图里玩家看到的文字、位置和视觉层级。
- 截图必须先标注用途：`目标效果稿 / 组件验证稿 / 运行截图 / 逻辑烟测截图`。只有与用户目标界面、目标功能分区和目标视觉锚点一致的运行截图，才能作为 UI 落地验收；旧框架里的状态机截图只能证明逻辑，不得替代目标界面截图。
- 资产化落地必须做“旧控件回收检查”：位图资产接管纸张、材质、主图或贴片后，旧 CSS / DOM 装饰层、版式调试条、重复标签、线框槽位和临时说明必须被隐藏、降权或迁走；截图中出现两套视觉系统叠在一起时，不能判定通过。
- 若资产化或视觉实验已经造成多套版式控件、旧 DOM 状态层、新位图贴片和说明文字混层，优先回退到 UX / 用户确认的稳定截图锚点，再按“每次只资产化一个承载物并同步回收旧控件”的顺序重做；不要继续在混层基线上局部调色、补间距或隐藏个别元素。
- 对复杂纸面、杂志、票据、档案墙、地图贴片等“拟物承载 UI”，重复语义和调试式标签必须从当前渲染层清掉，不能只靠 `display:none` 或更高层级遮住。截图验收前应至少做一次可见层审计：当前可见容器内不得出现禁用残留文字，关键槽位不相交，关键文本盒的 `scrollWidth / scrollHeight` 不应超过可见盒，且桌面 16:9 的主要视口无横向溢出。
- 资产化后的底图物理结构必须进入验收模型。打开杂志、签批纸、票据、地图墙、机器按钮这类资产里如果存在书脊、中缝、折角、纸边、夹板、票据边、压痕或按钮文字区，必须把这些区域标为 DOM 禁入带；槽位、hover / drag-over 蒙版、按钮、动态标题、动态数值和状态章不得进入禁入带。审计不能只看 DOM 盒子互不相交，还要检查 DOM 盒子和资产物理安全区不相交。
- 资产化验收必须同时看空态、中间态和满态。仅看满版容易漏掉空槽蒙版压书脊，仅看空态容易漏掉长标题或动态值出框。复杂纸面 UI 至少覆盖空态、1/3 或等价中间态、满态，并对书脊 / 主槽、签批纸动态字段、送印按钮做 100% 局部裁切检查。

复杂 UI / 分阶段 UI 重构交付时，优先提供“无标注真实截图 + 程序化标注截图”组合。标注截图必须基于真实页面 DOM 或游戏 UI 元素位置绘制框线、编号与短说明；不要把 AI 生图标注当作验收依据。

### 11.2 截图前检查

交付前逐项检查：

- 是否有标签堆叠；
- 同类功能标识位置是否一致；
- 是否仍有冗余说明；
- 删除内容后空间是否回收；
- 按钮是否对齐且不换行；
- 文字是否溢出、重叠或遮挡；
- 角标、徽章、头像组是否有独立槽位或安全区，是否遮挡标题、按钮文字、倒计时或地图点文字；
- 地图 / 卡片 / 弹窗是否在当前视口正常；
- 若涉及 hover / 展开，是否截图或审计对应状态；
- 是否有缓存旧图风险。

视觉对象还要做一次“目标读法”检查。这不是立方体专用规则，而是所有 UI、动效、模型、图标、状态、布局和视觉符号的通用验收法：

- 先把用户需求里的视觉名词翻译成可观察条件。用户说“立方体”，AI 必须先列出闭合体积、六面或等价可见结构、共享边角、厚度、遮挡、投影；用户说“可点击明显”，AI 必须先列出按钮形状、对比度、hover、指针、文案和 disabled 差异；用户说“不要像任务卡”，AI 必须先列出任务卡语法并确认新方案避开它。
- 返工前必须列出旧版或参考图里已经成立、不能丢的优点。视觉修改不是只消灭一个缺陷；如果新方案修好了 A 却破坏了原本成立的 B，也视为未通过。旧版优点可以是文字贴面、尺寸比例、按钮位置、动效节奏、投影、颜色层级或玩家已经认可的布局关系。
- 同时写出禁止误读项。每次视觉验收都要有一句“它不能被读成什么”，例如“不能像薄片 / 卡牌 / 散开的面片”“不能像可点击任务”“不能像同级模块”“不能像鼓励回收”。后续截图先检查禁止误读是否还存在。
- 实现完成后必须逐条对照这些条件，而不是只问“有没有渲染 / 有没有动画 / 有没有改代码”。自动断言、非空像素、动画播放和整体氛围只能证明页面有东西，不能证明视觉语义成立。
- 查看整页截图后，必须再裁切关键对象区域，以 100% 和放大视图肉眼检查；不能只用远景整图判断。复杂页面还要同时检查默认态、hover / 展开态、选中态、禁用态和用户截图指出的局部。
- 如果截图第一眼读法和方案命名冲突，以截图读法为准，先返工，不要用实现意图、代码结构或“我本来想表达”解释视觉结果。
- 对被用户连续纠偏过的问题，下一次同类工作必须先做回归检查：旧错误是否又出现、旧词汇是否还残留、旧视觉语法是否换了名字继续存在。
- 当用户要求“把实验页方案落地”时，必须检查是否出现“同名不同物”的降级：本体中的对象是否仍是实验页确认的同一种视觉对象，还是被换成了更低保真的按钮、卡片、标签、图标或 CSS 效果。若需求是实体骰，截图必须像实体骰；若需求是地图符号，截图必须像同一套地图符号；若需求是父子详情，截图必须保留同一层级关系。不能只保留方案名称、颜色、文案或某个 transform 参数。
- 模型 / 图标本体不要替状态框背锅。选中态、相关态、风险态应优先落在所属卡片、槽位或提交区；不要把黄色框、白色外环、轨迹环等装饰直接套在实体骰、道具、地图符号上，除非该装饰本身是明确的世界内效果。实体骰要先读成有厚度、有遮挡、有暗边和落地阴影的骰子，再考虑动效。
- 如果 AI 无法自信判断视觉对象是否成立，应先降级为“待确认视觉草图”，或给出局部截图请用户判断；不能把未通过自检的方案包装成已完成。
- 连续返工后的总结必须能举一反三：把问题拆成“对象主体、内容归属、材质 / 遮挡、状态动作、旧版优点、禁止误读”几个维度。不要只写“这个骰子要这样做”；应写成“任何声称某内容属于某个视觉对象时，都要验证内容是否随对象一起变形、遮挡、缩放和状态切换”。地图标签、按钮角标、卡片徽章、模型贴图、图标动效都适用同一原则。

### 11.3 截图数量与对话负载

- 截图较多时，优先生成截图汇总页，并在对话里只贴最关键的 1-3 张。
- 如果当前对话已经因为大量截图、长链路 UI 讨论或历史上下文变得明显繁重，AI 应主动提醒用户：建议新建对话，并给出当前任务状态、关键文件和截图目录，避免继续堆上下文导致未响应或卡死。

### 11.4 网页入口

- 根目录入口必须能清楚区分当前试玩原型、旧参考页、实验页。
- 截至 2026-05-27，根 `index.html` 在本仓库承担开发导航职责，不等同于正式玩家入口。做冗余信息审计时必须先判定页面角色：开发导航可以保留实验目录和旧参考入口，但必须标注清楚；完整全链试玩等主流程承载页则不能把演示、调试、视图切换控件暴露给玩家。
- 按钮文字要说明实际含义，例如“试玩当前原型”“打开符号实验页”，不要让用户误以为某个实验页是正式游戏。
- 如果存在缓存风险，入口链接应带版本参数或说明当前版本。
- 新增实验页后，应考虑是否需要在根入口放临时入口，避免用户翻目录。
- 如果用户要求“在 index 体验到某个刚确认的 UI 改动”，根入口的主按钮必须指向该改动所在页面；不能只把它藏在次级卡片里。
- 如果完整全链原型还没有套用某个实验页 UI，入口必须明确标注“旧壳层 / 次级入口 / 尚未套用”，避免用户误以为改动回退。
- 当用户确认某个实验页 UI 应进入完整版或主干时，必须同步所有实际承载页，不得只改 index 文案。验收至少打开一次 `index -> 完整全链 -> 目标界面` 的真实浏览器路径，并截图确认与当前 UI 规则一致。
- 交付 HTML 实验页、动效演示页或可交互原型时，必须同时提供“浏览器可直接播放 / 操作”的入口，例如 `http://127.0.0.1:端口/...` 或明确可双击打开的 HTML 路径；不能只给仓库源码文件链接。
- 默认试玩入口不得指向未经完整路径验收的实验版本号。若为了破缓存调整 `?v=...`，必须确认该版本已经通过根入口、全球地图、地区页、目标配置 / 判定页截图；否则保持默认入口指向最后确认的稳定版本。
- 若对话中的文件链接会打开编辑器源码，应明确标注“源码文件”，并另给“预览网页”链接。用户要体验动效时，默认应打开预览网页而不是源码文件。
- 行动日志不默认等同于开发日志或噪音。若它承载玩家行动回顾、现实剧情文字、因果反馈或世界状态变化，可以保留为叙事组件；只有纯调试输出、公式流水或重复主信息的日志才应删除、折叠或降级。

### 11.5 截图与网页版本一致

- 给用户的截图必须来自当前页面的真实浏览器截图。
- 不复用旧截图文件名。
- 如果用户指出网页和截图不一致，先检查缓存、截图裁切范围、是否打开了旧入口，不要直接解释成用户看错。

### 11.6 美术风格稿与 UI 原型

- 玩法 UI 原型先验证功能呈现和交互，不等同于最终 GUI 包装。
- 正式美术风格稿确定后，可用“玩法原型截图 + 风格稿”生成目标效果图；当前正式美术风格以 `design/art-direction/angus-visual-style-guide.md` 为准，必要时让 `angus_art_director` 审查 prompt 和结果是否跑偏。
- 效果图不能替代可操作原型；必须再拆解回组件、状态、槽位和实现规则。
- 临时风格尝试不要自动写入正式设计文档，除非用户明确要求沉淀。
- 程序化 SVG / Canvas / CSS 示意板只能称为低保真结构稿、信息映射稿或工程规格图。除非它已经达到真实美术渲染、材质、光照、纹理和标杆继承要求，否则不得称为美术风格稿、资源候选或生产标杆；需要美术完成度验收时，应另交生图 / 建模渲染 / 精修位图候选。

## 12. 派遣签批台与中央主舞台专项规则

> **2026-07-08 归并说明**：本节归并自 2026-06-22 至 2026-06-23 的九条尾部日期补充（派遣签批台 V3-V9 返工系列），内容保留、仅重组为编号小节。原始文本归档于 `_obsolete/ui-interaction-guidelines-legacy/dated-appendix-2026-07-08.md`。

### 12.1 页面主语与四物件结构（2026-06-23）

当用户指出"不要只是简单删掉，而是整个界面重构"时，不能再以删减单个面板、缩小重复信息或给空白处补便签作为主要改法。必须先重新确认页面主语、玩家动作和四物件关系，再出结构稿。

- **页面主语 Gate**：V8 以后派遣签批台的第一眼应读作"主编在编辑部外勤案卷桌面上组本次骰池、配辅助骰位并盖章"，而不是"任务条件达标后提交审批"。
- **四物件结构**：整屏默认组织为 `左侧任务卷宗 + 中央外勤案卷桌面 + 底部候选抽屉 + 右侧签批票据`。左侧回答为什么派人；中央回答谁去、带什么、组成了怎样的本次骰池、局部为什么可派；底部只供应人员 / 器材；右侧只做完整复核和 CTA。
- **不得以新功能填空**：中央空间释放后，优先放大已选人员席位、可选增援席、辅助骰位 / 随队器材托盘、本次骰池预备纸、档案底纸和局部贡献证据。不得新增覆盖矩阵、协同网络、队伍关系、路线规划、复核状态块或解释性便签来填补。
- **视觉代入感来自物件承载动作**：人员卡应像外勤证 / 派遣卡，器材应像随队托盘，地图应承载路线与任务地点，票据应是最终签批回执。若拟物元素不能承载当前操作或局部证据，应降级为背景或删除。
- **交付前反问**：遮住右侧票据后，中央是否仍能回答"谁去、带什么、组成了怎样的本次骰池、为什么大致可派"；遮住中央后，右侧是否只剩复核摘要而不是完整玩法解释。任一答案不成立，都不得进入真实内容风格稿或资产化生图。

### 12.2 主舞台不得空心化（2026-06-22）

当 UI 页面存在"中央主舞台 / 主工作台 / 主物件"时，不能只为了减少重复或把信息合并到侧栏，就把中央主舞台清空成背景、地图底板、装饰路线或少量标签。合并信息后必须同步补足主舞台的决策内容，或收缩容器。

- **中央单独裁切测试**：遮住侧栏，只看中央主舞台 5 秒，必须能回答当前页面的核心决策问题。派遣签批台中必须能回答"谁去、带什么、补了什么、为什么可签"。答不出，不得交付。
- **空心率测试**：中央主承载物不得出现大面积无功能空白；地图、桌面、纸板、档案夹等背景空白必须被路线、队伍、器材、覆盖关系、风险、补强或等价功能信息解释。
- **右栏越权测试**：侧栏 / 票据 / 详情栏只能做复核、摘要、收据或 CTA，不得成为唯一解释"为什么可执行 / 为什么值得点"的位置。
- **删除回收测试**：从主舞台删掉一块信息后，必须用新的主信息填回，或收缩主舞台面积；不能留下同等面积空洞。
- **旧版优点保护**：返工前列出上一版已经成立的 3 个优点；新稿不能修掉重复、拥挤或边界问题，却丢掉主决策闭环。
- **禁止转场补丁文案**：不要用"见右侧 / 见下方 / 详见票据"等文案修补布局关系；如果必须写这种文案，说明信息归属还没有成立。

该规则由派遣签批台 V3 过度合并反例触发：V3 将"需求覆盖与补强"移入右侧票据后，中央主舞台空心化。后续同类结构稿必须先过本 Gate，再交付给用户。

### 12.3 表达增强不得伪装成新增功能（2026-06-22）

中央主舞台只能重排、放大和清晰化既有功能，不得为了填补空间或提高"决策密度"另起第五功能区。尤其是"需求覆盖信息"可以被放大、拆行、标注来源、贴回角色卡或道具槽，但不能包装成 `覆盖矩阵`、`队伍覆盖关系系统`、`协同网络`、`关系算法` 等独立系统对象。

- **四区归属检查**：中央主舞台里的每个块，必须能归属到 `任务人员空槽 / 当前角色列表 / 辅助骰位或随队道具 / 需求覆盖信息` 四区之一；归属不清的块视为新增功能，先退回 UX / UI / 系统边界复审。
- **旧功能放大优先**：当中央显得空、散或信息密度不足时，优先给原四区更多尺寸、状态、贡献标签和关系说明；不要新增一个同级大模块来"解释"原功能。
- **命名降权**：禁止在功能界面中使用会暗示新增玩法的标题，例如 `覆盖矩阵`、`队伍覆盖关系`、`关系网络`、`协同矩阵`。默认使用 `需求覆盖`、`覆盖明细`、`可签依据` 等直接签批语言。
- **表现增强边界**：允许显示"谁贡献了哪项需求""道具补了哪项缺口""加入后缺口如何变化"；不允许新增覆盖分、协同值、关系加成、稳定性奖励，也不允许让玩家手动连线、锁定覆盖线或指定角色负责某属性。
- **右侧复核边界**：右侧票据只能复述最终摘要和承载 CTA，不得把"为什么可签"的主解释从中央拿走。遮住右侧后，中央仍应能读懂本次派遣配置成立。
- **交付前误读检查**：截图第一眼如果像多了一个新系统对象，而不是原四区获得了更清楚的表达，则该稿不得交付；先改名、降权、合并回席位 / 道具 / 需求行。

### 12.4 复核摘要优先归右侧票据（2026-06-23）

完整复核摘要不应占据中央主舞台。`需求 2/2`、`有效点 13/8`、`缺口 无`、`风险 压力+2`、`耗时 2天` 这类签批前最终核对，优先合并进右侧签批票据；中央只保留贴近操作对象的局部证据，例如角色卡贡献章、器材补缺标签、任务短条需求摘要和薄状态戳印。

- **中央主语检查**：第一眼应读作"正在组一支外勤队并准备盖章派遣"，而不是"正在查看一张校验表 / KPI 面板"。
- **重复复核检查**：如果中央和右侧同时大面积展示覆盖、达标率、缺口、风险，说明复核信息重复；应把完整摘要收进右侧，把中央空间还给人员、候选、器材和拟物工作台。
- **拟物留白允许**：中央可以有约 20-30% 的桌面 / 地图 / 档案负空间，但这些空间必须承托当前任务路线、人员卡摆放、器材托盘、纸层、线索或盖章动线；不得只是空背景。
- **局部证据保留**：把复核表移到右侧后，中央仍要通过角色贡献章、器材补缺、任务短条等回答"为什么大致可签"；不能让玩家必须只看右侧才知道配置效果。
- **候选与人员优先**：释放出的中央高度优先给已选人员席位和候选人员抽屉，其次给随队器材托盘，再给拟物桌面层次；不要用新的横向面板重新填满。
- **交付前截图判断**：截图若被读成后台表格、审批系统或配置页，而不是外勤派遣现场，应退回重排；修正方向是减少系统面板、增加派遣物件和人员操作面积。

### 12.5 拟物留白不得用伪状态块填充（2026-06-23）

当复核摘要已经归入右侧票据后，中央主舞台不应再用 `需求已满足`、`压力 +2`、`待盖章`、`可签`、`复核通过`、`覆盖已核对` 等小便签 / 戳印 / 状态块填补空位。这些块如果只是把右侧票据的结论换一种形状重复，必须删除，而不是缩小、改色或换成拟物贴纸。

- **删除优先于换皮**：发现重复复核信息时，默认删除；不要把大核对表改成小状态块，把表格问题变成便签问题。
- **三问 Gate**：中央每个非角色、非器材、非候选、非任务短条的块，都必须回答：玩家会操作它吗？它是否提供角色 / 器材附近无法表达的新局部证据？删掉它是否会让派遣操作链断裂？三问全否则删除。
- **负空间允许成立**：中央可以留出干净的地图、纸面、路线、桌面阴影和档案层次；这些拟物空间不需要被状态标签填满。空一些不等于空心，前提是人员席位、器材和候选操作已经清楚。
- **复核单一承载位**：签批状态、风险、耗时、缺口、有效点和盖章前确认只在右侧票据完整表达。中央若需要局部证据，只能贴在角色卡、器材槽或任务短条上。
- **父级整合责任**：subagent 给出"合并到右侧 / 删除重复"的结论后，父级 Codex 不得折中保留同义残留块。若仍不确定，先交付更少元素的结构稿，而不是添加解释性状态块。

### 12.6 拟物物件必须对应真实机制（2026-06-23）

派遣签批台可以有任务地点、地图纹理、路线暗线、图钉和档案纸层来增强外勤感，但这些元素不得暗示游戏内不存在的操作。若游戏没有路线规划、站点选择或路径分配，中央就不能把"路线纸 / 去哪里 / 地图线路"作为高权重功能物件。

- **真实机制优先**：中央拟物物件优先对应 `本次骰池`、`角色骰`、`辅助骰位 / 一次性道具骰`、`需求覆盖 / 有效点目标`、`签批后进入角色骰判定`。
- **路线降级**：路线、地名、图钉、地图折面只能作为背景装饰或任务身份线索，不得拥有标题、字段、按钮、状态、强描边或主要视觉面积。
- **物件越界检查**：每个拟物物件都要回答"玩家是否真的会在游戏里操作 / 判断这个对象"。答案是否时，只能作为无字装饰或 no-text 层；不能成为功能区。
- **中央替代表达**：需要外勤代入感时，优先把"人员证件卡被放入本次骰池""一次性道具骰写回辅助骰位""签批后进入角色骰判定"做成桌面物件，而不是发明路线规划物件。

### 12.7 骰面 / 覆盖不得常驻摊成中央表（2026-06-23）

即使要回到真实机制，也不得把角色骰面、道具骰面、需求覆盖或来源明细常驻摊成中央独立表格。若这些信息可以集成在角色卡、候选卡、道具卡或 hover / 详情层里，就不应占用中央主舞台。

- **卡牌内聚优先**：角色贡献、dice net、适配、补缺和移出动作优先放在角色卡 / 道具卡本体；中央只表达这些卡已经被投入当前任务。
- **苏丹式部署语法**：可参考《苏丹的游戏》的 `候选手牌池 -> 当前事件 / 任务承载 -> 投入卡牌 -> 右侧说明 / 确认`。学的是部署关系，不是宫廷皮肤、旧羊皮纸或整屏装饰。
- **表格降级**：完整骰面矩阵、来源明细和覆盖表默认进入 hover、详情、调试或右侧短说明；不得作为中央常驻主物件。
- **中央空间优先级**：中央空间优先给任务案卷承载台、已选卡槽、空槽、随队器材槽和当前投入卡之间的归属关系，而不是给解释表。

### 12.8 底层重构不得沿用旧骨架换皮（2026-06-23）

当用户要求"从底层重新思考界面怎么布置"时，不能只把旧页面的四栏骨架换成新标题、新纸张或新拟物称呼。派遣签批台 V9 复盘已确认：如果页面仍是 `左任务 + 中央已选卡 + 右复核票据 + 底部候选库存`，即使中间画了案卷、图钉或纸层，也仍然是旧结构。

- **骨架剪影检查**：遮住文案和材质，只看大块位置。若仍能一眼认出旧四栏，就不得称为底层重构。
- **动线重排检查**：新结构必须改变玩家视线顺序和操作动作，例如从 `候选手牌 -> 当前案卷 -> 本次队伍 -> 右下盖章` 读起，而不是继续 `左读题 -> 中停卡 -> 右看数 -> 下补卡`。
- **职责迁移检查**：至少改变两类关键职责的位置或关系：候选层、当前队伍、任务承载物、签批回执、CTA 锚点。只改变宽度、高度、标签或装饰不算。
- **旧稿降级**：V8.2 的苏丹式经验只保留"卡牌投入语法"；V9 降级为旧骨架换皮反例。后续真实内容风格稿和生图 prompt 不得以 V9 作为布局基准。
- **父级自检责任**：在让用户看图前，父级 Codex 必须先写出一句新的玩家动作流。写不出，或写出的句子与旧版相同，就先重排结构，不要交付截图。

### 12.9 左右栏成立时只重构中间主舞台（2026-06-23）

若用户明确指出左右两边栏目没有问题，父级 Codex 不得继续推翻整屏。此时问题域应锁定在中间主舞台：如何让中间空白成为"当前派遣现场"，而不是新增功能或重复右侧复核。

- **保留边界**：左侧继续承载任务卷宗 / 简报 / 外勤目的；右侧继续承载签批票据 / 复核清单 / 盖章 CTA；底部继续作为候选员工与器材抽屉。
- **中间改造目标**：把已选角色、空槽、随队器材和任务案卷底板组织成一个 `当前外勤承载台`。玩家第一眼应看到"这支队伍已经被放到 M330 案卷上"，而不是看到空桌面或后台状态条。
- **不新增功能**：不得用路线规划、中央骰池表、覆盖矩阵、队伍关系、伪状态块或解释便签填补空白。空白应通过卡片尺寸、纸层、压入关系、器材嵌入条和拟物背景解决。
- **局部证据位置**：角色贡献、补缺、低贡献风险放在角色卡和器材卡上；完整达标率、耗时、缺口和盖章前状态仍归右侧票据。
- **交付前检查**：只裁切中间区域看 5 秒，必须能回答"派谁 / 带什么 / 还缺哪个槽 / 卡片属于哪份任务"。若不能，先重排中间，不动左右。

## 13. 跨页面控件与资产化几何规则

### 13.1 任务级 CTA 与全局推进动作不得相邻（2026-06-18）

当一个页面同时存在"当前对象确认动作"和"全局时间 / 阶段推进动作"时，必须把二者在空间、材质、颜色语法和点击热区上分离：

- 当前对象动作只作用于当前选中任务、卡片、稿件或队伍，例如 `进入派遣签批`、`签批本次派遣`。
- 全局推进动作会改变天数、周阶段、结算或世界状态，例如 `推进一天`、`结束探索周`、`进入发刊结算`。
- 全局推进动作不得放在当前对象主 CTA 的正下方、右侧紧邻、同一托盘内或同一视觉延长线上；玩家不能因为追随主 CTA 动线而误触全局推进。
- 两者不得共享按钮底图、颜色语法、装饰托盘或 hit rect；资产化 UI 中必须拆成独立 atlas、状态矩阵和安全区。
- 全局推进若可能造成任务错过、截稿流失、占用天数或状态结算，应提供确认态、长按、二次点击或等价误触保护。

本规则由地区任务台 v3.6 触发：`进入派遣签批` 属于右侧任务详情，`推进一天` 属于底部全局日程条，二者不得相邻。

### 13.2 功能面正交与几何 QA（2026-06-18 / 06-29 / 07-06 收敛）

完整规则见 [`ui-geometry-and-text-safety-gates.md`](../workflows/ui-geometry-and-text-safety-gates.md)：功能承载页必须方正（§2.1，1 度阈值与一票否决 prompt 句）、几何 QA 自动触发与最低证据（§2.2 / §2.3，参考线必须贴真实边缘、无证据只能写"几何未验证"）、`text_geometry_pass` 与 `art_shell_geometry_pass` 双通行证（§3，文字正交不等于美术壳正交）。本文只保留以下补充判断器：

- **倾斜复发即切分层路线**：同类功能行（文字 / 点击 / 状态面）连续两轮因倾斜失败时，必须停止 prompt-only 整屏有字生图微调，改为"生图无字外观 + 正交功能资产 / 运行时文字层 / 可测量 mask"的分层资产化流程；发现"文字层正、底层壳斜"时同样退回分层资产，重建正交 no-text 壳并锁定 shell manifest 后再回填文字，不得继续调字号、调 safe zone 或在整屏图上补贴片。
- **低多边形色块只能是材质，不是褶皱或箭头**：功能文字槽内允许低对比大块面色差，但不得出现会被读成折痕、撕裂、压痕、高对比斜线、尖刺、箭头、路线指示或按钮延伸的形状；即使尖形块面没有越过 `visual_module_rect`，只要它刺向文字槽、图标槽或 action plate，也判定失败。文字槽越核心，色块越克制，优先横向压边、宽面明暗和低对比矩形块。
- **风格优势不豁免方正**：若生成结果文字嵌合、颜色和质感更好但信息面倾斜，仍降级为偏差样本；交付时优先同时附"原图 + 正交 QA 图 / 局部裁切"。

### 13.3 拟物纸张与动态文字安全区（2026-06-15）

世界地图、档案夹、票据、索引卡、签批纸等资产化 UI 可以使用倾斜纸页、叠页、夹子、口袋和标签制造拟物层次，但凡承载动态文字、数字、状态或按钮文案的正面区域，必须优先满足可布局性。正交阈值、图像等比（`image_aspect_pass`）与图槽契约（`image_slot_contract_pass`）见 gates 真源 §2 / §4；本文保留以下执行要点：

- **正交不等于扁平化**：功能组件通过正交 Gate 后，还必须保留所属风格稿的材质语言。对 clean low-poly weekly / WMW 支线来说，左卡、右侧 dossier、CTA、ticker、票据和地图板即使正面 0 度，也应保留大块低多边形平面色块、4-8 个主要明度块面、块状明暗面和克制的裁纸阴影；只有动态文字中心槽需要安静，且不得有明显褶皱 / 折痕 / 撕裂线穿过。若修正交后组件变成纯平空白矩形、SaaS 表单条或软件面板，应判定为风格保留失败。
- **装饰不得压内容边距**：三角兜、夹子、书签、色块、箭头、半调网点、折角、螺丝和装订边只能压在装饰层或禁入区，不得覆盖卡片正文框、标题槽、状态槽、按钮 label 槽和可读外边距。
- **先画视觉可写区，再落文字**：资产验收时不能只看控件 rect 是否未出界，要标出真实可写纸面、no-text rect 和至少 32px 视觉安全边距，再决定 Godot 动态层的位置。
- **底部 / 末张卡优先检查**：叠页和档案夹最容易在最后一张卡、底部 CTA、右侧详情纸板发生遮挡或斜切；截图验收必须局部裁切检查这些区域，而不是只看整屏远景。
- **不靠缩小字体补救资产问题**：如果 PNG 本身没有正交可写区或可读边距不足，应重出美术资源；不要通过减小字号、贴边排版或把文字挤进斜面来硬塞。

### 13.4 美术标杆必须转译成组件生产语法（2026-06-24）

当用户给出新的 UI / 美术风格标杆时，父级 Codex 不能只生成一张"看起来像标杆"的 moodboard、style board 或整屏相似图。除非用户明确要求只要灵感图，否则下一步必须把标杆转译成 Angus 真实界面的组件改造蓝图。

- **先盘点真实组件**：至少覆盖世界地图、地区任务台、派遣签批台、报道 / 发刊、角色 / 骰子、全局 HUD 中反复出现的组件，例如主舞台、地区索引卡、地图 pin、任务卡、详情纸、角色卡、候选抽屉、签批票据、主 CTA、全局推进、ticker、弹窗和状态贴纸。
- **每类组件必须给生产语法**：输出该组件应读作什么物件、承载什么玩家决策、对应哪些 `content_rects / no_text_rects / hit_rects`、需要哪些状态矩阵，以及哪些信息不得烘焙进底图。
- **标杆只提供语言，不替代功能分区**：风格元素只能包装既有真实功能；不得为了贴近标杆新增不存在的路线规划、后台终端、证据墙或装饰性状态块。
- **组件化不得变成面板化**：把标杆用于真实 UI 时，不能只保留功能骨架而丢掉标杆的资产板密度、纸件叠层、色彩文件夹、大胆周刊版式、贴纸 / 夹子 / 照片 / 色票 / 图标系统。若第一眼不像用户给的标杆，即使可操作区清晰，也只能算偏差稿。
- **低多边形必须先看块面颗粒度**：低多边形是大块概括、手绘裁纸感和形状经济，不是密集三角网、GIS 终端纹理、摄影噪声或票据微装饰。大块剪影先成立；票条、ticker、CTA 同屏只保留极少微细节，孔洞、条码、点阵、短刻度、微线不得堆叠。
- **低多边形必须留在组件本体上**：不能只让缩略图 / 快照保留低多边形，而把功能组件外壳做成平面 UI；左卡壳、右 dossier 纸面、CTA plate、底部 receipt 和状态票据都必须继承大块面语言，但文字组件上不能出现纸张被折起的褶皱线。
- **先做单组件或单状态 vertical slice**：优先选一个真实状态验证图文功能融合，通过后再扩展全屏、多状态和运行时。
- **生图 prompt 必须带组件约束**：声明目标组件、动态文字空白区、禁写区、状态层和运行时动态字段；不得只写"照着标杆风格做一张界面"。
- **交付必须说明可落地性**：说明哪些部分是 bitmap 底图、哪些是动态 UI、哪些需要独立 atlas / 状态贴图、哪些只是灵感图不能直接切入运行时。

### 13.5 修标杆组件不得扩大成整屏重生（2026-07-01）

当用户的目标是"把标杆组件改正、包装成实际游戏界面可用的组件"，不得把任务升级为反复生成完整世界地图、完整地区页或完整派遣页。整屏生图会重新采样布局、色调、材质、地图块面和按钮语法，容易把已经认可的标杆特征洗掉。

- **锁定不变项**：标杆的深色主场、纸品色号、大块低多边形色面、手绘贴纸符号、现代周刊物件和已认可布局先冻结；本轮只修组件可落地问题。
- **先组件板后整屏**：优先输出 `component_correction_sheet`，覆盖地区卡、右侧 dossier、CTA、底部 receipt、状态票据、贴纸 icon、标题条和 folder tab。组件板只验证组件语法，不验证整屏动线。
- **最小改造目标**：只解决正交、动态文字可写区、按钮 / 框体嵌合、状态矩阵、图标手绘感、低多边形块面保留和色号漂移；不得顺手重画世界地图、路线、任务内容或全屏构图。
- **回填验证**：组件板通过用户把关后，再选一个真实状态把组件回填到单屏验证。未通过组件板，不进入 atlas、manifest 或 Godot runtime。
- **产物命名**：这种图只能叫组件转译候选或组件校正板；在完成真实中文填充、几何 QA、色号复采样和像素艺术复审前，不得叫生产标杆或资源真源。

### 13.6 WMW 支线纸张材质必须先锁定（2026-07-01）

Clean low-poly weekly / WMW 支线里，纸张不是普通背景色，而是核心材质语言。后续世界地图、地区界面、任务派遣、票据、dossier、CTA 和状态卡只要使用该支线纸品组件，就必须先引用 `design/art-direction/clean-lowpoly-weekly-paper-material-contract.md`，不得只靠 prompt 写"高级灰 / warm beige / paper texture"让模型自由生成。

- **纸张真源来自标杆裁切**：使用 `docs/screenshots/2026-07-01-wmw-component-correction/13-wmw-paper-material-truth-board-v0-3.png` 与对应 JSON token 作为纸张校色尺。失败候选图不能反向成为纸张真源。
- **先材质后整屏**：先声明组件使用哪个纸张 token，再做组件板、单状态 mock 或整屏回填。没有纸张 token，不进入风格通过判断。
- **分层实现**：纸张至少拆成 base color、flat low-poly value planes、subtle print tooth、edge/rim、shadow/backing page。可写纸面保持干净；边缘和阴影承担物理层次。
- **禁止旧纸误读**：不得把低多边形明度块生成为云状污渍、褶皱、撕裂、旧档案脏污、泛黄旧档案或纸张破损。
- **生产建议**：若要追求稳定一致，生图只负责形状和氛围，纸张可通过 mask、材质 atlas 或 Lab 色彩归一化回到标杆 token；不要每次全局重调整张图。
